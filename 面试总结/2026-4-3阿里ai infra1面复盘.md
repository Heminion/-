### **【Q2】查询优化你是怎么定位问题、怎么解决的？是在线上开慢查询，还是离线复现？**

高分回答：

我会按“定位 - 分析 - 验证”三步来做。

**第一步，定位：**

1. 先从接口监控和业务反馈确认哪个接口慢
2. 再结合 MySQL 慢查询日志，找到具体 SQL
3. 如果线上允许，就在受控范围内开启慢查询并采样；如果线上不适合开太细，就在测试环境根据真实参数复现

**第二步，分析：**

1. 用 `EXPLAIN` 看执行计划，重点看 `type`、`key`、`rows`、`extra`
2. 回到代码里看是否有 N+1 查询、循环查库、索引失效、回表过多等问题

**第三步，解决：**

我当时那个案例里，本质问题是 N+1 查询。原逻辑是先查城市，再按城市循环查对应房源，导致一次请求触发多次 SQL。我把它改成了 `JOIN`，同时补充高频过滤字段索引，最后把接口耗时从大概 500ms 降到 50ms。

如果面试官继续追问“线上直接开慢查询会不会有风险”，我会补一句：线上可以开，但要控制阈值、采样范围和持续时间，不能为了排障长期粗暴全开。

### **【Q3】你说的循环查询具体是什么？为什么改成 JOIN 会更好？**

高分回答：

循环查询就是典型的 N+1。

比如业务上我要查一个城市下的房源，原来逻辑可能是：

1. 先查城市列表
2. 再遍历每个城市
3. 每个城市再查一次房源表

这样的问题是：

1. SQL 次数很多，数据库往返成本高
2. 每次查出来的数据量可能都不大，但整体累计开销很高
3. 代码层还有大量拼装逻辑，可维护性差

改成 `JOIN` 后，数据库一次性完成关联和过滤，能够：

1. 减少多次网络往返
2. 让优化器统一选择更优执行计划
3. 利用索引和批量处理能力

一句话总结：**N+1 是“把数据库擅长做的关联，拆成了应用层很多次小查询”，所以通常应该让数据库一次做完。**

---

### **【Q4】MySQL 为什么常用 B+ 树索引？它比二叉树、B 树、哈希索引好在哪？**

高分回答：

MySQL InnoDB 的主流索引结构是 B+ 树，核心原因是它在磁盘场景下综合表现最好。

和二叉树相比：

1. B+ 树是多路平衡树，一个节点可以放很多 key
2. 树高更低，磁盘 IO 次数更少

和 B 树相比：

1. B+ 树非叶子节点只存 key 和指针，不存整行数据
2. 同样大小的页能容纳更多 key，所以树更矮
3. 所有数据都在叶子节点，叶子节点天然有序，范围查询更高效

和哈希索引相比：

1. 哈希索引等值查询快
2. 但不擅长范围查询、排序和最左前缀这类能力
3. B+ 树兼顾单点查和范围查，更适合通用数据库场景

面试里可以再补一句：**为什么树矮更好？因为磁盘页访问是主要成本，树高每降低一层，就可能少一次随机 IO。**

## 2. 缓存与分布式设计

### **【Q5】你做的 Redis 缓存优化和重构，具体做了什么？**

高分回答：

我那次优化不是简单“把数据放到 Redis”，而是做了两类治理：

**第一类是代码层复用治理：**

原先很多缓存逻辑散落在不同地方，存在 key 命名不统一、过期时间不一致、重复代码多的问题。我把这部分逻辑抽出来做统一封装，让读缓存、写缓存、删缓存这些流程更标准。

**第二类是业务层隔离治理：**

我遇到过多语言场景下缓存串数据的问题，所以把语言维度显式拼进 Redis key 里，比如：

`cache:room:{lang}:{id}`

这样不同语言版本的数据天然隔离，不会互相污染。

如果再抽象一下，这次优化解决的核心问题是：

1. 提升缓存逻辑的一致性和可维护性
2. 避免多语言、多场景共用 key 导致的脏读

---

### **【Q6】为什么选 Redis，不选本地缓存？如果用一致性哈希把请求打到固定机器做 local cache，可行吗？**

高分回答：

这个方案是可行的，但要看场景。

**为什么我当时优先选 Redis：**

1. Redis 是**集中式缓存**，多实例服务**天然共享数据**
2. 数据更新后，其他服务实例可以立刻**读到最新值**
3. 运维、监控、TTL、淘汰策略都比较成熟

**本地缓存 + 一致性哈希的优点：**

1. 访问链路更短，延迟更低
2. 不依赖外部 Redis，热点命中性能可能更高

**它的代价：**

1. 扩容缩容时哈希分布会变，迁移复杂
2. 一致性、失效通知、容灾、监控都要自己做
3. 多副本、热点倾斜、节点宕机处理复杂度更高

所以如果是：

1. 数据规模不大
2. 追求极低延迟
3. 更新频率低

本地缓存方案有价值。

但如果是通用业务缓存、多个服务实例共享、需要成熟运维能力，我更倾向 Redis。

一句话总结：**Redis 胜在共享和成熟，本地缓存胜在极致低延迟。**

---

### **【Q7】Redis 是怎么分片的？常见部署方式有哪些？**

高分回答：

如果面试官问 Redis 分片，通常是想看你对 Redis 工程化部署有没有概念。

常见模式可以这么分：

1. **单机 Redis**：最简单，但容量和可用性都有限
2. **主从 + 哨兵**：解决高可用，哨兵负责故障转移，但数据仍是单分片
3. **Redis Cluster**：真正的分布式分片方案，把 key 映射到 16384 个哈希槽，再分配到多个节点

Cluster 下，分片逻辑不是“业务自己决定一台机器”，而是：

1. 先对 key 做 CRC16
2. 再对 16384 取模，得到哈希槽
3. 这个槽归哪个节点，就路由到哪个节点

所以如果问“Redis 是单分片还是多分片”，要看部署模式：

1. 主从 + 哨兵是单分片高可用
2. Cluster 才是多分片分布式

### **【Q8】Redis 的淘汰策略和过期删除机制有哪些？LRU / LFU 是什么？**

高分回答：

这里最好把“过期删除”和“内存淘汰”分开说。

**过期删除：**

Redis 对设置了 TTL 的 key，不是到点立刻全部同步删掉，而是结合两种机制：

1. **惰性删除**：访问 key 时发现它过期了，就顺手删掉
2. **定期删除**：后台周期性抽样扫描一部分过期 key，删除其中已过期的数据

这样做是为了在 CPU 开销和内存回收及时性之间做平衡。

**内存淘汰：**

当 Redis 达到 `maxmemory` 后，会按配置策略淘汰 key，常见的有：

1. `noeviction`：不淘汰，写入报错
2. `allkeys-lru`：从所有 key 中按最近最少使用淘汰
3. `volatile-lru`：只在设置了过期时间的 key 里按 LRU 淘汰
4. `allkeys-lfu`：从所有 key 中按最少使用频率淘汰
5. `volatile-lfu`：只在有过期时间的 key 里按 LFU 淘汰
6. `allkeys-random` / `volatile-random`：随机淘汰
7. `volatile-ttl`：优先淘汰剩余 TTL 更短的 key

**LRU** 是最近最少使用，认为“最近很久没用过”的数据更可能以后也不用了。  
**LFU** 是最少使用频率，认为“历史上用得少”的数据更适合淘汰。

### **【Q9】如果让你自己实现一个 LRU 缓存，应该怎么做？为什么是 HashMap + 双向链表？**

高分回答：

LRU 的目标是同时满足两件事：

1. `get` / `put` 尽量是 `O(1)`
2. 能快速知道“最近最少使用”的那个元素是谁

所以最经典的数据结构是：

1. **HashMap**：`key -> 节点`，保证能 `O(1)` 找到元素
2. **双向链表**：按访问顺序维护节点，最新访问的放头部，最久没访问的在尾部

为什么是双向链表，不是单向链表？

1. 因为节点被访问后，要把它从原位置摘下来再挪到头部
2. 双向链表删除任意节点是 `O(1)`，单向链表通常还得先找前驱

标准操作：

1. `get(key)`：如果命中，节点移到链表头部
2. `put(key, value)`：
   如果已存在，更新值并移到头部
   如果不存在，插入头部
   如果容量超限，删除尾节点，同时从 map 移除

一句话总结：**HashMap 负责快查，双向链表负责维护访问顺序。**

## 3. Java 并发与 JVM 思维

### **【Q10】如果让你实现一个并发安全的 Map，你会怎么做？ConcurrentHashMap 大概是什么思路？**

高分回答：

这个题最好按“从简单到高性能”的思路答。

**最简单实现：**

1. 用普通 `HashMap`
2. 外面套一把大锁，比如 `synchronized`

这样肯定线程安全，但并发性能差，因为所有读写都串行。

**进一步优化：**

1. 可以分段加锁，减少锁粒度
2. 读多写少场景可考虑读写锁
3. 更进一步可以使用 CAS + 局部 synchronized 的组合

如果问到 `ConcurrentHashMap`，JDK 1.8 的核心思路可以答成：

1. 底层仍然是数组 + 链表 / 红黑树
2. 读操作尽量无锁
3. 写操作对桶位或节点做更细粒度同步，而不是整张表一把大锁
4. 插入、扩容等过程会结合 CAS，减少锁竞争

面试里高分点不是把源码背全，而是说出：**它比“大锁包住 HashMap”更高并发的原因，是锁粒度更细，读操作更少阻塞。**

---

### **【Q11】`synchronized`、`ReentrantLock`、乐观锁分别是什么？怎么提高并发性能？**

高分回答：

**`synchronized`：**

1. Java 内置监视器锁
2. 属于悲观锁思路
3. 使用简单，JVM 还能做偏向锁、轻量级锁等优化

**`ReentrantLock`：**

1. 也是悲观锁
2. 但功能更丰富，支持可重入、可中断、超时、公平锁等能力
3. 不代表它天然就一定比 `synchronized` 快，要看场景

**乐观锁：**

1. 核心思路是先假设冲突少
2. 更新时再检查数据有没有被别人改过
3. 常见实现是版本号或 CAS

如果目标是提高并发性能，方向不是“把 `synchronized` 换成 `ReentrantLock` 就完了”，而是：

1. 减少锁粒度
2. 读写分离
3. 用 CAS 或版本号减少互斥
4. 避免长时间持锁

一句话总结：**悲观锁是先锁再做，乐观锁是先做再校验。**

---

### **【Q12】版本号乐观锁怎么实现？读写并发时怎么控制？它有什么局限？**

高分回答：

乐观锁最经典的实现方式就是版本号。

假设一条数据有 `value` 和 `version` 两个字段，更新流程是：

1. 先读取当前值和当前版本号，比如 `version = 5`
2. 修改时带上旧版本条件：
   `update ... set value = ?, version = version + 1 where id = ? and version = 5`
3. 如果受影响行数是 1，说明更新成功
4. 如果是 0，说明这期间数据被别人改过，需要重试或返回失败

它的特点是：

1. 读不加锁
2. 写时做冲突检测
3. 冲突少时性能较好

局限也要主动说出来：

1. 高冲突场景下会频繁失败重试
2. 只能保证更新时检测冲突，不代表所有复合业务逻辑天然安全
3. 如果有多个字段、多个步骤组合修改，仍可能需要更强的一致性控制

---

### **【Q13】对象池怎么实现？怎么让对象尽量不被频繁 GC？**

高分回答：

对象池的目标，是复用那些“创建成本高、初始化重、重复创建浪费大”的对象。

实现思路一般是：

1. 预先创建一批对象
2. 放到一个池子里维护空闲对象
3. 使用时从池子里借
4. 用完后归还，而不是直接丢弃

数据结构上常见会用：

1. 阻塞队列，比如 `ArrayBlockingQueue`
2. 或者链表 / 双端队列维护空闲对象

为什么这样对象不容易被 GC？

1. 因为池子本身持有这些对象的强引用
2. 只要对象仍被池子引用，就不是垃圾对象

如果是并发场景，还要考虑：

1. 借还超时
2. 最大池大小
3. 对象有效性检测
4. 泄漏回收

一句话总结：**对象池不是“让对象永远不回收”，而是通过长期持有可复用对象的引用，降低频繁创建和回收的成本。**

## 4. 数据结构与算法

### **【Q14】给你一个数组和一个整数 K，求和为 K 的连续子数组个数，怎么做？**

高分回答：

这题标准解法是 **前缀和 + HashMap**，时间复杂度 `O(n)`。

核心思路：

1. 定义前缀和 `pre[i]` 表示从 `0` 到 `i` 的累加和
2. 如果某一段子数组 `sum(i..j) = k`
3. 那么就等价于 `pre[j] - pre[i-1] = k`
4. 也就是在遍历到当前位置时，只要之前出现过 `curSum - k` 这个前缀和，就说明存在若干个满足条件的子数组

实现时：

1. `map` 存“某个前缀和出现过多少次”
2. 初始化 `map.put(0, 1)`，表示空前缀和出现一次
3. 每遍历一个数，先累加到 `curSum`
4. 答案加上 `map.getOrDefault(curSum - k, 0)`
5. 再把当前 `curSum` 放回 map

为什么滑动窗口不一定行？

因为数组里可能有负数，窗口和不具备单调性，无法稳定收缩。

---

### **【Q15】HashMap 底层怎么实现？`put` 流程、扩容、树化这些点怎么讲？**

高分回答：

JDK 1.8 的 `HashMap` 底层是 **数组 + 链表 + 红黑树**。

**`put` 流程：**

1. 先根据 key 计算 hash
2. 再通过 `(n - 1) & hash` 定位桶下标
3. 如果桶为空，直接插入
4. 如果桶不为空，就判断是链表还是树
5. 如果 key 已存在，覆盖旧值
6. 如果不存在，就追加到链表尾部或插入树中
7. 插入后如果元素个数超过阈值，就触发扩容

**扩容：**

1. 默认容量通常是 16，负载因子默认 0.75
2. 当 `size > capacity * loadFactor` 时扩容
3. 新容量通常变成原来的 2 倍
4. 然后对元素重新分配位置

JDK 1.8 有个常考优化点：

扩容时元素不一定都重新完整计算一次位置，而是看 hash 的某个新增高位 bit 是 0 还是 1，来决定元素留在原索引还是移动到 `原索引 + oldCap`，这样迁移效率更高。

**树化：**

当单个桶上的链表长度过长时，会转成红黑树，目的就是把查找复杂度从 `O(n)` 降到 `O(log n)`。

一句话总结：**HashMap 用数组定位桶，用链表或树解决哈希冲突。**

## 5. AI 工程化与开发方式

### **【Q16】你平时会用 AI 参与开发吗？AI 现在能介入到什么程度？**

高分回答：

会，但我不会把 AI 当成“自动写完一切”的黑盒，而是把它放在可控流程里用。

我一般会这样接入：

1. **需求拆解**：先让 AI 帮我把需求拆成功能点和边界情况
2. **代码生成**：生成接口骨架、DTO、校验逻辑、基础测试样例
3. **Review 与修正**：我自己负责确认业务正确性、边界条件、异常处理和风格一致性
4. **排障与重构**：让 AI 帮我分析报错、梳理调用链、给重构建议

我会把 AI 覆盖率说成：

1. 模板化、重复性、结构化代码，AI 覆盖率很高
2. 业务边界、数据一致性、复杂并发和最终质量把关，仍要工程师负责

这样回答会比“70% 或 80%”这种纯比例式回答更成熟。

### **【Q17】你做开发时怎么处理单测、corner case 和最终验证？**

高分回答：

我不会只让 AI 生成代码，然后直接相信它。

一般流程是：

1. 先明确输入输出和异常路径
2. 让 AI 帮我补基础测试样例
3. 我自己重点补 corner case，比如空值、边界值、重复请求、异常路径
4. 最后结合日志、接口联调和真实数据再做一次验证

如果面试官继续追问，我会强调一句：**AI 可以帮我提速，但不能替代测试设计和结果验收。**

### **【Q18】如果让你做知识库、Skill 或 Agent，你会怎么设计？**

高分回答：

我会从“场景、知识、检索、执行、评估”五步去设计。

1. **先定场景**：明确是代码问答、排障助手、业务知识检索，还是自动执行工具
2. **整理知识源**：文档、代码库、FAQ、接口定义、历史案例
3. **做检索层**：结构化信息走数据库或搜索，非结构化文档走向量检索或混合检索
4. **做工具层**：把常用能力封装成工具，比如查日志、查接口、生成 SQL、执行脚本
5. **做评估层**：看命中率、回答准确率、幻觉率、人工接管率

如果做 Skill 或 Agent，我会特别注意两点：

1. 给模型清晰的输入边界和权限边界
2. 让关键动作可审计、可回放、可回滚

因为真正落地时，难点不只是“能回答”，而是“稳定、可信、可控”。
