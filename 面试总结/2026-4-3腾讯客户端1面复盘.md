## 1. 项目深挖与高并发设计

### **【Q1】你简历里写了查询优化，能不能结合案例讲清楚你具体做了什么？**

高分回答：

可以。我当时优化的是房源列表查询接口，定位问题分三步：

1. 先通过慢查询日志和接口监控，发现这个接口 RT 偏高，平均大概在 500ms 左右
2. 再去看代码实现，发现存在明显的 N+1 查询问题：先查城市，再按城市循环查房源，导致一次请求会打很多次 SQL
3. 最后用 `EXPLAIN` 看执行计划，发现高频过滤字段索引利用也不够好

对应优化我做了两件事：

1. 把循环中的多次单表查询改成 `JOIN`，减少数据库往返次数
2. 给高频过滤条件补上合适索引，避免全表扫

最终效果是接口耗时从大约 500ms 降到 50ms 左右。

如果面试官继续追问，我会补一句：这类优化本质上是在同时解决“SQL 次数过多”和“单次 SQL 扫描过重”两个问题。

---

### **【Q2】Lua 脚本在你的秒杀项目里具体做什么？为什么它在高并发下是安全的？**

高分回答：

Lua 在我项目里的作用是把“校验资格 + 扣减库存 + 记录一人一单 + 入队”这几个步骤放到 Redis 里一次性执行。

具体会做四件事：

1. 判断库存是否充足
2. 判断用户是否已经下过单
3. 扣减 Redis 库存
4. 把订单消息写入消息队列，交给后端异步落库

它高并发下安全，核心原因不是“Lua 语法本身线程安全”，而是：

1. Redis 执行命令是单线程串行模型
2. Lua 脚本在 Redis 内部是作为一个整体原子执行的
3. 执行过程中不会被其他命令插入打断

所以它能避免“先查库存，再扣库存”这类拆开的多步操作在并发下出现超卖或重复下单。

一句话总结：**Lua 解决的是 Redis 侧多命令组合操作的原子性问题。**

---

### **【Q3】秒杀里为什么要引入消息队列异步处理？它解决什么问题？比同步直接落库强在哪？**

高分回答：

消息队列在秒杀场景里主要解决三件事：**削峰、异步、解耦**。

在我的项目里，用户请求到来后，请求线程不会直接去操作 MySQL，而是先在 Redis 用 Lua 做资格校验，校验通过后把订单写入消息队列；真正的创建订单、扣数据库库存、写订单表，由后台消费者异步处理。

这样做的价值有三点：

1. **削峰**：高峰流量先堆到队列里，数据库按自己的消费能力慢慢处理，避免被瞬时流量打垮
2. **降低 RT**：主线程只做 Redis 校验和入队，能很快返回，用户感知更好
3. **解耦**：抢购资格和订单落库分离，后面更容易做重试、监控、补偿

如果直接同步落库，请求线程要立即打数据库，在秒杀这种瞬时高并发场景下很容易把 DB 压垮，RT 和失败率都会明显变差。

当然它也有代价：用户可能先看到“抢购成功”，但后续消费失败导致没真正成单，所以要靠幂等、重试、监控和状态查询来兜底。

### **【Q4】如果让你设计一个千万级的秒杀优惠券系统，你会怎么设计？存储层还能怎么优化？**

高分回答：

如果按千万级秒杀来设计，我会把链路拆成四层：

1. **接入层限流**：Nginx 或网关做限流、黑名单、验证码，先挡掉明显无效流量
2. **Redis 资格校验层**：库存预热到 Redis，用 Lua 原子完成库存判断、一人一单判断和预扣减
3. **消息队列层**：资格通过后只入队，不在主线程写库
4. **异步落库层**：消费者按能力写 MySQL，做幂等校验、条件扣库存和失败补偿

存储层优化不能只说“加唯一索引”，那更多是保证正确性，不是核心性能优化。真正的优化点一般有：

1. **冷热分离**：热点库存判断放 Redis，DB 只做最终落库
2. **批量化 / 异步化**：数据库写入由消费者异步处理，必要时可批量 insert
3. **分库分表**：订单量非常大时，对订单表按用户或时间维度分片
4. **顺序写优化**：订单 ID 采用趋势递增，减少索引页分裂
5. **索引精简**：秒杀订单表保留必要索引，避免写放大

如果面试官继续问“怎么防重”，我会补一句：应用层幂等校验 + 数据库唯一约束要同时有，唯一约束是最后一道防线。

## 2. 鉴权与网络基础

### **【Q5】Cookie、Session、Token 各自是什么？有什么区别？**

高分回答：

这三个东西分别解决不同层面的问题，最好不要混着说。

**Cookie：**

1. 是浏览器端保存的一小段数据
2. 由服务端通过 `Set-Cookie` 下发，也可以由前端写入
3. 浏览器后续请求会自动携带符合域名/path 规则的 Cookie

它本身只是“存储载体”，不等于登录态。

**Session：**

1. 是服务端保存的会话数据
2. 通常服务端会给客户端一个 `sessionId`
3. 客户端后续带着 `sessionId` 来，服务端就能找到对应会话

它是传统的有状态登录方案，优点是服务端可控，缺点是分布式场景需要共享 Session。

**Token：**

1. 是服务端签发给客户端的一段凭证
2. 客户端通常放在请求头里，比如 `Authorization`
3. 服务端收到后进行校验，确认用户身份

Token 可以是有状态的，也可以是无状态的。比如：

1. JWT 是典型无状态 Token
2. 我项目里是随机 UUID + Redis 的有状态 Token

一句话区分：

1. Cookie 是客户端存储方式
2. Session 是服务端会话机制
3. Token 是身份凭证机制

### **【Q6】HTTPS 的加密过程怎么讲？**

高分回答：

HTTPS 本质上是 **HTTP + TLS**。它不是全程都用非对称加密，而是“非对称加密负责安全协商，对称加密负责后续传输”。

标准过程可以这么讲：

1. 客户端发起 TLS 握手，请求服务端证书，并带上自己支持的加密套件
2. 服务端返回证书、公钥以及自己选定的加密套件
3. 客户端校验证书是否合法，主要看 CA 签名、域名、有效期
4. 校验通过后，客户端生成一个随机的会话密钥材料，用服务端公钥加密发给服务端
5. 服务端用私钥解开，双方协商出同一个会话密钥
6. 后续 HTTP 数据传输就使用这个对称密钥进行加密

这样设计的原因是：

1. 非对称加密安全，但性能慢
2. 对称加密快，适合传大流量数据

HTTPS 主要解决三件事：

1. **加密**：防止中间人看到明文
2. **身份认证**：确认你连的是目标服务器
3. **完整性保护**：防止数据被篡改

### **【Q7】TCP 三次握手和四次挥手怎么讲才完整？**

高分回答：

**三次握手：**

1. 客户端发送 `SYN`，表示自己想建立连接，并告诉服务端自己的初始序列号
2. 服务端回复 `SYN + ACK`，表示自己同意建立连接，同时也带上自己的初始序列号
3. 客户端再回复 `ACK`，表示自己收到了服务端的确认

之所以需要三次，不是为了“形式上对称”，而是为了让双方都确认两件事：

1. 自己的发送能力正常
2. 对方的接收和发送能力正常

**四次挥手：**

1. 客户端发送 `FIN`，表示自己这边数据发完了
2. 服务端回复 `ACK`，表示知道了，但它可能还有数据没发完
3. 服务端数据发完后，再发送自己的 `FIN`
4. 客户端回复 `ACK`

这里容易说错的一点是：挥手过程中服务端第二次发的是 `FIN`，不是 `SYN`。

最后客户端会进入 `TIME_WAIT`，主要是为了：

1. 确保最后一个 ACK 能让服务端收到
2. 避免旧连接的报文影响后续新连接

---

### **【Q8】HTTP/2 有哪些新特性？和 HTTP/3 相比有什么区别？**

高分回答：

**HTTP/2 的核心改进：**

1. **二进制分帧**：不再是文本协议，更便于解析
2. **多路复用**：一个 TCP 连接上可以并发传多个请求，减少队头阻塞
3. **Header 压缩**：用 HPACK 压缩请求头，降低重复头部开销
4. **服务端推送**：服务端可主动推资源给客户端，不过现在实际使用不算多

**HTTP/3 的核心变化：**

1. 底层不再基于 TCP，而是基于 **QUIC over UDP**
2. 把传输层握手和加密协商进一步整合，连接建立更快
3. 避免了 HTTP/2 在 TCP 层仍然存在的队头阻塞问题

简单对比：

1. HTTP/2 解决的是“应用层复用效率”
2. HTTP/3 进一步解决的是“底层 TCP 队头阻塞和握手时延”

面试里一句高分总结可以这么说：**HTTP/2 是在 TCP 上优化 HTTP，HTTP/3 是直接绕开 TCP，用 QUIC 重新做一套更适合现代网络的传输方案。**

## 3. 并发与工程基础

### **【Q9】如果让你设计一个多线程下安全的数据读取，还要尽量保证性能，你会怎么做？**

高分回答：

这个题不能只答“加锁”，要先看读写比例。

如果是**读多写少**场景，我会优先考虑这几种思路：

1. **读写锁**：读操作共享，写操作互斥，提升读并发
2. **Copy-On-Write**：写时复制，读完全无锁，适合读远多于写的配置类场景
3. **乐观读**：比如 `StampedLock` 的乐观读，先无锁读取，冲突时再回退
4. **缓存快照**：维护只读快照，让读线程访问不可变对象

如果数据结构本身支持并发安全，也可以用像 `ConcurrentHashMap` 这类并发容器。

我的回答重点会放在一句话上：**线程安全和性能往往要结合读写模型一起设计，不能一上来就用大锁把所有线程都串起来。**

---

### **【Q10】如果让你自己设计一个线程池，你会怎么设计？它是怎么消费任务的？**

**核心组成：**

1. 核心线程数 `corePoolSize`
2. 最大线程数 `maximumPoolSize`
3. 阻塞队列 `workQueue`
4. 空闲线程存活时间 `keepAliveTime`
5. 线程工厂 `threadFactory`
6. 拒绝策略 `RejectedExecutionHandler`

**任务消费流程：**

1. 来一个任务，如果当前线程数小于核心线程数，直接创建核心线程执行
2. 如果核心线程满了，就把任务放入阻塞队列
3. 如果队列也满了，并且线程数还没到最大线程数，就继续创建非核心线程执行
4. 如果线程数已经达到最大值且队列也满了，就走拒绝策略
5. 非核心线程空闲超过 `keepAliveTime` 会被回收

如果让我自己实现，我底层一般会用：

1. 一个阻塞队列保存待执行任务
2. 一组工作线程不断从队列里 `take()` 任务执行
3. 用状态字段控制线程池运行、关闭和中断

高分点在于补一句：**线程池的价值不是“少写几行创建线程的代码”，而是统一管理线程生命周期、任务排队、资源上限和异常策略。**

### **【Q11】缓存击穿、穿透、雪崩分别是什么？**

高分回答：

**缓存穿透：**

查询一个根本不存在的数据，请求穿过缓存直接打到数据库。如果有人恶意构造大量不存在的 key，数据库会被打爆。

解决办法：

1. 缓存空对象
2. 布隆过滤器
3. 参数校验和限流

**缓存击穿：**

某个热点 key 失效瞬间，大量请求同时打到数据库。它的特点是“热点 key + 瞬时并发高”。

解决办法：

1. 互斥锁重建缓存
2. 逻辑过期 + 后台异步刷新
3. 热点 key 永不过期

**缓存雪崩：**

大量 key 在同一时间失效，或者 Redis 整体不可用，导致大量请求一起打到数据库。

解决办法：

1. 给 TTL 加随机值，避免同一时刻批量过期
2. 做 Redis 高可用
3. 多级缓存、限流、降级

一句话区分：

1. 穿透是“查不存在”
2. 击穿是“热点失效”
3. 雪崩是“很多 key 一起挂”

## 4. 算法与编码

### **【Q12】算法题 1：录音里题干不完整，但从对话看大概率是“最长无重复子串长度”这类滑动窗口题，应该怎么答？**

说明：这一题在录音中题干缺失，我这里是根据“找最长连续子字符串长度”的表述做的推断。

高分回答：

如果题目是“求最长无重复子串长度”，标准做法是**滑动窗口 + 哈希表**。

思路：

1. 用两个指针维护一个窗口 `[left, right]`
2. 用 `map` 记录字符最近一次出现的位置
3. 当 `right` 扫到一个重复字符时，把 `left` 移到“重复字符上次出现位置 + 1”和当前 `left` 的较大值
4. 每次更新窗口长度最大值

复杂度：

1. 时间复杂度 `O(n)`
2. 空间复杂度 `O(|字符集|)`

这类题的关键不是“暴力枚举所有子串”，而是利用窗口中“不重复”这个约束，让左右指针都只单调移动一次。

---

### **【Q13】算法题 2：解码字符串怎么做？**

高分回答：

如果是经典的 `k[encoded_string]` 解码题，比如 `3[a2[c]]`，最稳的解法是**双栈**或者**一个栈配合当前状态**。

核心思路：

1. 遇到数字，累计当前倍数 `num`
2. 遇到 `[`，把当前倍数和当前构造中的字符串压栈，然后重置
3. 遇到普通字符，就拼到当前字符串里
4. 遇到 `]`，就弹出上一个字符串和倍数，把当前字符串重复 `k` 次后拼回去

复杂度：

1. 时间复杂度和最终输出长度相关
2. 空间复杂度和嵌套深度相关

面试里最好主动补一句：**这种题适合用栈，是因为括号嵌套天然对应“后进先出”的处理顺序。**

## 5. AI 提效与工具意识

### **【Q14】现在 AI 冲击这么大，你平时有没有用 AI 做提效？有没有做过 MCP / Skill 这类工具？**

高分回答：

有，我现在会把 AI 放到日常开发流程里，但我把它定位成“提效助手”，不是“替我做最终决策的人”。

我通常这样用：

1. **需求理解阶段**：让 AI 帮我拆任务、梳理边界条件
2. **编码阶段**：按项目代码风格生成接口、DTO、基础 CRUD、测试样例
3. **排查阶段**：辅助分析报错、日志和可疑链路
4. **重构阶段**：帮我给出更清晰的函数拆分方案

如果面试官问有没有做过 MCP、Skill 之类的工具，我更好的回答方式不是直接说“没有”，而是：

我还没有完整做过 MCP 或 Skill 产品化，但我理解它们的方向本质上是把 AI 能力从“对话式帮写代码”提升到“可复用的工具链和工作流”。如果进入团队，我会优先补齐这块，包括：

1. 把常见操作封装成可调用工具
2. 给固定场景沉淀 Prompt 和知识库
3. 让 AI 能在受控上下文里稳定完成重复任务

这类回答会比单纯说“没做过”更有成长性。
