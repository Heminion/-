## 一、面试分析

这场滴滴后端一面是非常典型的简历深挖型后端面。面试官没有一上来大面积问八股，而是一直围绕简历里的实习、MySQL 优化、AI 抽取、秒杀系统和 Agent 项目追问：你为什么这么做、怎么一步步定位、方案为什么成立、有没有更优方案、底层原理是什么。

这场面试最核心的考察点有四个：

1. 简历真实性和项目掌握深度：写在简历上的每个结果都要能讲清楚背景、方案、取舍和验证方式
2. 后端基础：MySQL ACID、B+ 树、MVCC、Read View、慢查询优化、Redis 分布式锁、Lua 原子性
3. 系统设计思维：秒杀防超卖不能只背方案，要能解释为什么选 Redis Lua、乐观锁、异步下单、唯一索引等组合
4. 表达和读题能力：回答要先分层，再展开；算法题要先读清楚题意，不要急着套自己脑中的模板

这场主要失分点很明显：

1. 很多回答停留在“知道名词”，但没有把底层机制和业务场景串起来，比如 Redisson、ACID、MVCC
2. 秒杀系统没有讲出一套稳定的完整链路，乐观锁、悲观锁、Redis Lua、分布式锁之间的边界混在一起
3. MySQL 优化只说“改成 join 后变快”，但没有解释为什么 join 在这个场景合理，也没有说对比验证过程
4. AI 抽取项目没有先讲清楚输入、输出、字段、规则、校验和人工回显链路，导致面试官需要不断帮你追问
5. 算法题没有先确认“波兰表达式 / 前缀表达式”的定义，导致后面计算顺序理解错了

后续优先补三块：

1. 简历项目复盘：每个项目准备“背景 -> 问题 -> 方案 -> 为什么这样选 -> 结果 -> 如果重做怎么优化”
2. MySQL 和 Redis 底层：ACID、undo / redo log、MVCC、Read View、B+ 树、Redisson 必须能讲机制
3. 常见栈题：前缀表达式、后缀表达式、括号匹配、单调栈，至少要能现场写出 Java 代码

### 2. 我们先从你的实习经历开始。你通过 MySQL 日志定位性能瓶颈，这么做的背景是什么？你的分析思路是什么？为什么要定位 MySQL？怎么一步步推导？

高分回答：

这个优化的背景是 CRM 中台里有一个房源列表 / 房源详情相关接口，在数据量上来之后响应时间比较高，平均耗时大概在几百毫秒，用户侧表现是页面打开慢，运营侧批量查看房源时会明显卡顿。

我的分析思路不是一开始就认定 MySQL 有问题，而是先按链路排查：

1. 先看接口监控和日志，确认慢的是哪个接口、慢在什么时间段、是偶发还是稳定出现
2. 再看接口内部耗时拆分，发现主要耗时集中在数据库查询，而不是网络、序列化或者第三方接口
3. 然后打开 MySQL 慢查询日志，定位具体 SQL，看它的执行频率、单次耗时和扫描行数
4. 对问题 SQL 使用 `EXPLAIN` / `EXPLAIN ANALYZE` 看执行计划，重点看 `type`、`key`、`rows`、`Extra`，判断有没有全表扫描、索引失效、回表过多、临时表或文件排序
5. 最后结合业务代码看调用方式，确认是不是 N+1 查询、循环查库、分页后再逐条查关联数据等问题

当时比较关键的问题是房源列表里需要展示城市信息，旧逻辑先查一批房源，再循环根据 `city_id` 查询城市，形成 N+1 查询。数据量小的时候不明显，但列表条数增加后，数据库请求次数和网络往返都会放大。

所以我后面不是只改 SQL，而是先确认慢点来自重复查询，再比较了 join、批量 `IN` 查询和城市维表缓存几种方式。最终选择了适合当前数据量和接口形态的改法，把多次查询收敛成一次或少量查询，并通过压测和接口日志确认耗时从几百毫秒降到了几十毫秒。

5. 后处理层：解析 JSON，做字段类型校验、枚举归一化、单位转换、缺失字段处理，并转换成前端可回显、可人工编辑的数据结构

### 5. 你对 MCP 的理解是什么？

高分回答：

MCP 全称是 Model Context Protocol，可以理解为大模型应用和外部工具、数据源之间的一套标准连接协议。

传统做法里，每个大模型应用如果想接数据库、文件系统、搜索服务、业务 API，都要为每个工具单独写适配逻辑。MCP 想解决的问题是：用统一协议描述外部能力，让模型应用能以一致的方式发现工具、读取资源、调用能力。

我理解 MCP 里有几个核心角色：

1. Host：比如 Claude Desktop、IDE、Agent 应用，是用户真正交互的大模型宿主
2. Client：Host 内部负责和 MCP Server 通信的客户端
3. Server：对外暴露具体能力，比如文件读取、数据库查询、Git 操作、业务系统 API
4. Tools / Resources / Prompts：分别对应可调用工具、可读取资源和可复用提示模板

它的价值主要有三点：

1. 标准化工具接入，避免每个 Agent 重复造轮子
2. 降低模型使用外部上下文和工具的工程成本
3. 方便做权限控制、能力声明和调用边界管理

如果结合我的项目来说，我之前没有在项目里完整实现 MCP Server，但我能理解它和 Agent 工具调用的关系：MCP 更偏“工具和上下文接入协议”，ReAct Agent 更偏“模型如何决定何时调用工具、调用后如何继续推理”的工作流。

### 6. ReAct Agent 和普通 RAG 有什么区别？

高分回答：

普通 RAG 的核心流程是“检索增强生成”：用户提问后，系统先从知识库里召回相关文档，把文档片段拼到上下文里，再让大模型生成答案。它主要解决的是大模型知识边界和事实依据的问题。

ReAct Agent 的核心是“Reasoning + Acting”，也就是模型会在多轮循环里进行思考、选择动作、调用工具、观察结果，然后继续推理。它不只是回答问题，还可以根据中间结果决定下一步做什么。

两者的区别可以从四个角度理解：

1. 目标不同：RAG 主要增强知识，ReAct Agent 主要增强行动能力
2. 流程不同：RAG 通常是检索后生成的一次链路，ReAct 是思考、行动、观察的多步循环
3. 能力不同：RAG 适合知识问答，ReAct 适合故障排查、工单处理、多工具协作等任务
4. 状态不同：RAG 通常上下文较简单，Agent 需要维护任务状态、工具结果和失败重试

在扫地机器人客服项目里，可以把两者结合起来：用户问产品参数时走 RAG，从说明书和 FAQ 中召回答案；用户说“机器人不回充”时，Agent 可以先检索故障文档，再调用设备状态查询工具，最后根据电量、位置、错误码给出排查步骤。

### 7. 介绍一下你的秒杀系统。为什么用乐观锁？为什么不用悲观锁？乐观锁会有什么问题？怎么解决？

高分回答：

我的秒杀系统目标是解决高并发下的库存扣减、防超卖、一人一单和下单链路削峰。

整体链路可以这样讲：

1. 秒杀开始前，把商品库存预热到 Redis
2. 用户请求进来后，先在 Redis 里用 Lua 脚本原子判断库存和一人一单
3. Lua 判断通过后预扣 Redis 库存，并把下单消息写入队列
4. 后台消费者异步创建订单
5. 数据库层用唯一索引保证一人一单，用 `stock > 0` 条件扣减作为防超卖最终防线

为什么不用纯悲观锁？

悲观锁的思路是把库存行锁住，一个事务处理完后下一个事务再处理。它语义简单，但秒杀场景的特点是大量请求同时竞争同一行热点库存，如果所有请求都进入数据库排队拿行锁，会导致数据库连接堆积、锁等待增加，吞吐下降，而且很多请求其实最后会失败，没必要都打到 DB。

为什么用条件扣减？它和乐观锁是什么关系？

秒杀库存扣减更适合“先判断，成功就扣，失败就快速返回”。数据库层可以用类似下面的 SQL 做最终兜底：

```sql
UPDATE seckill_voucher
SET stock = stock - 1
WHERE voucher_id = ?
  AND stock > 0;
```

这个就是我在黑马点评项目里实际使用的条件扣减写法，对应 MyBatis-Plus 代码是：

```java
boolean success = seckillVoucherService.update()
        .setSql("stock = stock - 1")
        .eq("voucher_id", voucherId)
        .gt("stock", 0)
        .update();
```

它生成的核心 SQL 就是：

```sql
UPDATE seckill_voucher
SET stock = stock - 1
WHERE voucher_id = ?
  AND stock > 0;
```

判断 `affected_rows` 是否为 1，如果为 1 说明扣减成功，为 0 说明库存不足或并发冲突。

如果用版本号，也可以写成 `version = ?` 的 CAS，但我的项目没有加 version 字段。这里更准确的说法是：我用的是“库存条件扣减”，也可以理解为一种乐观并发控制思路：不提前用悲观锁锁住库存行，而是在更新时通过 `stock > 0` 判断这次扣减能否成功。它利用数据库单条 `UPDATE` 的原子性来保证库存不会扣成负数。在秒杀里不能只让所有请求打到 DB，而是要在 Redis 层先拦掉绝大多数无效请求，再通过消息队列削峰，最后让 DB 做最终一致性兜底。

### 8. 版本号是怎么解决防超卖的？你怎么防超卖？

高分回答：

版本号是一种常见的乐观锁方案，本质是 CAS，也就是 Compare And Set。它更新库存时不只判断商品 ID，还会判断当前版本号是不是我之前读到的版本号。如果版本号已经变了，说明有其他事务先修改了库存，那么这次更新失败。

但我这个黑马点评秒杀项目里，实际没有使用 version 字段，而是使用 `stock > 0` 的条件扣减来防超卖。核心 SQL 是：

```sql
UPDATE seckill_voucher
SET stock = stock - 1
WHERE voucher_id = ?
  AND stock > 0;
```

对应到代码里就是：

```java
boolean success = seckillVoucherService.update()
        .setSql("stock = stock - 1")
        .eq("voucher_id", voucherId)
        .gt("stock", 0)
        .update();
```

这里能防超卖的关键是：数据库会保证单条 `UPDATE` 的原子性。并发请求同时扣库存时，只有满足 `stock > 0` 的更新会成功。如果库存已经被扣到 0，后续请求的 `WHERE stock > 0` 条件不成立，影响行数就是 0，业务代码根据 `success == false` 返回“库存不足”，库存不会被扣成负数。

举个例子，库存只剩 1 时，两个请求同时执行这条 SQL。数据库会串行化同一行上的更新操作，第一个请求成功把库存从 1 扣到 0；第二个请求再执行条件判断时，发现 `stock > 0` 不成立，所以更新失败。这就实现了防超卖。

如果面试官继续问“那版本号怎么做”，可以补充：

```sql
UPDATE seckill_voucher
SET stock = stock - 1,
    version = version + 1
WHERE voucher_id = ?
  AND stock > 0
  AND version = ?;
```

版本号 CAS 和 `stock > 0` 条件扣减都属于不提前加悲观锁、通过更新条件判断并发是否成功的思路。区别是版本号会感知“这一行有没有被其他事务改过”，而 `stock > 0` 更贴合库存扣减场景，只关心库存是否还够扣。我的项目实际采用的是后者。

真正的秒杀防超卖我会做多层防线：

1. Redis Lua：请求入口原子检查库存和用户是否下过单，成功后预扣 Redis 库存
2. 消息队列：把创建订单异步化，削掉高峰流量
3. 数据库条件扣减：`stock > 0` 保证 DB 库存不会扣成负数
4. 唯一索引：对 `(user_id, voucher_id)` 建唯一索引，保证一人一单
5. 幂等处理：消费者重复消费时，根据订单号或唯一索引避免重复创建订单

这样即使 Redis 层、MQ 层或消费者出现异常，数据库仍然是最终防线。

### 9. 当时防超卖的实现思路是什么？是你实现的吗，还是系统原本就有？

高分回答：

可以这样回答得更稳：

这个秒杀项目是我在项目实践中实现和复盘的核心模块，不是简单调用一个现成组件。实现思路是把高并发请求尽量挡在 Redis 层，不让所有请求直接打到数据库。

具体做法是：

1. 活动开始前把秒杀库存加载到 Redis
2. 用户请求进入后，执行 Lua 脚本
3. Lua 脚本里先判断库存是否大于 0，再判断用户是否已经下过单
4. 校验通过后扣减 Redis 库存，并记录用户已购买标记

6. 消费者在数据库事务里扣减库存并创建订单，同时依赖唯一索引防止重复订单

如果面试官问“为什么 Redis 扣了，DB 还要防超卖”，可以补一句：

Redis 是前置削峰和快速失败，数据库是最终一致性的落点。线上系统不能只相信缓存状态，因为可能有消息重复、消费失败、人工修复、缓存与数据库不一致等情况，所以 DB 层仍然要有 `stock > 0` 的条件扣减和唯一索引。

### 10. 我们用了 Redis，为什么还要用 Lua？为什么要 Lua 脚本？

高分回答：

因为秒杀入口不是一个单独操作，而是一组必须一起成功或一起失败的操作：

1. 判断库存是否大于 0
2. 判断用户是否已经下过单
3. 扣减库存
4. 记录用户下单标记
5. 返回是否允许进入后续下单流程

如果这些操作用多条 Redis 命令分开执行，中间就可能被其他请求插入，出现并发问题。比如两个请求都先查到库存是 1，然后都继续扣减，就可能超卖。

Lua 脚本的优势是 Redis 会把脚本作为一个整体执行。Redis 单线程执行命令，在脚本执行期间不会被其他命令打断，所以可以保证这组检查和扣减逻辑的原子性。

另外 Lua 还有一个工程上的好处：减少网络往返。原来多次 Redis 请求才能完成的逻辑，可以合并成一次脚本调用，延迟更低。

不过也要注意，Lua 脚本不能写得太重，不能做耗时操作，否则会阻塞 Redis 主线程。秒杀里一般只放简单的读写和判断逻辑。

### 11. 只能用 Lua 脚本实现这个能力吗？还有哪些方案？

高分回答：

不是只能用 Lua。防超卖有很多方案，关键是结合并发量、库存规模、实现复杂度和一致性要求来选。

常见方案有：

1. 数据库悲观锁：事务里 `SELECT ... FOR UPDATE` 锁住库存行，再判断和扣减。实现简单，一致性强，但热点库存会导致大量锁等待，不适合高并发秒杀入口。
2. 数据库乐观锁 / 条件扣减：通过 `version` 或 `stock > 0` 做原子更新，判断影响行数。适合做最终兜底，但如果所有请求都打到 DB，压力仍然很大。
3. Redis 分布式锁：对商品或用户维度加锁，拿到锁再执行扣减逻辑。语义直观，但锁粒度如果太粗会影响吞吐，锁续期和释放也要小心。
4. Redis Lua：把库存判断、一人一单、预扣库存合到一个原子脚本里，适合秒杀入口快速拦截。
5. 消息队列串行化：请求先进入队列，同一商品库存由消费者顺序处理，天然减少并发写冲突，但用户感知会变成异步结果。

如果是我设计秒杀系统，我会优先选“Redis Lua 前置校验 + MQ 异步下单 + DB 条件扣减兜底 + 唯一索引防重复”的组合。原因是它能把高并发读写挡在 Redis 和 MQ 层，数据库只处理已经筛选过的有效请求。

### 12. 那这里到底是乐观锁还是悲观锁？为什么选这套方案？

高分回答：

这里要分层回答，不能把所有锁混在一起。

Redis Lua 本身不是传统意义上的数据库乐观锁或悲观锁，它是利用 Redis 单线程执行脚本的特性，把多步逻辑变成一个原子操作。

如果数据库落库时使用：

```sql
UPDATE voucher
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

这更接近乐观并发控制或条件更新：不提前锁住所有请求，而是让数据库在更新时判断条件，成功就影响 1 行，失败就影响 0 行。

如果使用 `SELECT ... FOR UPDATE` 先锁库存行，再扣减，那就是悲观锁。

秒杀场景我不优先选纯悲观锁，是因为热点商品会让大量事务在数据库行锁上排队，连接资源和锁等待成本比较高。我的选择是：

1. 入口用 Redis Lua 快速判断和预扣，减少 DB 压力
2. 中间用 MQ 削峰，让创建订单异步化
3. 数据库用条件扣减或版本号做最终防线
4. 用户维度用唯一索引保证一人一单

所以这不是单纯“乐观锁或悲观锁”的二选一，而是不同层次用不同机制解决不同问题。

### 13. Redis 分布式锁是用什么实现的？

高分回答：

我项目里如果需要分布式锁，会优先使用 Redisson，而不是自己手写简单的 `setnx`。

原因是 Redisson 已经封装了分布式锁常见问题，比如加锁原子性、锁过期时间、可重入、自动续期、释放锁时校验持有者，以及等待锁时的发布订阅通知。

如果只是非常简单的场景，也可以用 Redis 的 `SET key value NX EX seconds` 实现基础锁，但生产里要特别注意锁过期、误删别人锁、业务执行时间超过 TTL 等问题。

### 14. Redisson 原理是什么？它怎么表示这个订单或资源被锁住了？

高分回答：

Redisson 分布式锁的核心思想是：在 Redis 里创建一个代表锁的 key，谁成功创建或持有这个 key，谁就拿到了锁。

但 Redisson 不是简单的 `setnx`，它做了更多封装：

1. 加锁时通过 Lua 脚本保证“判断锁是否存在 + 设置锁 + 设置过期时间”这几步的原子性
2. 锁的数据结构通常是 Redis hash，field 里会记录客户端线程标识，value 是重入次数，所以它支持可重入
3. 如果当前线程已经持有锁，再次加锁时不会失败，而是把重入次数加 1
4. 解锁时也用 Lua 脚本校验当前线程是不是锁持有者，只有持有者才能释放，避免误删别人的锁
5. 如果业务执行时间比较长，Redisson 的 watchdog 会在锁默认过期前自动续期，避免业务没执行完锁就过期
6. 如果释放锁后有其他线程在等待，Redisson 会通过发布订阅机制通知等待方重新竞争锁

所以如果面试官问“怎么表示订单被锁住”，可以说：

在 Redis 中会有一个锁 key，比如 `lock:order:123` 或 `lock:user:1001:voucher:2001`。这个 key 存在并且持有者标识匹配时，就表示这个资源当前被某个线程持有锁。其他线程尝试加锁会失败或等待。

需要补一句：Redisson 能解决很多单 Redis 节点分布式锁的工程问题，但如果讨论极端分布式一致性，还要考虑 Redis 主从切换、锁丢失、RedLock 争议和业务幂等兜底。

### 15. MySQL 中的 ACID 是什么？

高分回答：

ACID 是事务的四个特性：

1. Atomicity，原子性：事务里的操作要么全部成功，要么全部失败回滚
2. Consistency，一致性：事务执行前后，数据都要满足业务约束和数据库约束
3. Isolation，隔离性：并发事务之间不能互相产生不符合隔离级别的影响
4. Durability，持久性：事务提交后，即使数据库崩溃，已经提交的数据也不能丢失

面试里要注意，不要把一致性和持久性说混。

---

### 16. ACID 底层是怎么实现的？

高分回答：

可以把 ACID 和 InnoDB 的几个机制对应起来讲：

1. 原子性主要依赖 undo log。事务修改数据前，会记录修改前的版本。如果事务失败或回滚，InnoDB 可以根据 undo log 把数据恢复到修改前。
2. 持久性主要依赖 redo log。事务提交时，InnoDB 会先把变更写入 redo log，崩溃恢复时通过 redo log 重放已提交事务，保证提交后的修改不丢。
3. 隔离性主要依赖锁和 MVCC。当前读通过行锁、间隙锁等控制并发修改；快照读通过 Read View 和 undo log 版本链读取历史版本。
4. 一致性是最终目标，不是单独某一个日志实现的。它依赖原子性、隔离性、持久性共同保证，同时也依赖主键、唯一索引、外键、非空约束和业务层校验。

如果再深入一点，InnoDB 还有 WAL，也就是 Write-Ahead Logging。修改数据页可以先写 redo log，再择机刷脏页到磁盘，这样既保证崩溃恢复，又提升性能。

如果涉及 MySQL binlog 和 InnoDB redo log，还可以补充两阶段提交：MySQL 通过 redo log prepare 和 binlog 写入，再 redo log commit，保证数据库崩溃恢复后，binlog 和 InnoDB 数据尽量保持一致。

### 17. undo log / redo log 是怎么实现事务语义的？

高分回答：

undo log 主要服务于回滚和 MVCC。每次事务修改一行记录时，InnoDB 会把修改前的数据版本记录到 undo log 里，并通过记录里的回滚指针形成版本链。如果事务回滚，就沿着 undo log 把数据恢复；如果其他事务做快照读，也可以根据 Read View 沿着版本链找到自己可见的历史版本。

redo log 主要服务于持久性和崩溃恢复。InnoDB 修改数据时，通常先改 Buffer Pool 里的数据页，这些页还没立刻刷盘，叫脏页。为了防止宕机后丢失修改，InnoDB 会先把物理页修改记录写到 redo log。崩溃恢复时，只要事务已经提交，就可以根据 redo log 把数据页恢复到正确状态。

简短总结就是：

1. undo log 记录“修改前是什么”，用于回滚和历史版本读取
2. redo log 记录“数据页做了什么修改”，用于宕机后的重放恢复
3. undo 保证原子性，redo 保证持久性，二者配合锁和 MVCC 一起支撑事务

### 18. MySQL 底层索引为什么用 B+ 树，而不是传统 B 树？InnoDB 的 B+ 树和标准 B+ 树有什么差异？

高分回答：

MySQL InnoDB 选择 B+ 树，主要是因为数据库索引要面向磁盘和范围查询优化。

相比 B 树，B+ 树有几个优势：

1. B+ 树非叶子节点只存 key 和指针，不存完整数据，所以同样大小的数据页能放更多 key，树的扇出更大，高度更低
2. 树高更低意味着一次查询需要的磁盘 IO 更少，查询性能更稳定
3. 所有数据都在叶子节点，查询路径更统一
4. 叶子节点按 key 有序连接，非常适合范围查询、排序扫描和分页扫描

传统 B 树的非叶子节点也会存数据，这会导致单个页能容纳的 key 更少，树更高；同时范围查询时可能需要在树中反复中序遍历，不如 B+ 树叶子链表扫描自然。

InnoDB 的 B+ 树和教材里的标准 B+ 树也有一些实现差异：

1. InnoDB 的节点对应数据页，默认页大小通常是 16KB
2. InnoDB 聚簇索引的叶子节点存整行数据，表数据本身就是按主键 B+ 树组织的
3. InnoDB 二级索引的叶子节点不直接存整行，而是存二级索引 key 和主键值，必要时再回表查聚簇索引
4. InnoDB 叶子页之间通过双向链表连接，便于范围扫描和前后遍历
5. InnoDB 页内部还有页目录、槽、记录头等结构，不是抽象教材里的纯 key-pointer 数组

所以面试时可以总结为：B+ 树更适合磁盘数据库的点查和范围查；InnoDB 在标准 B+ 树基础上结合页结构、聚簇索引、二级索引和双向链表做了工程化实现。

### 19. 你知道 MVCC 吗？它的实现原理是什么？

高分回答：

MVCC 是 Multi-Version Concurrency Control，多版本并发控制。它的核心思想是：读操作尽量不阻塞写操作，写操作也尽量不阻塞普通快照读。不同事务可以根据自己的可见性规则读取同一行记录的不同版本。

InnoDB 的 MVCC 主要依赖三部分：

1. 隐藏字段：每行记录里有事务 ID，比如 `trx_id`，表示最后修改这行的事务；还有回滚指针 `roll_pointer`，指向 undo log 中的上一个版本
2. undo log 版本链：一行记录被多次修改后，旧版本会保存在 undo log 中，通过回滚指针串成版本链
3. Read View：事务做快照读时生成的视图，用来判断某个版本对当前事务是否可见

查询时，InnoDB 会先看当前行最新版本的 `trx_id`。如果这个版本对当前事务可见，就直接返回；如果不可见，就沿着 undo log 版本链往前找，直到找到一个可见版本或找不到为止。

在隔离级别上：

1. Read Committed 通常每次快照读都会生成新的 Read View，所以能读到其他事务已经提交的新数据
2. Repeatable Read 通常在第一次快照读时生成 Read View，后续复用，所以同一事务内多次读取结果一致

---

### 20. Read View 是什么？

高分回答：

Read View 可以理解为事务做快照读时生成的一张“可见性快照”。它不是真的把数据复制一份，而是记录当时系统里事务的活跃情况，用来判断某个数据版本当前事务能不能看见。

Read View 里比较关键的信息有：

1. `m_ids`：生成 Read View 时仍然活跃的事务 ID 列表
2. `min_trx_id`：活跃事务 ID 中最小的 ID
3. `max_trx_id`：下一个即将分配的事务 ID，也可以理解为当前已出现事务 ID 的上界
4. `creator_trx_id`：创建这个 Read View 的事务 ID

判断一行版本是否可见时，会看这个版本的 `trx_id`：

1. 如果版本的 `trx_id` 等于当前事务 ID，说明是自己改的，可以看见
2. 如果 `trx_id` 小于 `min_trx_id`，说明在 Read View 创建前已经提交，可以看见
3. 如果 `trx_id` 大于等于 `max_trx_id`，说明是 Read View 创建后才出现的事务，不可见
4. 如果 `trx_id` 在 `m_ids` 里，说明当时还没提交，不可见
5. 如果 `trx_id` 不在 `m_ids` 里，说明 Read View 创建时已经提交，可以看见

这套规则配合 undo log 版本链，就实现了快照读。

### 21. 你查询时间从 500ms 优化到 50ms，是优化了什么？怎么分析得出可以通过这个优化解决问题？

高分回答：

这个问题不能只回答“我把两次查询改成 join”，要把定位过程讲完整。

我当时会先从接口耗时和慢查询日志定位到具体接口，再看 SQL 调用次数。发现这个接口的慢不只是单条 SQL 慢，而是存在 N+1 查询：先查一页房源列表，然后对每条房源再根据 `city_id` 查询城市信息。

如果一页 50 条房源，就会变成 1 次房源查询 + 50 次城市查询。单次城市查询可能只要几毫秒，但网络往返、连接占用和重复查询叠加后，总耗时会明显增加。

接下来我会做三个验证：

1. 打日志或链路追踪，确认一次接口请求里 SQL 执行次数确实很多
2. 用 `EXPLAIN` 看房源表和城市表相关字段是否有索引，比如 `house.city_id`、`city.id`
3. 对比 join、批量 `IN` 查询、城市缓存三种方案在当前数据量下的耗时和扫描行数

最终如果选择 join，我会这样解释：

这个场景里房源和城市是多对一关系，城市表是维表，数据量相对较小，关联字段有索引，列表分页后参与关联的房源数量有限。因此把 N 次城市查询收敛成一次 join，可以减少网络往返和重复查询，整体收益明显。

但我也会补充：join 不是绝对最优解。如果城市表很大、关联条件没有索引、结果集很宽，或者分页方式不合理，join 可能会变重。更通用的方案是先查房源列表，再把本页 `city_id` 去重后批量查城市表，或者对城市维表做缓存。

### 22. 联表一定是最优解吗？分两次查询未必比联表慢，联表其实是比较重的操作。你怎么推断应该通过联表解决？

高分回答：

联表不一定是最优解。这个问题我会先承认这一点，然后说明我是如何做选择的。

判断 join 是否合适，我会看几个条件：

1. 关联关系：是一对一、多对一，还是一对多。如果是一对多，很容易放大结果集，要谨慎。
2. 数据量：主表分页后参与 join 的行数有多少，维表数据量有多大。
3. 索引：关联字段上有没有索引，执行计划里是否走了合适的 key。
4. 返回字段：是不是只取必要字段，还是把大字段也一起 join 出来了。
5. 执行计划：`rows`、`type`、`Extra` 是否合理，有没有临时表、文件排序、全表扫描。
6. 实际对比：优化前后 SQL 次数、接口耗时、数据库 CPU、扫描行数是否下降。

在我这个场景里，原问题的本质是 N+1 查询，而不是“必须用 join”。所以更准确的表述应该是：我把循环逐条查询改成集合化查询。集合化查询可以是 join，也可以是批量 `IN` 查询。

如果面试官追问哪个更优，我会这样答：

如果城市表是低频变化的维表，我更倾向于“本页房源查出来后，收集 `city_id` 去重，再批量查询城市表，甚至加本地缓存或 Redis 缓存”。这样可以避免复杂 join，也能解决 N+1。join 适合数据量可控、索引完备、查询字段少、分页后结果集较小的场景。

这个回答比单纯说“join 变快了”更稳，因为它体现的是优化思路，而不是硬背结论。

### 23. CRM 中台 AI 抽取是怎么实现的？抽取了哪些内容？AI 是怎么实现抽取的？你怎么定义规则？

高分回答：

这个 AI 抽取的目标是把运营输入的非结构化房源文本或 URL，转成 CRM 系统可以使用的结构化字段。

抽取内容主要包括：

1. 基础信息：房源标题、国家、城市、区域、详细地址
2. 价格信息：租金、币种、押金、账单是否包含、水电网费说明
3. 户型信息：房型、卧室数量、卫生间数量、面积、楼层
4. 租期信息：可入住时间、最短租期、租约结束时间
5. 配套设施：家具、厨房、洗衣机、空调、网络、停车位等
6. 图片和来源：图片链接、原始 URL、来源平台
7. 联系信息：联系人、联系方式、备注说明

实现上，我会分成“预处理、模型抽取、后处理”三段。

预处理阶段：

1. 校验输入，文本和 URL 至少有一个
2. URL 做归一化、去空、去重，必要时抓取网页正文
3. 对文本做长度限制和无效内容过滤

模型抽取阶段：

1. 从配置中心读取 prompt 模板和 expected schema
2. prompt 里明确每个字段的含义、类型、单位、枚举范围和缺失时返回规则
3. 要求模型只返回 JSON，不返回额外解释
4. 调用 AI Workbench 获取结构化结果

后处理阶段：

1. 解析 JSON，失败时做兜底和错误提示
2. 校验字段类型，比如价格必须是数字，币种必须在枚举范围内
3. 对单位做归一化，比如周租、月租、平方米、平方英尺
4. 对枚举字段做标准化，比如房型、设施、城市名
5. 标记低置信度或缺失字段，回显给运营人工确认

规则定义不是写死在代码里，而是尽量配置化。比如 schema 定义字段名、类型、是否必填、枚举值、字段说明；prompt 根据 schema 自动拼接。这样后续不同国家、不同房源类型扩展时，不需要频繁改核心代码。

最后要强调：AI 抽取结果不会直接入库，而是进入人工校对流程。这样能兼顾效率和业务准确性。

### 24. 这个 AI 做的其实是不是抽取？还是格式化？

高分回答：

更准确地说，它包含两个步骤：信息抽取和结构化格式化。

第一步是抽取。模型需要从非结构化文本或网页内容里识别出有业务含义的信息，比如租金、城市、地址、户型、租期、设施等。这一步解决的是“原文里哪些内容是我们要的字段”。

第二步是格式化和归一化。比如原文里写的是 “£350 per week”，系统里可能要拆成 `price = 350`、`currency = GBP`、`rent_period = week`。再比如设施字段要归一到系统枚举，城市名要和系统城市表匹配。

所以如果面试官问这个问题，我会主动澄清：

它不是简单把文本排版成 JSON，而是先做字段抽取，再按 schema 做结构化、类型校验和业务归一化。最终输出的是系统可回显、可校对、可保存的数据结构。

### 25. 算法题：如果有思路，可以先说一下整体思路。波兰表达式 / 前缀表达式怎么求值？

高分回答：

这道题的关键是先读清楚题意：波兰表达式也叫前缀表达式，运算符在操作数前面。例如：

```text
* + 2 3 4
```

表示：

```text
(2 + 3) * 4 = 20
```

前缀表达式可以从右往左扫描，用一个数字栈求值：

1. 从右到左遍历 token
2. 如果遇到数字，就入栈
3. 如果遇到运算符，就从栈里弹出两个数
4. 第一个弹出的数是左操作数，第二个弹出的数是右操作数
5. 计算结果再压回栈
6. 遍历结束后，栈顶就是最终结果

时间复杂度是 O(n)，每个 token 只处理一次；空间复杂度是 O(n)，最坏情况下数字都入栈。

Java 实现：

```java
import java.util.ArrayDeque;
import java.util.Deque;

class Solution {
    public int evalPrefix(String[] tokens) {
        Deque<Integer> stack = new ArrayDeque<>();

        for (int i = tokens.length - 1; i >= 0; i--) {
            String token = tokens[i];

            if (isOperator(token)) {
                int left = stack.pop();
                int right = stack.pop();
                int value = calculate(left, right, token);
                stack.push(value);
            } else {
                stack.push(Integer.parseInt(token));
            }
        }

        return stack.pop();
    }

    private boolean isOperator(String token) {
        return token.length() == 1 && "+-*/".contains(token);
    }

    private int calculate(int left, int right, String op) {
        switch (op) {
            case "+":
                return left + right;
            case "-":
                return left - right;
            case "*":
                return left * right;
            case "/":
                return left / right;
            default:
                throw new IllegalArgumentException("Unsupported operator: " + op);
        }
    }
}
```

面试时可以边写边用例子验证：

```text
tokens = ["*", "+", "2", "3", "4"]

从右往左：
4 入栈
3 入栈
2 入栈
遇到 +，弹出 2 和 3，得到 5，入栈
遇到 *，弹出 5 和 4，得到 20
```

需要注意：

1. 前缀表达式从右往左扫，后缀表达式从左往右扫
2. 减法和除法有左右顺序，不能写反
3. 如果 token 可能是负数，判断运算符时要用 `token.length() == 1`，避免把 `-3` 当成运算符
4. 如果题目要求浮点数或除零处理，要按题意补充

## 三、这场面试最应该背熟的三套表达

### 1. 秒杀系统标准表达

秒杀系统不能只说“用了 Redis 和 Lua”，要讲成完整链路：

1. 活动开始前把库存预热到 Redis
2. 请求进来先执行 Lua，原子判断库存和一人一单
3. 通过后 Redis 预扣库存，并发送下单消息
4. MQ 削峰，消费者异步创建订单
5. DB 用 `stock > 0` 条件扣减防超卖
6. DB 用 `(user_id, voucher_id)` 唯一索引防重复下单
7. 消费失败要有重试、幂等和库存补偿

一句话总结：

秒杀的核心不是某一种锁，而是用 Redis 快速拦截、MQ 削峰、数据库做最终一致性兜底。

### 2. MySQL 优化标准表达

MySQL 优化不要直接说“我加索引 / 改 join”，要按定位链路说：

1. 先从接口监控确认慢接口
2. 再从日志确认慢点在数据库
3. 用慢查询日志定位具体 SQL
4. 用 `EXPLAIN` 看执行计划
5. 结合代码确认是否有 N+1、索引失效、回表过多、排序临时表
6. 提出多个方案并对比：索引、改 SQL、批量查询、缓存、分页优化
7. 用优化前后的耗时、SQL 次数、扫描行数证明效果

一句话总结：

性能优化要讲“定位依据”和“验证结果”，不能只讲最后改了什么。

### 3. 项目介绍标准表达

任何项目都可以按这个模板讲：

1. 背景：业务为什么需要这个功能
2. 问题：原来痛点是什么
3. 目标：这个模块要达成什么效果
4. 方案：系统分几层，每层做什么
5. 取舍：为什么这样选，有没有其他方案
6. 结果：性能、效率、准确性或业务效果
7. 复盘：如果重做，还会怎么优化

一句话总结：

面试官不是只想听“我做了什么”，更想听“我为什么这么做，以及我怎么证明它有效”。
