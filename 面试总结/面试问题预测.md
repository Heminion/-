## 一、项目深挖与系统设计（黑马+agent）

### **🌟用户登录态怎么实现？**

标准流程：手机号+验证码校验通过后签发 token，客户端携带 token 访问接口，服务端鉴权。

  **手机号验证码登录 + 服务端生成随机 token + Redis 保存用户登录信息 + 拦截器续期 + ThreadLocal 传递当前用户**

1. 校验手机号格式。
2. 去 Redis 取验证码并比对。
3. 根据手机号查库。
4. 如果用户不存在，就自动注册。
5. 生成一个随机 token，不是 JWT，而是 UUID。
6. 把用户精简信息 UserDTO 转成 Hash 存进 Redis。
7. Redis key 是 login:token:token值。
8. 最后把 token 返回给前端。

### **🌟登录校验怎么设计？ThreadLocal 为什么要用？**

**项目设计**：token（UUID）存 Redis，key 为 `login:token:{token}`，value 为 UserDTO（Hash）；登录成功返回 token，前端存 localStorage 或 Cookie，请求时放 Header `authorization`。

**拦截器**：RefreshTokenInterceptor 取 token、查 Redis，命中则 `UserHolder.saveUser()` 写入 ThreadLocal 并刷新 TTL；LoginInterceptor 检查 `UserHolder.getUser()` 是否为空，空则 401。

**ThreadLocal 作用**：同一请求内 Controller/Service 任意层都能 `UserHolder.getUser()` 取当前用户，无需层层传参；请求结束 `afterCompletion` 里 `removeUser()` 防止线程复用串数据。

### **🌟双拦截器流程是什么？**

**RefreshTokenInterceptor（order=0）**：对所有路径生效；取 Header 的 token，查 Redis；无 token 或查不到用户则直接放行（不拦截）；有用户则写入 ThreadLocal、刷新 Redis TTL、放行。

**LoginInterceptor（order=1）**：排除登录、验证码、店铺列表等公开路径；检查 ThreadLocal 是否有用户；无则 401 拦截，有则放行。

**顺序**：先 Refresh 恢复/续期登录态，再 Login 做强校验；二者配合实现“公开接口可访问、需登录接口无 token 即拦截”。

🌟**秒杀流程怎么设计？**

1) 秒杀前把库存放入 Redis；  
2) Lua 脚本原子校验库存和一人一单，并预扣库存；  
3) Lua 里 `XADD` 写入 `stream.orders`；  
4) 后台消费者 `XREADGROUP` 异步创建订单，成功后 `XACK`。  
   配合 Redisson 用户粒度锁和数据库条件扣减，保证高并发下防超卖与防重复下单。

### **🌟你随便选一个项目，给我大概详细讲一下都是做什么的。**

以「雅鉴生活志」为例。

**业务上**为用户提供商户点评、秒杀优惠券等。

**技术上**主要解决两个问题：一是防超卖，二是一人一单。  

 **具体实现**：

① Lua 脚本在 Redis 侧原子完成库存判断、用户去重（SISMEMBER）、扣减（INCRBY）、入队（XADD）；

② 主线程快速返回「抢购资格已获得」，订单创建由后台单线程消费者 XREADGROUP 消费后落库；

③ 消费端对同一用户加 Redisson 锁，再查 DB 是否重复，并用 `stock = stock - 1 where stock > 0` 乐观锁扣库存。

这样既防超卖，又保证一人一单，同时主链路响应快、DB 压力可控。

### 🌟**Lua 具体是怎么解决你的问题的呢？**

Lua 在 Redis 中作为**脚本整体执行**，具备**原子性**。

项目里的 `seckill.lua` 依次执行：

① `get seckill:stock:{voucherId}` 判断库存；

② `sismember seckill:order:{voucherId} userId` 判断是否重复下单；

③ `incrby stock -1` 扣减；

④ `sadd orderKey userId` 记录用户；

⑤ `xadd stream.orders` 入队。

这一套逻辑在一次脚本执行中完成，没有「先查后写」之间的并发插入，避免了超卖和重复下单。

### **🌟Lua 在 Redis 里的主要作用是什么？同一用户同时点两次，Lua 是并发执行两次还是串行排队？为什么能串行？**

 Lua 的主要作用是**原子性**：一系列 Redis 命令在一个脚本里执行，要么全成功要么全失败，且执行期间不会被其他命令打断。  
同一用户发两次请求，会触发两次 Lua 执行，但 Redis 是**单线程**执行命令的，所以这两次 Lua 会**串行排队**执行：先执行完第一次，再执行第二次。

### **🌟如果中间失败了怎么处理呢？**

Lua 脚本内部任一步失败会**整体回滚**（Redis 会撤销已执行命令）。

若 **Lua 执行成功**但入队后、消费前**进程挂掉**：消息在 Redis Stream 的 **pending-list** 中，消费者重启后会从 pending 重新消费；

消费端用 `user_id + voucher_id` 判重和 DB 唯一约束做幂等，重复消费不会重复建单。

若消费失败抛异常，不 XACK，消息会重新投递，由幂等逻辑兜底。

### 🌟订单号怎么生成？在发送端还是消费端生成？

本项目在**发送前**就用 `RedisIdWorker` 生成订单号，并作为字段写入 Stream。  
ID 结构是时间戳差值左移 + 当日自增序列（Redis `INCR`），兼顾趋势递增、全局唯一、低冲突。  

### **🌟重试不会出现问题吗？你的每一步重复执行会不会出问题？**

这里需要区分两个概念：

**可重入**是同一线程多次获取同一把锁；

**幂等**是同一操作多次执行效果与一次一致。

面试官问的更多是「重试是否导致重复下单」，属于幂等范畴。  
**项目中的幂等设计**：

① 订单号在入队前由 RedisIdWorker 生成并写入消息，重试时使用同一订单号；

② 消费端先查 `user_id + voucher_id` 是否已存在；

③ 建议 DB 增加 `unique(user_id, voucher_id)`，重复插入视为幂等并 ACK。可重入锁解决的是「同一用户并发多请求的串行化」，与幂等是不同维度。

### **🌟你项目里用到锁了吗？**

用了分布式锁。  
“雅鉴生活志”秒杀下单在消费端按 `userId` 加 Redisson 锁（`lock:order:{userId}`），配合 DB 中“同用户同券”查询校验，防止并发重复下单。  
另外，库存扣减使用 `stock = stock - 1 and stock > 0` 条件更新，避免超卖。

### **🌟你是怎么实现这种可重入的机制的？**

项目里用的是 **Redisson 分布式锁**，它底层支持**可重入**：同一线程多次调用 `lock()`，内部用 `state` 计数，`unlock()` 时 `state--`，为 0 才真正释放。

## 二.实习深挖

### 🌟**你做这个项目最大的技术挑战是什么？怎么解决？最终效果如何？**

**技术挑战：多源异构房源数据的统一建模和稳定同步。**

不同供应商在价格、面积、租期、房型、状态这些字段上的格式差异很大，如果每接一家都写一套硬编码逻辑，后续维护和扩展会越来越重。 

  

**解决思路**：

**第一，先统一领域模型**，

把数据抽象成 Property、Unit、Room、Tenancy 这几层；

**第二，用 `expr` 这套表达式能力把字段映射规则配置化**，

比如价格解析、面积换算、租期编码、设施组装都通过表达式和自定义函数处理，而不是散落在各个供应商逻辑里；

**第三，通过 MQ / MNS 把抓取、转换、落库解耦，**让老 PHP 链路和新 Go 链路都能复用同一套同步思路。   



**最终效果，**

新供应商接入从“改一堆业务代码”变成“优先补配置和映射规则”；数据进入 CRM 之前已经被标准化，下游查房库、销售后台和运营流程消费起来更稳定；链路边界也更清晰，排障和扩展成本都更低。

## 三.场景题

### **🌟场景题：金币换现金，一天只能换一次，三步（检查资格 → 扣 1 万金币 → 发 1 块钱），伪代码实现。**

高分回答：  

```java
// 1. 互斥锁 key：按用户+日期，保证同一用户同一天串行
String lockKey = "withdraw:" + today + ":" + userId;
RLock lock = redisson.getLock(lockKey);
//最多等 3 秒尝试获取这把锁；如果拿到了，默认持有 10 秒，10 秒后自动释放。
if (!lock.tryLock(3, 10, TimeUnit.SECONDS)) return "系统繁忙";

try {
    // 2. 检查今日是否已提现（幂等 + 资格）
    if (withdrawLogDao.exists(userId, today)) return "今日已提现";
    // 3. 扣金币（乐观锁或 where balance >= 10000）
    int rows = userDao.deductCoins(userId, 10000);
    if (rows == 0) return "余额不足";
    // 4. 发钱 + 写提现记录（同一事务）
    payService.send(userId, 1);
    withdrawLogDao.insert(userId, today);
} finally {
    lock.unlock();
}
```

#### **🌟流程本身会有什么问题？机器挂了，用户金币扣了但钱没发，怎么恢复？**

 若扣金币和发钱在**同一 DB 事务**内，任一步失败会整体回滚，不存在「扣了不发」；若中间进程挂掉，事务未提交也会回滚。  
若扣金币和发钱**分属不同服务/库**，无法用本地事务，需要**分布式事务或最终一致性**：如本地消息表、RocketMQ 事务消息、TCC 等。恢复时通过定时任务扫描「已扣未发」记录做补偿或人工处理。

---

#### **🌟用户同时点了两次会是什么情况？怎么保证幂等？**

两次请求若都能进入，可能执行两次扣金币和两次发钱。

保证幂等的手段：

① **互斥锁**：`lock:withdraw:date:userId`，同用户同天串行，第二次进来时第一次已写提现记录，检查失败直接返回；

② **唯一约束**：提现记录表 `unique(user_id, date)`，第二次插入失败，捕获异常视为「已处理」；

③ **幂等键**：请求带唯一 requestId，先查是否已处理，有则直接返回成功。  
注意：**可重入锁**是同一线程可多次获取，不适合「两次点击 = 两个请求/两个线程」的互斥；这里需要的是**互斥锁**（同一 key 只允许一个线程），不是可重入。

---

#### **🌟可重入锁的 key 是 date+userId 吗？如果一天能换两次呢？**

 锁的 key 用 `date+userId` 可以，保证同用户同天串行。

若一天能换两次，锁仍可不变，

**逻辑改为**：在锁内查 `withdraw_log` 今日次数，若 < 2 则执行扣款+发钱+插入记录，否则返回「今日次数已用完」。  
可重入锁的 key 与「一天几次」无关；可重入解决的是「锁内调用另一需同一锁的方法」时的重入，不是次数限制。

次数限制靠业务表（如 withdraw_log）的 count 或唯一约束（如 `unique(user_id, date, seq)`）实现。

---

#### **🌟扣金币和发钱不在同一数据库/不同系统，怎么处理？**

 无法用本地事务，需要**分布式事务**或**最终一致性**：  
① **本地消息表**：扣金币时写本地事务 + 消息表，定时任务发 MQ，消费端发钱，失败重试；发钱成功则回调或更新消息状态。  
② **RocketMQ 事务消息**：发 Half 消息 → 执行本地扣金币 → 提交/回滚消息 → 消费端发钱，失败则回查 + 重试。  
③ **TCC**：Try 阶段预扣、预占；Confirm 真正扣和发；Cancel 回滚。  
④ **Saga**：拆成多个本地事务 + 补偿，任一步失败执行逆向补偿。  
核心思路：扣金币和发钱通过可靠消息或补偿机制达到最终一致，保证不会出现「扣了不发」或「发了不扣」。

### **🌟如果让你设计一个千万级的秒杀优惠券系统，你会怎么设计？存储层还能怎么优化？**

如果按千万级秒杀来设计，我会把链路拆成四层：

1. **接入层限流**：Nginx 或网关做限流、黑名单、验证码，先挡掉明显无效流量
2. **Redis 资格校验层**：库存预热到 Redis，用 Lua 原子完成库存判断、一人一单判断和预扣减
3. **消息队列层**：资格通过后只入队，不在主线程写库
4. **异步落库层**：消费者按能力写 MySQL，做幂等校验、条件扣库存和失败补偿

存储层优化不能只说“加唯一索引”，那更多是保证正确性，不是核心性能优化。真正的优化点一般有：

1. **冷热分离**：热点库存判断放 Redis，DB 只做最终落库
2. **批量化 / 异步化**：数据库写入由消费者异步处理，必要时可批量 insert
3. **分库分表**：订单量非常大时，对订单表按用户或时间维度分片
4. **顺序写优化**：订单 ID 采用趋势递增，减少索引页分裂
5. **索引精简**：秒杀订单表保留必要索引，避免写放大

如果面试官继续问“怎么防重”，我会补一句：应用层幂等校验 + 数据库唯一约束要同时有，唯一约束是最后一道防线。

## 四、Java 基础与集合类

### **🌟ArrayList 和 LinkedList 的区别？**
**底层结构**：

ArrayList 基于动态数组，容量不足时触发扩容；

LinkedList 基于**双向链表**，每个节点含 prev/next 指针。

**复杂度**：

ArrayList **随机访问 O(1)**，中间插入删除需**移动元素 O(n)**；

LinkedList **查找需遍历 O(n)**，在已定位节点处插入/删除仅改指针 O(1)；

### **🌟HashMap 底层结构和 put 流程？1.7 与 1.8 差异？**
 **结构**：数组 + 链表 + 红黑树。

**put 流程**：

(1) 对 key 做 `hashCode()` 再与高16位异或扰动，降低低位碰撞；

(2) `(n-1) & hash` 定位桶下标；

(3) 桶空则直接插入；

(4) 桶非空则遍历链/树：key 相同则覆盖 value 并返回旧值，不同则追加；链上插入前会先比较 key，避免重复 key 入链。

(5) 若链表长度>=8 且数组>=64，链表转红黑树，查找复杂度从 `O(n)` 降到 `O(log n)`；

树节点数<=6 时退化为链表。

**扩容**

1. 默认容量通常是 16，负载因子默认 0.75
2. 当 `size > capacity * loadFactor` 时扩容
3. 新容量通常变成原来的 2 倍
4. 然后对元素重新分配位置

扩容时元素不一定都重新完整计算一次位置，而是看 hash 的某个新增高位 bit 是 0 还是 1，来决定元素留在原索引还是移动到 `原索引 + oldCap`，这样迁移效率更高。

**五、JDK 1.7 和 1.8 的主要差异**

**1. 数据结构不同**
1.7：

- 数组 + 链表

1.8：

- 数组 + 链表 + 红黑树

意义：

- 1.7 链表过长时查找退化成 O(n)
- 1.8 树化后可优化到 O(log n)

**2. 链表插入方式不同**
1.7：

- 采用 头插法

1.8：

- 采用 尾插法

影响：

- 1.7 在扩容时，链表反转，且并发下更容易出现链表成环问题
- 1.8 尾插法更稳定

**3. 扩容时的数据迁移方式不同**
1.7：

- 每个节点重新计算位置并迁移
- 实现上更容易出现并发问题

1.8：

- 节点要么留在原索引，要么移动到 原索引 + oldCap
- 因为容量翻倍后，只看新增的那一位是 0 还是 1
- 迁移效率更高

这个是 1.8 很经典的优化。

**4. 哈希冲突严重时的处理不同**
1.7：

- 只能靠链表

1.8：

- 链表长度过长时转红黑树

**5. 并发下的问题表现不同**
两者都：

- HashMap 都是线程不安全的

但 1.7 更典型的问题是：

- 多线程扩容时可能形成环形链表
- 进而导致死循环、CPU 飙高

1.8 虽然避免了这个典型问题，但：

- 仍然不是线程安全
- 并发场景应该用 ConcurrentHashMap

### **🌟equals 和 hashCode 的关系？**
 **语义**：`equals` 判断两个对象逻辑相等；`hashCode` 返回对象哈希值，用于哈希表定位桶。

**契约**：若 `a.equals(b)==true`，则 `a.hashCode()==b.hashCode()` 必须成立；反之不成立（哈希碰撞时）。

**在 HashMap 中的使用**：先用 `hash(key)` 定位桶，桶内再遍历用 `equals` 比较 key；

若 key 相等则覆盖，否则追加。

重写 `equals` 必须同时重写 `hashCode`，否则放入 HashSet/HashMap 会出问题（两个“相等”对象可能进不同桶）。

### **🌟Object 常用方法有哪些？**
  **常见方法**：`equals()` 判断相等

`hashCode()` 哈希值、

`toString()` 字符串表示、

`getClass()` 获取类对象、

`clone()` 浅拷贝、

`wait()/notify()/notifyAll()` 线程协作、



### **🌟深拷贝和浅拷贝区别？**
 **浅拷贝**：复制对象本身字段值，基本类型复制值，引用类型复制引用（地址），新旧对象共享引用对象。

**深拷贝**：递归复制引用对象，副本和原对象完全隔离，修改一方不影响另一方。

**Object.clone()**：默认浅拷贝，且需实现 Cloneable。

**实现深拷贝方式**：递归 clone、拷贝构造、序列化/反序列化、BeanUtils 等。

典型坑：浅拷贝下修改共享的 List，原对象也会受影响。

### **🌟讲一下 Java 类加载/初始化流程。**

高分回答（示例）：
类加载主流程：加载（Loading）→ 链接（Linking：验证、准备、解析）→ 初始化（Initialization）→ 使用 → 卸载。  
初始化阶段核心是执行 `<clinit>`，即静态变量显式赋值和静态代码块。  
高分点：强调“加载”和“初始化”不是一回事，很多题目就在考触发初始化的边界条件。

**🌟什么是类加载，什么是类初始化？**

- 类加载：是“把类弄进 JVM，并做好基础准备”
- 类初始化：是“真正执行这个类的静态逻辑”

**🌟例子**

```java
class A {    
  static int x = 10;    
  static {        
    System.out.println("A init");    
  } 
} 
```

- 加载时：JVM 先把 A 的字节码读进来，完成验证、准备、解析
- 准备阶段：x 先是默认值 0
- 初始化阶段：才会执行 x = 10 和静态代码块，打印 A init

---

### **🌟什么情况下会触发类初始化？**

高分回答（示例）：
**主动使用会触发**，常见包括：  

1) `new` 创建对象；  
2) 访问或赋值该类的静态变量（非 `final` 编译期常量）；  
3) 调用该类静态方法；  
4) 反射主动使用；  
5) 初始化子类前先初始化父类；  
6) 启动类（含 `main`）初始化。  
   不会触发的典型场景：访问编译期常量、创建“该类数组类型”。

---

### **🌟另一个类里调用某个静态字段，会触发该类初始化吗？**

高分回答（示例）：
要看字段是不是“编译期常量”。  
如果是 `static final` 且值可在**编译期**确定，常量会被调用方常量池内联，通常不触发定义类初始化；  
如果是普通静态字段，通常会触发。  
回答这题最好明确“常量折叠/内联”这个关键词。

**🌟什么是编译期常量**

1. static final
2. 值在编译阶段就能确定
3. 一般是基本类型或字符串字面量常量

**🌟编译期常量VS运行时常量**

- 编译期常量：编译阶段就能确定值，编译器可以直接把值内联到使用方代码里
- 运行时常量：编译阶段不能确定，必须等程序运行时才能得到值

**🌟例子**

```java
class A {
    static {
        System.out.println("A init");
    }

    public static final int X = 10;

}
```

```java
class B {
    public static void main(String[] args) {
        System.out.println(A.X);
    }
}
```

这里很多情况下输出只有：

```
10
```

不会输出：

```
A init
```

原因是 10 在编译阶段就已经确定了，编译器可能直接把 A.X 替换成字面量 10。
运行时 B 不需要真的去“主动使用” A，所以 A 不初始化。

这就是“在另一个类里调用某个静态字段，不一定触发类初始化”的原因。

**🌟静态变量==静态字段**

---

### **🌟`new User[10]` 会初始化 User 类吗？**

高分回答（示例）：因为 new User[10] 创建的不是 User 对象，而是 User[] 数组对象。

JVM 只是在内存里开了一块能放 10 个 User 引用的位置，这时候数组里的每个元素默认都是 null，并没有真正去创建任何一个 User 实例，也就没有“主动使用” User 类，所以不会触发 User 的初始化。

你可以看这个例子：

```java
class User {    
  static {        
    System.out.println("User init");    
  } 
} 
public class Test {    
  public static void main(String[] args) {        
    User[] arr = new User[10];        
    System.out.println(arr.length);    
  } 
} 
```

输出通常只有：

```
10 
```

不会打印：

```
User init 
```

因为这里发生的是：

1. 创建了一个数组对象 User[]
2. 数组元素类型是 User
3. 但并没有创建 User 实例
4. 所以 User 类不需要初始化

你可以把它理解成：

- new User()：真的要用 User 这个类创建对象，所以要先初始化 User
- new User[10]：只是创建“装 User 引用的数组壳子”，还没真正用到 User 对象，所以不初始化 User

### 🌟单例模式了解吗

**单例模式就是**：一个类在整个系统里只创建一个实例，并且提供一个全局访问点来获取它。

常见使用场景：

- 配置中心对象
- 线程池管理器
- 缓存管理器
- 日志对象
- 数据库连接管理类

**各种单例模式对比**

**1. 饿汉式**

- 优点：简单、线程安全
- 缺点：不能懒加载

**2. 懒汉式（不加锁）**

- 优点：延迟加载
- 缺点：线程不安全

**3. 懒汉式（同步方法）**

- 优点：线程安全、实现简单
- 缺点：性能较低

**4. 双重检查锁（DCL）**

- 优点：懒加载、线程安全、性能较好
- 缺点：写法相对复杂，需要理解 volatile

**5. 静态内部类**

- 优点：懒加载、线程安全、实现优雅
- 缺点：理解上比饿汉式稍绕一点

**6. 枚举单例**

- 优点：最安全，能防反射和反序列化
- 缺点：有些业务同学不习惯这种写法

## 五、并发与线程

### **🌟进程、线程、协程的区别？**

**进程**是资源分配单位，

**线程**是 CPU 调度单位；同进程的线程共享地址空间。  
**协程**是用户态轻量执行单元，切换开销更低，适合高并发 IO 场景。  

### **🌟Java 里怎么创建线程？**

1) 直接方式：继承 `Thread`、实现 `Runnable`、实现 `Callable + FutureTask`；  
2) 工程方式：`ThreadPoolExecutor`（生产环境主流）；  
3) 原则：优先线程池，避免无限创建线程导致上下文切换和 OOM。  

---

### **🌟如果让你自己设计一个线程池，你会怎么设计？它是怎么消费任务的？**

**核心组成：**

1. 核心线程数 `corePoolSize`
2. 最大线程数 `maximumPoolSize`
3. 阻塞队列 `workQueue`
4. 空闲线程存活时间 `keepAliveTime`
5. 线程工厂 `threadFactory`
6. 拒绝策略 `RejectedExecutionHandler`

**任务消费流程：**

1. 来一个任务，如果当前线程数小于核心线程数，直接创建核心线程执行
2. 如果核心线程满了，就把任务放入阻塞队列
3. 如果队列也满了，并且线程数还没到最大线程数，就继续创建非核心线程执行
4. 如果线程数已经达到最大值且队列也满了，就走拒绝策略
5. 非核心线程空闲超过 `keepAliveTime` 会被回收

如果让我自己实现，我底层一般会用：

1. 一个阻塞队列保存待执行任务
2. 一组工作线程不断从队列里 `take()` 任务执行
3. 用状态字段控制线程池运行、关闭和中断

---

### **🌟常见线程池有哪些？**

`newFixedThreadPool`、`newCachedThreadPool`、`newSingleThreadExecutor`、`newScheduledThreadPool`。  
但生产更推荐直接 `ThreadPoolExecutor` 显式配置，避免 `Executors` 默认参数引入无界队列或线程膨胀风险。

- ThreadPoolExecutor：线程池的核心实现类
- newFixedThreadPool、newCachedThreadPool、newSingleThreadExecutor、newScheduledThreadPool：快捷创建方式

---

### **🌟线程生命周期是什么？**

高分回答（示例）：
`NEW` → `RUNNABLE` → `BLOCKED / WAITING / TIMED_WAITING` → `TERMINATED`。  
高分点：区分 Java 层 `RUNNABLE`（含就绪和运行）与 OS 调度态；说明 `wait/join/park/sleep` 对状态的影响。

```
NEW
 -> start()
RUNNABLE
 -> 抢不到 synchronized 锁
BLOCKED
 -> 抢到锁后回到
RUNNABLE
 -> wait()/join()/park()
WAITING
 -> 被唤醒后回到
RUNNABLE
 -> sleep()/wait(timeout)/join(timeout)
TIMED_WAITING
 -> 超时或唤醒后回到
RUNNABLE
 -> run() 执行结束
TERMINATED

```

---

### 🌟synchronized 原理和使用位置有哪些

**synchronized 的底层原理**

synchronized 是基于 对象监视器 **Monitor** 实现的。

你可以把每个 Java 对象理解成“可能关联一把监视器锁”：

- 线程进入 synchronized 代码块时，要先获得这个对象的 Monitor
- 拿到锁才能执行
- 执行完或异常退出时释放锁
- 其他线程如果也来竞争同一把锁，就会阻塞等待

**synchronized 使用位置有哪些**

synchronized 主要有 3 种使用位置。

**1. 修饰普通方法**

```java
public synchronized void test() { } 
```

**2. 修饰静态方法**

```java
public static synchronized void test() { } 
```

**3. 修饰代码块**

```java
synchronized (lock) {    // 临界区 } 
```

### **🌟`synchronized` 和 `ReentrantLock` 的区别？**

`synchronized` 是 JVM 内置监视器锁，语法简单，自动释放；  
`ReentrantLock` 是 JUC 显式锁，支持可中断、公平锁、尝试加锁、条件队列，多条件变量更灵活。

### 🌟单机锁VS分布式锁

- 单机锁：只在一个 JVM / 一个进程内部生效
- 分布式锁：在多个 JVM、多个服务实例之间生效

**一、单机锁是什么**

比如：

- synchronized
- ReentrantLock

它们锁住的是当前进程里的线程。

举个例子：

你的服务只部署了 1 台机器，或者虽然有多线程，但都在同一个 JVM 里。
这时用 synchronized / ReentrantLock 就能保证：

“同一时刻只有一个线程进入临界区”

但它只能管本机线程。

如果服务部署成 3 个实例：

- 实例 A 有自己的锁
- 实例 B 有自己的锁
- 实例 C 有自己的锁

这三个锁彼此不知道对方的存在，所以不能实现全局互斥。

**二、分布式锁是什么**

分布式锁要解决的问题是：

“多个服务实例、多个 JVM、甚至多台机器上的线程，怎么共同竞争同一把锁”

它通常依赖一个“大家都能访问到的共享存储/协调组件”，比如：

- Redis
- ZooKeeper
- etcd
- 数据库

常见做法比如 Redis 分布式锁：

```
SET lock_key unique_value NX PX 30000 
```

含义是：

- 只有 key 不存在时才能加锁
- 设置过期时间，防止死锁

这样不管请求打到哪台机器，只要它们都去 Redis 竞争同一个 lock_key，就能实现“全局只有一个成功”。

### 🌟乐观锁和悲观锁的区别？

**悲观锁**：认为冲突多，访问数据时先加锁（SELECT FOR UPDATE、synchronized），其他线程阻塞等待，适合写多读少。  
**乐观锁**：认为冲突少，读不加锁，更新时检查版本号/条件是否变化（如 `update ... where version=旧值` 或 `where stock>0`），失败则重试，适合读多写少。

  版本号机制是在更新时额外校验一个 version 字段，更新成功后 version 加 1。这样即使数据值改回原值，version 也会变化，从而**避免 ABA 问题**。

乐观锁不只有 CAS 和版本号两种，本质是在提交时校验数据是否被别人改过，版本号、时间戳、条件更新都算。

CAS 更偏底层并发原子操作，版本号更偏数据库和业务层并发控制。

### 🌟乐观锁的局限

1. 高冲突场景下会频繁失败重试
2. 只能保证更新时检测冲突，不代表所有复合业务逻辑天然安全
3. 如果有多个字段、多个步骤组合修改，仍可能需要更强的一致性控制

###   🌟怎么提高并发性能？

1. 减少锁粒度
2. 读写分离
3. 用 CAS 或版本号减少互斥
4. 避免长时间持锁

### **🌟如果让你设计一个多线程下安全的数据读取，还要尽量保证性能，你会怎么做？**

如果是**读多写少**场景，我会优先考虑这几种思路：

1. **读写锁**：读操作共享，写操作互斥，提升读并发
2. **Copy-On-Write**：写时复制，读完全无锁，适合读远多于写的配置类场景
3. **乐观读**：比如 `StampedLock` 的乐观读，先无锁读取，冲突时再回退
4. **缓存快照**：维护只读快照，让读线程访问不可变对象

如果数据结构本身支持并发安全，也可以用像 `ConcurrentHashMap` 这类并发容器。

### **🌟AQS 原理是什么？**
**核心**：AbstractQueuedSynchronizer，用 `volatile int state` 表示**同步状态** + CLH **双向队列**管理阻塞线程 + **CAS 修改 state**。

**流程**：

线程尝试 CAS 获取 state，成功则占锁；

失败则封装成 Node 入队，并 park 阻塞；

前驱释放锁时 unpark 后继，循环尝试获取。

**应用**：ReentrantLock、ReentrantReadWriteLock、Semaphore、CountDownLatch、线程池 Worker 都基于 AQS。

**可重入**：state 可大于 1，同一线程多次 lock 则 state++，unlock 时 state--，为 0 才真正释放。

🌟**AQS是什么**

AQS 是 AbstractQueuedSynchronizer，中文一般叫“抽象队列同步器”。它是 Java 并发包 java.util.concurrent 里非常核心的一个基础框架

**AQS 提供了一套“状态管理 + 等待队列 + 线程阻塞唤醒”的通用机制**，具体的锁语义由子类自己定义。

### **🌟如果让你实现一个并发安全的 Map，你会怎么做？**ConcurrentHashMap 的大概思路

“如果让我**实现并发安全 Map**，

最基础的做法是**给 HashMap 外层加锁**，这能保证线程安全，但**并发性能差**。

进一步可以用**读写锁**，让**读操作并发执行**。

再往上，如果要支持高并发，我会采用**哈希桶数组**的结构，把**锁粒度降到段或者桶**，而不是锁整个 Map。读操作尽量**无锁**，写操作先定位桶，**空桶**用 **CAS 插入**，发生冲突时只**锁当前桶**，在桶内更新链表或红黑树。对于哈希冲突严重的桶，可以把**链表转成红黑树**来降低查询复杂度。

最难的是**扩容**，因为并发迁移时要保证数据不丢失、读写可见，我会引入**迁移标记**，并允许多个线程**协作搬迁**。

**ConcurrentHashMap** 在 JDK8 基本就是这个**思路**，本质上是数组 + 链表/红黑树，配合 CAS、桶级 synchronized 和协作扩容来实现高并发。”

**HashMap VS HashTable VS ComcurrentHashMap**

- HashMap：线程不安全，扩容和并发写会出问题
- Hashtable：线程安全，但基本是大锁，性能差
- ConcurrentHashMap：细粒度并发控制，高并发下性能更好

### **🌟wait/notify 有什么作用？**
 **作用**：在持有对象 monitor 的线程间做协作，实现“条件不满足则等待、条件满足则被唤醒”。

**wait()**：释放当前对象锁，当前线程进入该对象的等待集，直到被 notify 或中断；被唤醒后需重新竞争锁才能从 wait 返回。

**notify()**：唤醒等待集中任意一个线程；

**notifyAll()** 唤醒全部。

**前提**：必须在 `synchronized(对象)` 块内调用，否则抛 `IllegalMonitorStateException`。

**与 sleep 区别**：sleep 不释放锁，wait 释放锁。

## 六、JVM

### **🌟JVM 内存结构有哪些？**
**五块区域**：

① 程序计数器 PC：当前线程执行字节码行号，唯一无 OOM；

② 虚拟机栈：栈帧（局部变量、操作数栈、返回地址），方法调用入栈、返回出栈；

③ 本地方法栈：native 方法；

④ 堆：对象实例、数组，GC 主战场，线程共享；

⑤ 方法区（JDK8 实现为元空间）：类元数据、常量、静态变量。

**线程私有**：PC、虚拟机栈、本地方法栈；

**共享**：堆、方法区。

**栈溢出**：栈深度超限（如无限递归）抛 StackOverflowError；

**堆溢出**：对象过多抛 OutOfMemoryError。

### **🌟元空间、堆分代、Eden/Survivor 比例？**
 **元空间**：JDK8 取代永久代，存类元数据于本地内存，避免永久代 OOM；默认不限制大小，需注意 metaspace 膨胀。

**堆分代**：新生代（Eden + 2 个 Survivor）+ 老年代；新对象先在 Eden，Minor GC 后存活对象进 Survivor，多次存活后晋升老年代，Major GC 回收老年代。

**比例**：Eden:S0:S1 常见 8:1:1（-XX:SurvivorRatio 可调）；新生代与老年代比例约 1:2（-XX:NewRatio）。

**目的**：分代假设“大部分对象朝生夕死”，新生代小一些可加快 Minor GC。

### **🌟垃圾回收器有哪些？**
 **Serial：单线程，STW，适用客户端；****

**ParNew：多线程版 Serial，配合 CMS；**

**Parallel Scavenge：多线程，关注吞吐量；**

**CMS：并发标记清除，低停顿，有碎片和浮动垃圾；**

**G1：分区回收，可设停顿目标，适合大堆；**

**ZGC/Shenandoah：超低延迟。**

选型**：吞吐优先用 Parallel；低延迟用 G1/ZGC；老项目或小堆用 CMS。

### **🌟对象池怎么实现？怎么让对象尽量不被频繁 GC？**

对象池的目标，是复用那些“创建成本高、初始化重、重复创建浪费大”的对象。

实现思路一般是：

1. 预先创建一批对象
2. 放到一个池子里维护空闲对象
3. 使用时从池子里借
4. 用完后归还，而不是直接丢弃

数据结构上常见会用：

1. **阻塞队列**，比如 `ArrayBlockingQueue`
2. 或者**链表 / 双端队列**维护空闲对象

为什么这样对象不容易被 GC？

1. 因为池子本身持有这些对象的**强引用**
2. 只要对象仍被池子引用，就不是垃圾对象

如果是并发场景，还要考虑：

1. 借还超时
2. 最大池大小
3. 对象有效性检测
4. 泄漏回收

一句话总结：**对象池不是“让对象永远不回收”，而是通过长期持有可复用对象的引用，降低频繁创建和回收的成本。**

## 七、MySQL 与事务

### 🌟索引是什么？

索引是帮助数据库快速定位数据的数据结构，InnoDB 默认使用 B+ 树。  
本质是用空间换时间，提升查询效率，但会增加写入和维护成本。  

### **🌟为什么 InnoDB 选 B+ 树？**
高分回答：  
（1）**B+ 树 vs 普通二叉树**：

B+ 树是**多路平衡树**，**单节点可存大量键**，**树高低，磁盘 IO 次数少**；

普通二叉树在数据有序时会退化成链表，查找 O(n)。  
（2）**B+ 树 vs B 树**：

B+ 树**非叶子节点不存数据，只存键和指针**，单页可容纳更多键，树更矮；

数据全在叶子节点，且叶子通过双向链表串接，天然**支持范围查询和顺序扫描**。  
（3）**B+ 树 vs 哈希**：

哈希等值查找 O(1)，但不支持范围、排序、模糊查询，且对磁盘页友好性差；

B+ 树适合磁盘按页读写模型。B+ 树单点查询复杂度约 O(log n)

### **🌟联合索引最左前缀与范围截断怎么理解？**
（1）**最左前缀**：联合索引 `(a,b,c)` 在 B+ 树中按 a→b→c 顺序排序；查询时必须从最左列开始匹配，否则索引无法使用。如 `where b=1 and c=2` 无法利用该索引。  
（2）**范围截断**：等值条件可继续利用后续列，但遇到范围条件（`>`、`<`、`between`、`like '%x'`）后，**该列及之后的列无法再用于有序查找**。例：`where a=1 and b>2 and c=3` 只用到 a 和 b，c 需回表过滤。  
（3）**SQL 写法顺序**：优化器会重排 WHERE 条件，关键是谓词类型（等值/范围），不是书写顺序。

### **🌟主键索引、唯一索引、普通索引区别？**
（1）**主键索引**：

每个表只能有一个，**值唯一且非空**，InnoDB 用主键组织聚簇索引

（数据按主键物理排序存储），其他索引的叶子节点存主键值用于回表。  
（2）**唯一索引**：

可建多个，保证列值唯一，NULL 可有多条（视实现而定）；

用于业务唯一约束，如手机号、用户名。  
（3）**普通索引**：

只加速查询，不保证唯一。  

### **🌟为什么推荐自增整型主键，而不是业务字段（如身份证）？**

自增主键写入时基本**顺序追加**，B+ 树页**分裂少，插入更稳定**；  
业务字段通常更长，索引更大，二级索引也会更重；  
此外业务字段可能变更，不适合做主键。  
所以工程上常用“无业务含义的短整型/长整型主键”。

### **🌟慢查询如何排查？N+1 问题怎么解决？**
高分回答：  
（1）**慢查询排查流程**：

① 开启 `slow_query_log`、设置 `long_query_time` 阈值；

② 从慢日志或监控定位慢 SQL；

③ 用 `EXPLAIN` 看 `type`（all/index/range/ref）、`key`、`rows`、`Extra`（是否文件排序、临时表、回表）；

④ 结合业务判断是否索引失效（函数包裹列、隐式类型转换、范围截断）；

⑤ 重建联合索引或 SQL 重写；

⑥ 回归压测与监控对比。  
（2）**N+1 问题**：一次查主表得 N 条，再循环查 N 次关联表，共 1+N 次查询。解决：改为 JOIN 一次查出，或批量查询关联表后内存组装。实习中把城市-房源从循环查改为 JOIN，查询时间从 500ms 降到 50ms，就是典型 N+1 优化。

### 🌟MySQL 隔离级别
 **四种隔离级别**：

读未提交 RU、

读已提交 RC、

可重复读 RR（默认）

串行化 Serializable

### 🌟**脏读，不可重复读，幻读** 

**脏读**：事务 A 读到事务 B 未提交的修改；

发生在 RU。  
**不可重复读**：事务 A 内两次读同一行，结果不同（B 已提交的修改被读到）；

RC 及以下会出现，RR 通过 MVCC 解决。  
**幻读**：事务 A 内两次按相同条件查询，记录数不同（B 插入或删除了满足条件的行）；

RR 下 InnoDB 通过 MVCC + 间隙锁减少幻读，串行化彻底消除。 

| 问题       | 现象                     | 解决级别               |
| :--------- | :----------------------- | :--------------------- |
| 脏读       | 读到未提交数据           | Read Committed 及以上  |
| 不可重复读 | 同一行前后读取结果不同   | Repeatable Read 及以上 |
| 幻读       | 同条件查询结果集数量不同 | Serializable           |

 

### 🌟数据库和缓存不一致怎么处理

我采用 Cache Aside：写请求“先更新 DB，再删除缓存”。  
在项目中店铺更新就是 `updateById` 后删除 `cache:shop:{id}`。  
如果追求更高一致性，可加延迟双删、删除失败重试、消息补偿，并配 TTL 做兜底。

### 🌟为什么更新数据库后删缓存，而不是直接更新缓存？

1) 并发写时“改缓存”容易发生**覆盖回退**（新值被旧写覆盖）；  
2) 缓存字段可能比数据库复杂，更新路径容易漏字段；  
3) 热点不稳定时，删缓存让下一次读按需回源，整体更稳。  

### **🌟给表建索引要考虑哪些因素？**

高分回答（示例）：
从“收益-成本-稳定性”三维回答：  

1) 查询模式：where/join/order by/group by 高频列；  
2) 选择性（区分度）：高区分列优先；  
3) 联合索引列顺序：最左前缀、等值优先、范围靠后；  
4) 覆盖索引机会；  
5) 写放大成本（插入/更新维护索引）；  
6) 数据量与冷热分布。  
   结合实习经历可补一句：通过慢 SQL 反推索引，而不是先拍脑袋建索引。

### **🌟建了索引查询仍然慢，怎么排查？**

高分回答（示例）：
我的排查步骤是：  

1) 先看慢查询日志定位 SQL；  
2) `EXPLAIN` 看 `type/key/rows/Extra`，判断是否走索引、是否回表/临时表/文件排序；  
3) 检查是否有索引失效（函数、隐式类型转换、范围条件截断）；  
4) 根据 where/join/order by 重建联合索引；  
5) 必要时做 SQL 重写、分页优化、冷热数据分层。  
   高分点在于“步骤化”和“可落地”。

**🌟`EXPLAIN` 看 `type/key/rows/Extra`**

- type：访问类型，判断 SQL 扫描效率高不高

  常见从好到差大致可以这么记：

  - system
  - const 通过主键或唯一索引，并且只匹配一条记录。
  - eq_ref
  - ref 使用普通索引或非唯一索引做等值查询。
  - range 范围查询。
  - index 扫描整个索引树 虽然走了索引，但其实是“全索引扫描”
  - ALL 全表扫描

- key：实际用了哪个索引

- rows：MySQL 预估要扫描多少行

- Extra：额外信息，能看出有没有回表、临时表、文件排序等风险

**🌟什么是回表**

在 InnoDB 里：

- 主键索引的叶子节点，存的是整行数据
- 二级索引的叶子节点，存的是“索引列值 + 主键值”

所以如果你先走了二级索引，但查询需要的列不在这个二级索引里，MySQL 就要先从二级索引找到主键，再根据主键去主键索引里把整行数据查出来。

这个“再去主键索引查一次”的过程，就叫回表。

**🌟什么是临时表**

临时表指 MySQL 在执行 SQL 时，为了处理中间结果额外创建的表。

比如：

```mysql
SELECT age, COUNT(*) FROM user GROUP BY age; 
```

如果不能直接利用索引高效完成分组，MySQL 可能先生成一个临时表来存中间分组结果。

**风险**

- 临时表本身有开销
- 数据量小时可能在内存
- 数据量大时可能落磁盘，性能会更差

所以 Using temporary 通常说明 SQL 还有优化空间。

**🌟什么是文件排序**

Using filesort 不是说“一定用文件”，而是说：

“MySQL 不能按索引顺序直接拿到结果，必须额外做排序。”

例如：

```
SELECT * FROM user WHERE age = 20 ORDER BY score; 
```

如果没有 (age, score) 这样的合适索引，MySQL 就可能先筛选出 age=20 的记录，再自己排序。

这就是 filesort。

### **🌟联合索引下不同查询语句会命中哪些列？规则是什么？**

高分回答（示例）：
规则核心是**最左前缀**：联合索引从左到右匹配，遇到**范围查询**后，后续列利用会受限；中间列断开会导致后续列无法用于索引定位。  
面试时建议按 `where` 条件顺序、是否等值、是否范围逐项推导，不要直接拍结论。  
关键词：最左前缀、范围截断、覆盖索引、回表。

### **🌟执行 `alter table` 时数据库一般做哪些操作？**

高分回答（示例）：
看 DDL 类型与版本能力（MySQL 5.6/5.7/8.0 的 `ALGORITHM=INSTANT/INPLACE/COPY` 差异）：  
可能涉及元数据锁（MDL）、创建临时表/重建表、回填数据、重建索引、切换新旧表、提交元数据变更。  
高分补充：线上变更要考虑锁等待和阻塞风险，必要时用 gh-ost / pt-osc 做在线变更。

**1. 解析 SQL，检查元数据**

数据库先解析你的 ALTER TABLE 语句，确认：

- 要改哪张表
- 改什么结构
- 语法是否合法
- 表、列、索引是否存在
- 当前变更是否允许执行

例如你要加一个列，它先得知道表结构里有没有同名列。

**2. 获取元数据锁（MDL）**

执行 ALTER TABLE 时，MySQL 会对表加元数据锁。

这个锁的作用是：
在修改表结构期间，防止别的会话同时对这张表做不兼容的结构变更，保证一致性。

这是线上特别重要的一点，因为：

- 如果有长事务一直占着表
- ALTER TABLE 可能拿不到锁，被阻塞
- 反过来，ALTER TABLE 拿到锁后，也可能影响后续查询或写入

所以很多线上 DDL 慢，不一定是“改表本身慢”，而可能是“等锁慢”。

**3. 判断采用哪种 DDL 算法**

MySQL 会根据变更类型和版本能力，决定这次 DDL 是：

- INSTANT
- INPLACE
- COPY

这是面试高分点。

**INSTANT**

只改元数据，不重建数据页，速度最快。
例如某些“加列到末尾”的操作，在较新版本 MySQL 里可以做到瞬时完成。

**INPLACE**

不需要整张表复制，但可能仍需要重建部分数据结构或索引。
比 COPY 好，但也不一定完全无影响。

**COPY**

最重的一种方式。
通常会创建新表，把旧表数据一行行拷贝过去，再切换表。
这种开销最大，对大表风险也最高。

所以你可以理解为：

- 能只改字典就只改字典
- 不行就尽量原地处理
- 再不行才整表拷贝

**4. 可能创建临时表/新表**

如果当前变更不能直接在原表上完成，数据库可能会：

1. 创建一张新表，结构是修改后的结构
2. 把旧表数据拷贝过去
3. 重建相关索引
4. 完成后切换新旧表

这就是很多人说的“重建表”。

常见容易触发表重建的操作有：

- 修改列类型
- 调整列顺序
- 某些加减列
- 修改主键
- 某些字符集变更

**5. 回填数据**

如果涉及新表重建或数据格式变更，MySQL 需要把旧表数据搬到新结构里。

例如：

```
ALTER TABLE user MODIFY COLUMN name VARCHAR(128); 
```

这时数据库可能要把原有数据按新的列定义重新组织。

如果表很大，这一步就可能很慢。

**6. 重建索引**

如果表结构变化影响索引，数据库可能需要重建索引。

例如：

- 新增索引
- 删除索引
- 修改被索引列类型
- 重建表时顺带重建所有相关索引

索引重建本身也是重活，尤其大表更明显。

**7. 更新数据字典 / 元数据**

结构改完以后，MySQL 要更新系统里的表定义信息，比如：

- 列定义
- 索引定义
- 主键信息
- 表版本
- 统计信息

这一步相当于告诉数据库：
“从现在开始，这张表的新结构是这个。”

**8. 切换新旧表并提交**

如果用了重建表方式，最后会做一次切换：

- 新表替换旧表
- 提交元数据变更
- 释放锁

这一步完成后，外部看到的就是新结构。

**9. 释放锁**

DDL 完成后，数据库释放持有的元数据锁，其他会话才能继续正常访问。

**🌟什么是alter table** 

ALTER TABLE 就是修改表定义，不是改表里的某一行数据，而是改表结构。

```mysql
ALTER TABLE user ADD COLUMN age INT;
ALTER TABLE user DROP COLUMN age;
ALTER TABLE user MODIFY COLUMN name VARCHAR(64);//修改列类型
ALTER TABLE user ADD INDEX idx_age(age);
ALTER TABLE user DROP INDEX idx_age;
ALTER TABLE user RENAME COLUMN old_name TO new_name;
```

**🌟什么是元数据**

数据库里的真正业务数据是这样的：

```
user 表里有一行：id=1, name='Tom', age=20 
```

这是“数据”。

那下面这些信息不是业务数据本身，而是“描述这些数据怎么存、怎么组织、怎么约束”的信息，这就是元数据：

- 有哪些库、哪些表
- 表里有哪些列

**🌟什么是分库分表**

分库分表，就是把原来一张大表、一个大库的数据，拆到多个库、多个表里。

**1. 分表**

还是在同一个数据库里，但把**一张表拆成多张表**。

- 降低单表数据量
- 提高单表查询和写入性能

**2. 分库**

把数据**拆到多个数据库实例**里。

- 分散数据库压力
- 提高整体吞吐
- 解决单库容量瓶颈

**3. 分库分表**

一起做。

比如：

- 先按用户 ID 分到 4 个库
- 每个库再拆成 8 张表

这样整个数据规模和吞吐能力都会明显提升。

**🌟为什么要分库分表**

本质上是为了解决这几类问题：

- 单表数据量过大
- 单库连接数和吞吐到瓶颈
- 索引太大导致查询慢
- 写入热点过高
- 数据库磁盘和 CPU 扛不住

- 模糊查询
- 高亮
- 聚合分析

你可以把它理解成：

MySQL 更适合事务和精确查询，ES 更适合搜索和复杂检索。

------

**🌟ES 解决什么问题**

- 关键词搜索

- 海量文本检索

## 八、Redis、缓存与登录态

### 🌟**实现 LRU 缓存（最近最少使用淘汰）**

高分回答：  
**思路**：最近访问的放前面，最久未访问的淘汰。

**实现**：**HashMap + 双向链表**。HashMap 存 key→Node；链表按访问顺序，头为最近使用，尾为最久未使用。`get`：存在则把节点移到头并返回值；

`put`：存在则更新值并移到头；不存在则新建节点放头，超容量则删尾节点。

也可用 `LinkedHashMap`（accessOrder=true），重写 `removeEldestEntry`。时间 O(1)，空间 O(capacity)。

**HashMap + 双向链表**

```java
import java.util.HashMap;
import java.util.Map;

public class LRUCache {
    class Node {
        int key, value;
        Node prev, next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private int capacity;
    private Map<Integer, Node> map = new HashMap<>();
    private Node head = new Node(0, 0);
    private Node tail = new Node(0, 0);

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        if (!map.containsKey(key)) {
            return -1;
        }
        Node node = map.get(key);
        remove(node);
        addToHead(node);
        return node.value;
    }

    public void put(int key, int value) {
        if (map.containsKey(key)) {
            Node node = map.get(key);
            node.value = value;
            remove(node);
            addToHead(node);
            return;
        }

        Node node = new Node(key, value);
        map.put(key, node);
        addToHead(node);

        if (map.size() > capacity) {
            Node last = tail.prev;
            remove(last);
            map.remove(last.key);
        }
    }

    private void addToHead(Node node) {
        node.next = head.next;
        node.prev = head;
        head.next.prev = node;
        head.next = node;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }
}


```


### **🌟Redis 为什么单线程还快？**
 **原因**：① 内存访问纳秒级，比磁盘快几个数量级；

② IO 多路复用（select/epoll），单线程可同时监听大量连接，避免阻塞；

③ 单线程执行命令，无锁竞争、无上下文切换；

④ 命令执行路径短，数据结构高效（跳表、压缩列表等）。

**Redis 6**：网络 IO 可多线程，但命令执行仍是单线程，保证原子性。

**对比多线程**：多线程需加锁，反而可能降低吞吐；Redis 瓶颈在内存和网络，不在 CPU。

### **🌟为什么选 Redis，不选本地缓存？如果用一致性哈希把请求打到固定机器做 local cache，可行吗？**

**为什么优先选 Redis：**

1. Redis 是**集中式缓存**，多实例服务**天然共享数据**
2. 数据更新后，其他服务实例可以立刻**读到最新值**
3. 运维、监控、TTL、淘汰策略都比较成熟

**本地缓存 + 一致性哈希的优点：**

1. 访问**链路更短**，**延迟更低**
2. 不依赖外部 Redis，热点**命中性能**可能更高

**Redis 胜在共享和成熟，本地缓存胜在极致低延迟。**

🌟**什么是本地缓存**
本地缓存就是某台应用机器进程内的缓存，数据直接存在这台**机器的内存**里，比如 Java 里常见的 Caffeine、Guava Cache，或者自己用 **HashMap 做一个简单缓存**。

🌟**local cache和redis的区别**

1. local cache：缓存放在**应用机器自己的内存里**
2. Redis：缓存放在独立的**分布式缓存服务**里

🌟**什么是一致性哈希**
一致性哈希是一种**分配策略**，把某个 key 稳定地映射到某一台机器上。
比如对 userId=123 做哈希，结果总是落到第 3 台机器，那么和这个用户相关的请求就尽量打到第 3 台机器，这样第 3 台机器上的本地缓存就能生效。

- 尽量让同一个 key 总去同一台机器
- 扩容缩容时，减少大量 key 重新映射

所以你说的“用一致性哈希把请求打到固定机器做 local cache”，**是可行的**，而且业界确实有这种思路。

但面试里通常还要继续往下答：**可行，不代表更优，也不一定适合这个场景。**

🌟**为什么很多场景选 Redis，不选纯本地缓存**
因为一旦服务是**多机部署**，纯**本地缓存会有几个典型问题**：

- **缓存不共享**
  - 同一个 key 可能在某台机器命中，在别的机器 miss
- **一致性差**
  - 数据更新后，所有机器上的本地缓存都要失效，很难统一管理
- **容量受限**
  - 每台机器给业务线程和缓存都要留内存，缓存空间有限
- **扩缩容影响大**
  - 新机器没有历史缓存，流量切换后命中率容易抖动
- **运维能力弱**
  - Redis 天然支持 TTL、淘汰策略、监控、主从、高可用，本地缓存很多要自己补

### **🌟Redis 是怎么分片的？常见部署方式有哪些？**

**分片**就是把数据拆散到多台 Redis 节点上，目的是**横向扩容**，提升容量和吞吐。

1.**怎么分片？**

Redis 早期可以通过客户端分片来做，比如哈希取模或一致性哈希；

现在更常见的是 Redis Cluster，它把 key 映射到 16384 个 hash slot，再把 slot 分配给不同节点。

2.**Redis 常见部署方式**

包括**单机、主从、哨兵和 Cluster**。

**单机**最简单；

**主从**主要用于读写分离；

**哨兵**是在主从基础上做高可用故障转移；

**Cluster** 则同时支持分片和高可用，适合更大规模的生产环境。

### **🌟Redis 的淘汰策略和过期删除机制有哪些？LRU / LFU 是什么？**

**过期删除：**

Redis 对设置了 TTL 的 key，不是到点立刻全部同步删掉，而是结合两种机制：

1. **惰性删除**：访问 key 时发现它过期了，就顺手删掉
2. **定期删除**：后台周期性抽样扫描一部分过期 key，删除其中已过期的数据

这样做是为了在 **CPU 开销和内存回收及时性**之间做平衡。

**内存淘汰：**

当 Redis 达到 `maxmemory` 后，会按配置策略淘汰 key，常见的有：

1. `noeviction`：不淘汰，写入报错
2. `allkeys-lru`：从所有 key 中按**最近最少使用**淘汰
3. `volatile-lru`：只在设置了过期时间的 key 里按 LRU 淘汰
4. `allkeys-lfu`：从所有 key 中按最少使用频率淘汰
5. `volatile-lfu`：只在有过期时间的 key 里按 LFU 淘汰
6. `allkeys-random` / `volatile-random`：随机淘汰
7. `volatile-ttl`：优先淘汰剩余 TTL 更短的 key

**LRU** 是最近最少使用，认为“最近很久没用过”的数据更可能以后也不用了。  
**LFU** 是最少使用频率，认为“历史上用得少”的数据更适合淘汰。

### **🌟缓存穿透、击穿、雪崩区别和方案？**

**穿透**：查不存在的数据，缓存和 DB 都无，每次请求打库。

方案：缓存空值（短 TTL）、布隆过滤器前置拦截。

**击穿**：热点 key 过期瞬间，大量请求同时打库。

方案：互斥锁（只有一个线程查库回填）、逻辑过期（不设真实 TTL，另存过期时间，异步重建）。

**雪崩**：大量 key 同时过期或 Redis 宕机，请求涌向 DB。

方案：过期时间加随机偏移、多级缓存、限流降级、集群高可用。

### **🌟缓存击穿的互斥锁和逻辑过期分别怎么做？有什么区别？**

**互斥锁**：查缓存未命中时先 `setnx lock:key` 抢锁，拿到锁的线程查库并回填缓存后释放锁；其他线程未抢到则 sleep 后重试查缓存。

**逻辑过期**：缓存不设真实 TTL，value 中存过期时间；命中后发现逻辑过期则抢锁，抢到则开异步线程回填，当前线程直接返回旧数据；未抢到也返回旧数据。

**区别**：互斥锁会阻塞等待，逻辑过期不等待、立即返回旧值，高并发下体验更好。

### **🌟布隆过滤器原理是什么？如何降低误判率？**

布隆过滤器用位数组 + 多个哈希函数判断“可能存在/一定不存在”。  
特点是无假阴性、有假阳性。  
降低误判率的方法：增大位数组长度、增加并优化哈希函数个数、控制装载率并定期重建。

### **🌟Cache Aside 为什么“更新数据库后删缓存”？**
  **为什么删而不是更新**：

① 并发写：A 写 1、B 写 2，若都改缓存，执行顺序可能是 B 先更新缓存 2、A 后更新缓存 1，最终库是 2 但缓存是 1，不一致；

② 缓存字段可能来自多表或聚合，更新逻辑复杂易漏；

③ 删缓存让下次读回源，按最新库数据重建，更简单可靠。

## 九、消息队列、异步与一致性

### **🌟为什么用消息队列？**
**三大价值**：

① 解耦：生产者和消费者互不依赖，新增消费方只需订阅；

② 削峰：瞬时高峰写入队列，消费者按能力消费，保护下游；

③ 异步：主流程快速返回，耗时操作异步处理。

### **🌟消息队列一般用在什么场景？**

三类典型场景：异步解耦、削峰填谷、跨系统事件驱动。  
例如注册后发短信/邮件、订单创建后通知下游、高峰流量下平滑消费。 

### **🌟为什么服务链路里要用消息队列？**

核心是把“用户强感知链路”和“可延后任务”拆开。  
主流程快速响应，下游异步处理，降低 RT 并保护数据库/下游服务。

### **🌟RabbitMQ 完整通信流程是什么？**

生产者将消息发送到 Exchange，

Exchange 根据 routing key + binding 路由到 Queue，

消费者从 Queue 拉取/订阅并消费，成功后 ACK。  

为了可靠性通常会加：消息持久化、发布确认、消费者手动 ACK、重试和死信队列。  

### **🌟服务负载高时，有哪些手段处理用户请求？**

先分层处理：接入层限流、服务层降级熔断、数据层缓存与异步化。  
常见手段：令牌桶限流、热点缓存、请求合并、异步队列削峰、隔离舱线程池。

### **🌟令牌桶和漏桶有什么区别？适合什么场景？**

令牌桶是按速率生成令牌，允许一定突发流量；  
漏桶是固定速率出流，强制平滑请求。  
一般 API 网关限流常用令牌桶（兼顾突发），强平滑整形常用漏桶。

### **🌟消息可靠性如何保证（不丢/不重）？**
 **不丢**：

① 生产端：开启确认机制（如 RabbitMQ publisher confirm），消息落盘后才 ack；

② Broker：持久化到磁盘；

③ 消费端：手动 ACK，处理成功后再确认，失败则 nack 重试。

**不重**：

消息系统通常“至少一次”投递，重试可能重复；

需业务幂等：唯一业务键（user_id+voucher_id）、DB 唯一约束、去重表等，重复消费时识别为已处理并 ACK。

### **🌟消费重试导致重复下单怎么处理？**
  **问题**：消费失败后重试，若第一次其实已成功（如超时、网络抖动），重试会再执行一次创建订单，导致一单多建。

**方案**：

① 订单号在入队前生成并写入消息，消费时用同一 ID，避免每次重试生成新 ID；

② 业务唯一键：user_id + voucher_id 天然唯一，消费前先查是否已存在；

③ 数据库唯一约束 `unique(user_id, voucher_id)` 兜底，重复插入抛异常时视为幂等成功并 ACK；

④ 去重表：存 messageId，消费前查，有则跳过。

### 🌟你知道二阶段事务消息吗？**

知道，它是解决“本地事务与消息发送原子性”问题的方案。  
流程通常是：先发半消息（prepare）→ 执行本地事务 → 提交/回滚消息；若状态不明，由 MQ 回查本地事务状态。  
适用场景是跨系统最终一致性，不等价于本地 ACID 事务。  
在当前项目里未实现这一套，但可作为“删除缓存失败后异步补偿”或“订单与下游状态同步”的升级方向。

二阶段事务消息 = 先发一条暂时不可投递的半消息，等本地事务执行成功后再提交消息；如果本地事务失败，就回滚消息。

**第一阶段**

先发一条“半消息”或者叫“预备消息”

特点是：

- MQ 先把消息存下来
- 但这条消息对消费者不可见
- 消费者此时还不能消费

**第二阶段**

执行本地事务，然后根据结果决定：

- 本地事务成功：提交消息，让消息对消费者可见
- 本地事务失败：回滚消息，删除或丢弃这条消息

所以叫二阶段，本质上就是：

1. 先预留消息
2. 再确认提交还是回滚

### 🌟消息队列异步处理主要是做什么？解决什么问题？比你直接做有什么优势？**

**做什么：**

项目里秒杀通过 Redis Stream 异步创建订单。

这里的**异步处理**，具体就是 **Lua 校验通过**后，先把订单消息**写入 Redis Stream**，也就是完成**入队**；

然后由后台消费者线程 VoucherOrderHandler 去**消费消息**，

最终执行**数据库扣库存**和**订单落库**。

这里的 DB 指的是 MySQL，消费者指的是项目里单线程线程池启动的订单处理线程。

**解决的问题**：

请求线程只做 Redis 原子校验和入队，快速返回；

而数据库写操作交给后台慢慢处理，从而起到削峰、保护数据库的作用。

**优势：**

① **削峰**：瞬时大量请求只做 Lua 校验和**入队**，DB 由消费者按能力处理，不会被冲垮；

② **降 RT**：主线程快速返回，用户体验好；

③ **解耦**：下单与落库分离，后续可扩展多消费者、重试、监控。  
代价：用户看到「抢购成功」后，若消费失败或延迟，可能出现「提示成功但实际未成单」；需通过 XACK 语义、pending 重试、幂等设计和监控告警来降低影响。

**🌟1.入队是什么**

**把秒杀请求对应的订单信息写进消息队列**，让后面的后台线程慢慢消费，而不是当前请求线程直接去操作数据库。

- 把“这个用户抢到了、要创建订单了”这件事，先记到 **stream.orders** 这个消息流里

```java
redis.call('xadd', 'stream.orders', '*', 'userId', userId, 'voucherId', voucherId, 'id', orderId)
```

**🌟2.消费者是什么**

VoucherOrderHandler
它会不断从 **stream.orders** 里读消息

```java
List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
        Consumer.from("g1", "c1"),
        StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
        StreamOffset.create("stream.orders", ReadOffset.lastConsumed())
);

```

- 从 stream.orders 读订单消息
- 读到了就转成 VoucherOrder
- 然后调用 createVoucherOrder(voucherOrder) 真正创建订单

### **🌟异步慢慢处理可能带来什么问题？用户已提示成功但消费失败怎么办？措施是什么？**

高分回答：  
问题：消费延迟或失败时，用户以为成功实则未成单，体验差，可能客诉。  
措施：① Redis Stream 用 XACK 确认，**未 ACK 的消息会进入 pending-list**，消费者可从 pending 重新拉取；

② 项目里有 `handlePendingList` 处理异常后未确认的消息；

③ 前端可**轮询订单状态**或通过 **WebSocket** 推送最终结果；

④ 监控消费延迟、失败率、pending 堆积，及时告警；⑤ 对长时间未成单的做补偿（退款/补发优惠券等）。  
坦诚说：在「至少一次投递 + 幂等」模型下，理论上存在「一直失败最终放弃」的边界，需要人工或自动化补偿流程兜底。

**🌟Redis Stream 的工作原理**

正常消息 -> 加入 pending-list -> **处理成功** -> ACK -> 从 pending list 移除 -> 完成
正常消息 -> 加入 pending-list -> **处理中失败** -> 不 ACK -> 留在 pending-list
下次**异常恢复** -> 重新读 pending-list -> 再处理成功 -> ACK -> 从 pending list 移除 -> 完成

```
[用户请求秒杀]
        |
        v
[Lua 脚本执行]
判断库存
判断是否重复下单
扣 Redis 库存
写入 Stream
        |
        v
[stream.orders]
  一条订单消息进入流
        |
        v
[XREADGROUP by g1/c1]
消息投递给消费者 c1
        |
        v
[Pending List]
状态：已投递，未确认
        |
        +--------------------+
        |                    |
        | 成功处理            | 处理失败/宕机
        v                    v
[创建订单 + 扣DB库存]      [未 ACK]
        |                    |
        | XACK               |
        v                    |
[从 Pending List 删除] <-----+
        |
        v
[消息处理完成]

```

**🌟什么是pending list**

- PEL：Pending Entries List
- 意思是“待确认消息列表”

**🌟为什么要向前端推送最终结果（在用户点了秒杀之后，接口不是已经马上返回“成功”了吗）**

```
用户点了秒杀
-> 接口马上返回“成功”
-> 但后台订单可能还在处理中
-> 用户不知道最终到底有没有下单成功
```

这就是为什么要补一个“最终结果通知机制”。

**🌟什么是webSocket**

**前端和后端之间建立一条长期保持的双向连接。**

**和普通 HTTP 最大区别是：**

- HTTP：前端发请求，后端回响应，一次就断
- WebSocket：连接建立后，前后端都可以随时主动发消息给对方

普通 HTTP 像“打电话问一句就挂断”
WebSocket 像“电话一直通着，有消息就直接说”

### **🌟用消息队列能不能解决「扣金币和发钱在不同服务」？如果发钱永远不能成功怎么办？回滚的是什么？**

  可以。

流程：

① 检查资格后发 MQ，消息体包含 userId、金额等；

② 消费者先扣金币（本地事务），成功则发下一条消息或调用发钱服务；

③ 发钱服务执行；若发钱失败，可重试；超过重试仍失败，进入死信队列，由定时任务或人工处理。  
若发钱「永远」失败（如账户异常）：需**补偿**，把已扣的金币加回用户账户。即回滚的是「扣金币」这一步，通过补偿任务或人工操作完成。消息队列本身不提供自动回滚，需要业务设计补偿逻辑。

**🌟「扣金币和发钱在不同服务」是什么意思**

**一个完整业务动作，被拆到了两个独立的微服务里做。**

```
奖励服务
   |
   +--> 调账户服务：扣金币
   |
   +--> 调钱包服务：发钱
```

**导致的问题**

因为这两个动作不在同一个数据库、同一个本地事务里。

假设流程是：

1. 调用账户服务，扣金币成功
2. 调用钱包服务，发钱失败

那就会出现：

- 金币已经扣了
- 钱没发出去

业务结果不一致。

这就是**分布式事务/最终一致性问题**。

## 十.分布式

### 🌟说说分布式 RPC 框架有哪些？说说Spring Cloud / Dubbo / 注册中心

**分布式 RPC 框架有哪些**

**1. Java 生态常见**

- Dubbo
- Spring Cloud OpenFeign
- gRPC
- Motan
- HSF（阿里内部较多）
- Thrift

**2. 跨语言常见**

- gRPC
- Thrift

**1. 注册中心**
是基础设施，负责服务注册和发现。

**2. Dubbo**
是 RPC 框架，需要借助注册中心找到服务地址。

**3. Spring Cloud**
是微服务治理体系，也需要借助注册中心来做服务发现。

------

#### **🌟什么是分布式 RPC 框架**

RPC 是 Remote Procedure Call，远程过程调用。

意思是：
你在本地像调用一个普通方法一样，**去调用另一台机器上的服务**。

比如：

```
orderService.createOrder() 
```

表面像本地方法，实际上这个服务可能部署在另一台机器上，底层会经过：

- 服务发现
- 网络通信
- 序列化/反序列化
- 负载均衡
- 超时重试
- 返回结果

所以分布式 RPC 框架，本质上就是帮我们屏蔽这些远程调用细节。

------

#### **🌟Spring Cloud 是什么**

严格来说，Spring Cloud 不是一个单纯的 RPC 框架，它是**微服务治理框架集合**。

它解决的不只是“远程调用”，还包括：

- 服务注册与发现
- 配置中心
- 负载均衡
- 熔断降级
- 网关
- 链路追踪
- 消息总线

所以你可以理解成：

Spring Cloud = 一整套微服务基础设施
而远程调用只是其中一部分。

Spring Cloud 更偏微服务全家桶，服务调用通常走 HTTP；Dubbo 更偏专门做高性能 RPC 调用。

------

#### **🌟Dubbo 是什么**

Dubbo 是阿里开源的高性能 Java RPC 框架。

它的核心能力包括：

- 服务发布
- 服务发现
- 远程调用
- 负载均衡
- 容错重试
- 集群容错
- 监控治理

Dubbo 更像“专门解决服务间调用”的框架，重点在 RPC 性能和服务治理。

------

#### **🌟注册中心是什么**

注册中心可以理解成：

服务的通讯录 + 地址簿

在分布式系统里，一个服务通常不是只有一个实例，比如：

- user-service 有 3 台
- order-service 有 5 台

那消费者怎么知道该调用谁？

这时候就需要注册中心。

它主要干两件事：

**1. 服务注册**
服务启动时，把自己的信息注册上去，比如：

- 服务名
- IP
- 端口
- 健康状态

**2. 服务发现**
消费者去注册中心查询某个服务有哪些可用实例，然后再进行调用。

### 🌟**分布式 UID 怎么设计？**

高分回答：  
**常见方案**：

① 雪花算法（时间戳 + 机器 ID + 序列号），趋势递增、高性能；

② Redis INCR（按天或按业务 key），简单可靠；

③ 数据库自增（多库需号段）；

④ UUID（无序、索引效率差，不推荐做主键）。  

**项目结合**：`RedisIdWorker` 使用"时间戳差值左移 32 位 + 当日 Redis 自增序列"，key 为 `icr:order:yyyy:MM:dd`，保证全局唯一、趋势递增、易读。需注意时钟回拨和序列溢出的边界处理。

🌟**什么是UID**

UID 就是 Unique Identifier，中文一般叫“**唯一标识**”或“唯一 ID”。
系统里给每一条数据、每一个对象**分配一个不会重复的编号**，用来唯一地区分它。

比如：

- 用户表里的 user_id
- 订单表里的 order_id
- 商品表里的 sku_id
- 分布式系统里的全局流水号

如果放到你刚才那道面试题里，UID 指的就是“全局唯一的流水号”，要求**在多台机器同时生成时也不能重复**。

🌟**UID、UUID、雪花算法 ID 三者的区别**

- UID：概念名，泛指唯一 ID
- UUID：一种随机/规则生成的全局唯一字符串 ID
- 雪花算法 ID：一种分布式场景下常用的整型全局唯一 ID 生成方案

### 🌟分布式事务了解过吗？

  常见方案：

① **2PC**：协调者两阶段提交，同步阻塞，有单点；

② **TCC**：Try-Confirm-Cancel，需业务实现补偿；

③ **Saga**：长事务拆成多个本地事务，失败执行逆向操作；

④ **本地消息表**：事务内写业务+消息，异步发 MQ；

⑤ **RocketMQ 事务消息**：Half 消息 + 本地事务 + 回查。  
适用场景：扣金币和发钱分属不同服务时，无法用本地事务，需上述方案之一保证最终一致。项目中未实现完整分布式事务，但秒杀和 Cache Aside 采用最终一致性思路。

## 十一.Spring

### 🌟**Spring 事务传播机制有哪些？**

Spring 一共定义了 7 种传播行为，在 Propagation 枚举里：

- REQUIRED
- REQUIRES_NEW
- SUPPORTS
- NOT_SUPPORTED
- MANDATORY
- NEVER
- NESTED

**1. REQUIRED**

这是默认值，也是**最常用的**。

- 如果当前有事务，就加入当前事务
- 如果当前没有事务，就新建一个事务

**2. REQUIRES_NEW**

- 不管当前有没有事务，都新建一个事务
- 如果外层已经有事务，就把外层事务先挂起
- 内层事务执行完，再恢复外层事务

**3. SUPPORTS**

- 如果当前有事务，就加入事务
- 如果当前没有事务，就以非事务方式执行

**4. NOT_SUPPORTED**

- 以非事务方式执行
- 如果当前有事务，就把当前事务挂起

**5. MANDATORY**

- 必须在已有事务中运行
- 如果当前没有事务，直接抛异常

**6. NEVER**

- 必须在没有事务的情况下执行
- 如果当前存在事务，直接抛异常

**7. NESTED**

- 如果当前有事务，就在当前事务里开启一个嵌套事务
- 如果当前没有事务，一般等价于 REQUIRED，新建事务

🌟**什么是Spring 事务传播机制**

一个已经带事务的方法，去调用另一个也带事务的方法时，Spring 应该怎么处理这两个事务边界。

它解决的是：

- 是加入当前事务？
- 还是新开一个事务？
- 还是干脆不用事务执行？
- 如果外层有事务、内层抛错，彼此会不会互相影响？

所以“传播”这个词的意思就是：
**事务在方法调用链之间怎么传递。**

🌟**为什么需要事务传播机制**

举个简单例子：

```
A() {    下单();    B(); } 
```

假设：

- A() 有事务
- B() 也有事务

那问题来了：

- B() 是加入 A() 的事务一起提交吗？
- 还是自己单独开一个事务？
- 如果 B() 失败了，要不要把 A() 一起回滚？
- 如果 A() 失败了，B() 已经提交了怎么办？

这就是事务传播机制要定义的规则。

## 十二.AI应用

### 🌟如何通过提示词让 AI 生成符合项目风格的代码？有最佳实践吗

我一般会把提示词设计成一个**固定模板**，让 AI 不只是“写功能”，而是**按项目约束来生成代码**。

核心思路是**先把上下文喂完整**，**再把边界讲清楚**，最后**给验收标准**。通常我会在提示词里明确这几类信息：

- 角色和目标：告诉它你现在是这个项目里的后端工程师，要完成什么需求
- 技术栈和框架：比如 Java + Spring Boot + MyBatis，或者 PHP + ThinkPHP
- 项目风格：目录结构、命名规范、DTO/VO 习惯、异常处理方式、日志风格
- 参考代码：给它当前项目里最接近的 controller、service、mapper 或已有模块，让它模仿
- 输入输出契约：接口参数、返回结构、错误码、字段含义
- 非功能要求：幂等、事务、缓存、鉴权、日志、监控、单测
- 边界条件：空值、重复请求、并发、异常回滚、兼容旧接口
- 输出要求：只改哪些文件，是否要带注释，是否要补测试

**最佳实践**我一般总结成 4 点：

1. 先给“相似样例”，再让它生成
   AI 最容易学的是模式，不是抽象要求。直接给一个项目里现成的 service/controller 示例，效果通常比只说“按项目风格写”好很多。
2. 把“不要做什么”写清楚
   比如不要引入新框架、不要修改返回结构、不要改表结构、不要用项目里没有的工具类。这种负约束很重要。
3. 一次只让它做一件明确的事
   不要一个提示词里同时让它设计接口、写实现、补测试、重构老代码、解释思路。越聚焦，生成结果越稳定。
4. 让它按检查清单自检
   比如在提示词最后加一句：
   “生成后请自检：是否符合现有目录结构、是否复用已有工具类、是否处理异常和事务、是否和现有返回格式一致。”
   这样结果会明显更贴近工程代码。

### 🌟说说 **RAG / MCP / AI 工程化**

- RAG：怎么让 AI 用到外部知识
- MCP：怎么让 AI 标准化**调用工具和数据源**
- AI 工程化：怎么把 AI 能力真正做成可落地、可维护的系统

------

🌟**RAG 是什么**

RAG 是 Retrieval-Augmented Generation，中文一般叫“检索增强生成”。

它的核心思想是：

先从外部知识库里**检索相关内容**，再把检索结果作为上下文交给大模型生成答案。

为什么需要它？

因为大模型本身有几个问题：

- 训练数据不是实时的
- 不知道你公司的私有知识
- 容易幻觉
- 很难直接记住大量垂直领域文档

所以 RAG 的目标就是：

不给模型硬塞知识，而是在**回答前临时查资料**。

------

**🌟RAG 的基本流程**

一个典型 RAG 流程通常是：

1. 用户提问
2. 把问题转成向量或检索条件
3. 去知识库里查相关文档片段
4. 把检索结果拼进 prompt
5. 让模型基于这些资料回答
6. 返回结果，必要时附来源

比如用户问：

“公司报销流程怎么走？”

RAG 系统会先去内部文档库检索：

- 报销制度
- OA 流程
- 财务说明

然后再让模型基于这些文档回答。

------

🌟**MCP 是什么**

MCP 一般指 Model Context Protocol。

可以把它理解成：

让大模型用统一协议去连接外部工具、数据源和能力的标准。

如果说 RAG 解决的是“怎么给模型补知识”，
那 MCP 更像解决：

怎么让模型**规范地调用工具**。

比如一个 AI 助手可能要连接：

- 数据库
- 文件系统
- Git 仓库
- 浏览器
- 日历
- 知识库
- 第三方 API

如果每接一个工具都手写一套私有协议，会非常乱。
MCP 的价值就是把这些工具能力标准化，让模型知道：

- 这个工具能做什么
- 输入参数是什么
- 返回结果是什么
- 怎么安全调用

------

🌟**什么是 AI 工程化**

AI 工程化，说白了就是：

把大模型能力从一个 Demo，做成稳定、可维护、可上线的生产系统。

很多人会写 prompt，能做个聊天页面，但这不叫工程化。
工程化更关注的是：

- 系统架构
- 稳定性
- 成本
- 安全
- 评估
- 迭代效率

### **🌟你平时会用 AI 参与开发吗？AI 现在能介入到什么程度？**

会，但我不会把 AI 当成“自动写完一切”的黑盒，而是把它放在可控流程里用。

我一般会这样接入：

1. **需求拆解**：先让 AI 帮我把需求拆成功能点和边界情况
2. **代码生成**：生成接口骨架、DTO、校验逻辑、基础测试样例
3. **Review 与修正**：我自己负责确认业务正确性、边界条件、异常处理和风格一致性
4. **排障与重构**：让 AI 帮我分析报错、梳理调用链、给重构建议

我会把 AI 覆盖率说成：

1. 模板化、重复性、结构化代码，AI 覆盖率很高
2. 业务边界、数据一致性、复杂并发和最终质量把关，仍要工程师负责

### **🌟你做开发时怎么处理单测、corner case 和最终验证？**

一般流程是：

1. 先明确输入输出和异常路径
2. 让 AI 帮我补基础测试样例
3. 我自己重点补 corner case，比如空值、边界值、重复请求、异常路径
4. 最后结合日志、接口联调和真实数据再做一次验证

### **🌟如果让你做知识库、Skill 或 Agent，你会怎么设计？**

高分回答：

我会从“场景、知识、检索、执行、评估”五步去设计。

1. **先定场景**：明确是代码问答、排障助手、业务知识检索，还是自动执行工具
2. **整理知识源**：文档、代码库、FAQ、接口定义、历史案例
3. **做检索层**：结构化信息走数据库或搜索，非结构化文档走向量检索或混合检索
4. **做工具层**：把常用能力封装成工具，比如查日志、查接口、生成 SQL、执行脚本
5. **做评估层**：看命中率、回答准确率、幻觉率、人工接管率

如果做 Skill 或 Agent，我会特别注意两点：

1. 给模型清晰的输入边界和权限边界
2. 让关键动作可审计、可回放、可回滚

### 🌟什么是AIGC

AIGC 就是利用人工智能技术生成内容的方式，核心是通过大模型、生成模型等，根据输入的提示词自动生成文本、图片、音频、视频等内容。

## 十三.计算机网络

### **🌟TCP 三次握手和四次挥手过程？**

**三次握手：**

1. 客户端发送 `SYN`，表示自己想建立连接，并告诉服务端自己的初始序列号
2. 服务端回复 `SYN + ACK`，表示自己同意建立连接，同时也带上自己的初始序列号
3. 客户端再回复 `ACK`，表示自己收到了服务端的确认

之所以需要三次，不是为了“形式上对称”，而是为了让双方都确认两件事：

1. 自己的发送能力正常
2. 对方的接收和发送能力正常

**四次挥手：**

1. 客户端发送 `FIN`，表示自己这边数据发完了
2. 服务端回复 `ACK`，表示知道了，但它可能还有数据没发完
3. 服务端数据发完后，再发送自己的 `FIN`
4. 客户端回复 `ACK`

这里容易说错的一点是：挥手过程中服务端第二次发的是 `FIN`，不是 `SYN`。

最后客户端会进入 `TIME_WAIT`，主要是为了：

1. 确保最后一个 ACK 能让服务端收到
2. 避免旧连接的报文影响后续新连接

### **🌟了解 SSO（单点登录）吗？**

SSO 的目标是在多个系统间一次登录、处处可用。  
核心是统一认证中心、统一会话凭证和跨系统信任（如 OAuth2/OIDC/CAS）。

### 🌟Cookie、Session、Token 各自是什么？有什么区别？

高分回答：

这三个东西分别解决不同层面的问题，最好不要混着说。

**Cookie：**

1. 是浏览器端保存的一小段数据
2. 由服务端通过 `Set-Cookie` 下发，也可以由前端写入
3. 浏览器后续请求会自动携带符合域名/path 规则的 Cookie

它本身只是“**存储载体**”，不等于登录态。

**Session：**

1. 是服务端保存的会话数据
2. 通常服务端会给客户端一个 `sessionId`
3. 客户端后续带着 `sessionId` 来，服务端就能找到对应会话

它是传统的有状态登录方案，优点是服务端可控，缺点是分布式场景需要共享 Session。

**Token：**

1. 是服务端签发给客户端的一段凭证
2. 客户端通常放在请求头里，比如 `Authorization`
3. 服务端收到后进行校验，确认用户身份

Token 可以是有状态的，也可以是无状态的。比如：

1. JWT 是典型无状态 Token
2. 我项目里是随机 UUID + Redis 的有状态 Token

一句话区分：

1. Cookie 是客户端存储方式
2. Session 是服务端会话机制
3. Token 是身份凭证机制

### **🌟HTTPS 的加密过程怎么讲？**

HTTPS 本质上是 **HTTP + TLS**。它不是全程都用非对称加密，而是“非对称加密负责安全协商，对称加密负责后续传输”。

标准过程可以这么讲：

1. 客户端发起 TLS 握手，请求服务端证书，并带上自己支持的加密套件
2. 服务端返回证书、公钥以及自己选定的加密套件
3. 客户端校验证书是否合法，主要看 CA 签名、域名、有效期
4. 校验通过后，客户端生成一个随机的会话密钥材料，用服务端公钥加密发给服务端
5. 服务端用私钥解开，双方协商出同一个会话密钥
6. 后续 HTTP 数据传输就使用这个对称密钥进行加密

这样设计的原因是：

1. 非对称加密安全，但性能慢
2. 对称加密快，适合传大流量数据

HTTPS 主要解决三件事：

1. **加密**：防止中间人看到明文
2. **身份认证**：确认你连的是目标服务器
3. **完整性保护**：防止数据被篡改

### **🌟HTTP/2 有哪些新特性？和 HTTP/3 相比有什么区别？**

高分回答：

**HTTP/2 的核心改进：**

1. **二进制分帧**：不再是文本协议，更便于解析
2. **多路复用**：一个 TCP 连接上可以并发传多个请求，减少队头阻塞
3. **Header 压缩**：用 HPACK 压缩请求头，降低重复头部开销
4. **服务端推送**：服务端可主动推资源给客户端，不过现在实际使用不算多

**HTTP/3 的核心变化：**

1. 底层不再基于 TCP，而是基于 **QUIC over UDP**
2. 把传输层握手和加密协商进一步整合，连接建立更快
3. 避免了 HTTP/2 在 TCP 层仍然存在的队头阻塞问题

简单对比：

1. HTTP/2 解决的是“应用层复用效率”
2. HTTP/3 进一步解决的是“底层 TCP 队头阻塞和握手时延”

面试里一句高分总结可以这么说：**HTTP/2 是在 TCP 上优化 HTTP，HTTP/3 是直接绕开 TCP，用 QUIC 重新做一套更适合现代网络的传输方案。**
