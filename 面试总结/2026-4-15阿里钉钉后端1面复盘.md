### 2. MySQL 里面的事务隔离级别有哪几种？

高分回答：

MySQL 里事务隔离级别主要有四种，从低到高分别是：

1. 读未提交，Read Uncommitted
2. 读已提交，Read Committed
3. 可重复读，Repeatable Read，也是 InnoDB 默认隔离级别
4. 串行化，Serializable

它们本质上是在并发性能和一致性之间做权衡。隔离级别越高，能避免的并发读写异常越多，但锁冲突和性能开销也通常越大。

---

### 3. 这几个隔离级别分别解决了什么问题？

高分回答：

可以从三个典型并发问题来回答：脏读、不可重复读、幻读。

读未提交基本不解决这些问题，一个事务能读到另一个事务还没提交的数据，所以可能发生脏读。

读已提交解决脏读。也就是说，一个事务只能读到其他事务已经提交的数据。但是在同一个事务里，两次读取同一行，可能因为别的事务提交了更新而读到不同结果，所以仍然可能有不可重复读。

可重复读解决不可重复读。在 MySQL InnoDB 里，普通快照读通过 MVCC 保证同一个事务内多次读取看到的是同一个一致性视图。同时，InnoDB 在当前读、范围更新、加锁查询这类场景下会使用 next-key lock，也就是记录锁加间隙锁，来阻止其他事务在锁定范围内插入新记录，所以在工程上也基本解决了幻读问题。

串行化是最严格的隔离级别，它把并发事务尽量变成串行执行，能避免脏读、不可重复读和幻读，但并发能力最差。

面试里要注意一句话：标准 SQL 语义下，可重复读不一定完全解决幻读；但 MySQL InnoDB 的 RR 通过 MVCC 和 next-key lock，在快照读和当前读场景下分别处理了幻读问题。

### 4. MySQL 里可重复读就能解决幻读，它是怎么实现的？

高分回答：

InnoDB 的可重复读解决幻读要分两类读来看：普通快照读和当前读。

第一类是普通快照读，比如普通 `select`。它依赖 MVCC。事务第一次执行一致性读时会生成一个 Read View，Read View 里记录了当前活跃事务列表、最小活跃事务 ID、下一个将要分配的事务 ID 等信息。后续同一个事务里的快照读复用这个 Read View，再结合 undo log 版本链判断某个版本对当前事务是否可见。这样即使其他事务后来插入或修改并提交了数据，当前事务的普通查询也仍然看到第一次快照读时的一致性结果。

第二类是当前读，比如 `select ... for update`、`select ... lock in share mode`、`update`、`delete`。当前读要读取最新数据，所以不能只靠快照隔离。InnoDB 会对扫描到的索引范围加 next-key lock。next-key lock 可以理解为记录锁加间隙锁，既锁住已经存在的索引记录，也锁住记录之间的间隙，从而阻止其他事务在这个范围内插入新记录。

所以高分总结是：普通快照读通过 MVCC + Read View 让事务看不到后续插入的新行；当前读通过 next-key lock 锁住查询范围，阻止别人在范围内插入新行。这两部分结合起来，让 InnoDB 的 RR 在常见场景下解决了幻读。

### 5. 什么是缓存雪崩、缓存击穿、缓存穿透？怎么解决？

高分回答：

这三个问题都可能导致请求绕过缓存打到数据库，但原因不一样。

缓存雪崩是大量 key 在同一时间失效，或者 Redis 集群整体不可用，导致大量请求同时打到数据库。解决方案包括：给过期时间加随机偏移，避免同一批 key 同时过期；热点数据提前预热；使用多级缓存；Redis 做主从、哨兵或 Cluster 提高可用性；在服务侧做限流、降级和熔断，保护数据库。

缓存击穿是某一个热点 key 过期了，而这个 key 在瞬间有大量并发请求，导致这些请求同时打到数据库。解决方案包括：互斥锁重建缓存，只允许一个线程查库并回填；逻辑过期，先返回旧值并异步刷新；对极热点数据可以设置不过期，再通过后台任务主动刷新。

缓存穿透是请求查询一个缓存和数据库都不存在的数据，比如恶意请求不存在的 ID，导致每次都打到数据库。解决方案包括：参数合法性校验；缓存空值并设置较短 TTL；使用布隆过滤器在访问缓存和数据库前做前置拦截。

一句话区分：雪崩是大量 key 或 Redis 整体出问题，击穿是单个热点 key 过期，穿透是查不存在的数据。

---

### 6. 布隆过滤器具体怎么解决缓存穿透？

高分回答：

布隆过滤器适合用在缓存和数据库之前，先判断请求的 key 是否可能存在。

它的底层结构是一个位数组和多个哈希函数。初始化时，把数据库中合法的 ID 或 key 通过多个哈希函数映射到位数组上，并把对应位置置为 1。查询时，对请求 key 做同样的多次哈希：

如果有任何一个位置是 0，说明这个 key 一定不存在，可以直接拦截，不再访问缓存和数据库。

如果所有位置都是 1，说明这个 key 可能存在，再继续查缓存或数据库。

布隆过滤器的特点是可能误判存在，但不会误判不存在。也就是说，它可能让少量不存在的 key 通过，但能拦住大部分明显不存在的请求。因此工程上通常会把布隆过滤器和缓存空值一起使用：布隆过滤器做第一层拦截，缓存空值处理误判穿过来的少量请求。

还要补一句更新问题：如果业务有新增数据，需要同步把新 key 加进布隆过滤器；如果有大量删除，普通布隆过滤器不支持准确删除，可以使用计数布隆过滤器，或者定期全量重建。

### 7. 你最近做的 Agent 项目里面，ReAct 这个部分是怎么做的？

高分回答：

我这个项目里的 ReAct 指的是 Reasoning + Acting，不是前端 React。它解决的是扫地机器人客服场景里的多步骤任务编排问题。

普通 RAG 更像是“用户提问 -> 检索知识库 -> 生成答案”，适合回答静态知识。但有些问题需要先调用工具拿到上下文，再结合知识库回答。比如用户问“我在深圳，最近天气很潮湿，扫地机器人拖地应该怎么设置”，这就不仅要查产品说明，还需要知道用户所在城市和湿度。

我的 ReAct 链路大致是：

1. 先识别用户意图，判断是产品知识问答、故障排查，还是需要外部工具辅助
2. 模型根据工具描述选择动作，比如解析城市、调用天气或湿度工具、查询设备状态工具
3. 工具返回 observation 后，模型继续判断是否需要下一步动作
4. 需要产品知识时，再调用 RAG 检索召回说明书、FAQ 或维护建议
5. 最后把工具结果和检索结果综合成用户能理解的回答

工程上我会给 Agent 加上最大轮次、工具调用超时、参数 JSON Schema 校验和兜底回复，避免模型陷入无限循环，或者因为工具返回异常导致整个回答失败。

### 8. 这个 Agent 项目里主要的技术难点在哪里？或者你觉得比较有亮点的地方是什么？

高分回答：

这个项目我认为真正的难点不是简单把大模型接进来，而是把模型、知识库和工具调用变成一个稳定可控的后端服务。

第一个难点是多源上下文编排。用户的问题可能同时依赖产品知识、环境信息和设备状态，单纯 RAG 不够，所以我用 ReAct 让模型可以按步骤选择工具，再结合知识库回答。

第二个难点是 RAG 的召回质量。扫地机器人说明书、FAQ、故障码、维护建议这些文档如果直接切块，很容易召回不准。所以需要按产品型号、故障类型、使用场景做元数据标记，并控制 chunk 大小。必要时还可以加 rerank，把更相关的片段排到前面。

第三个难点是工具调用的稳定性。模型输出天然不稳定，所以工具参数需要结构化校验，比如城市、设备型号、故障码都要有明确 schema；工具失败时要有重试、降级和可解释的兜底回复。

第四个难点是可观测性。Agent 链路比普通接口长，如果回答错了，要能追踪当时的用户问题、检索片段、工具调用参数、工具返回结果和最终回答，方便定位是召回问题、工具问题还是模型生成问题。

所以我会把亮点总结为：这个项目把 RAG 的知识增强和 ReAct 的工具行动能力结合起来，并在后端层面做了工具 schema、调用限制、异常兜底和链路日志，让它更接近真实可用的客服系统。

### 9. 在秒杀项目里，怎么保证不超卖和一人一单？具体怎么实现？

高分回答：

我会把秒杀链路分成入口快速判断、异步下单、数据库最终兜底三层。

第一层是在 Redis 入口用 Lua 脚本保证原子性。Lua 脚本里一次性完成三件事：判断库存是否大于 0，判断当前用户是否已经下过单，扣减 Redis 库存并记录用户下单标记。因为 Redis 执行 Lua 是单线程原子执行的，所以并发请求不会在这几步之间穿插。

第二层是异步下单。Lua 判断成功后，把 userId、voucherId、orderId 这类下单消息写入队列，由后台消费者异步创建订单。这样入口请求可以快速返回，数据库不会直接承受秒杀流量。

第三层是数据库兜底。真正创建订单时，在数据库事务里做条件扣减：

```sql
update voucher
set stock = stock - 1
where id = ? and stock > 0;
```

如果影响行数为 0，说明数据库库存不足，不能创建订单。同时订单表上建立唯一索引：

```sql
unique key uk_user_voucher(user_id, voucher_id)
```

这样即使前面 Redis 或消息队列出现重复消费，数据库也能兜住防超卖和一人一单。Redis 负责削峰和快速失败，数据库唯一索引和条件扣减负责最终正确性。

### 10. 如果同一个用户并发发了两个请求过来要下单，怎么做到一人一单？

高分回答：

同一个用户并发两个请求时，首先在 Redis Lua 层拦截。

比如用一个 set 记录某个券已经下单的用户：

```text
seckill:order:{voucherId} -> userId set
```

Lua 脚本逻辑是：

```lua
-- 1. 判断库存
if tonumber(redis.call('get', stockKey)) <= 0 then
    return 1
end

-- 2. 判断用户是否已经下过单
if redis.call('sismember', orderKey, userId) == 1 then
    return 2
end

-- 3. 扣库存并记录用户
redis.call('decr', stockKey)
redis.call('sadd', orderKey, userId)
return 0
```

因为 Lua 脚本在 Redis 中是原子执行的，所以两个并发请求不会同时通过。第一个请求执行成功后，会把用户 ID 写入 set；第二个请求再进来时，`sismember` 就能发现这个用户已经抢过了，直接拒绝。

不过这里还要强调：Redis 只是入口层的一人一单，数据库层还必须有 `user_id + voucher_id` 唯一索引。因为消息可能重复投递，消费者可能重试，最终仍然要靠唯一索引保证不会创建两笔订单。

### 11. 这里只是把标记打到 Redis 上，后续怎么保证这个单一定下去？

高分回答：

这个问题的关键是区分两种失败：消息已经进队列之后消费者失败，和 Lua 成功之后消息还没进队列机器就宕机。

如果消息已经进入可靠队列，比如 Redis Stream、RocketMQ、Kafka，那么消费者失败可以通过 pending list、消费组重试、死信队列、幂等消费来解决。订单创建要按 orderId 或 `user_id + voucher_id` 做幂等，避免重复消费导致重复下单。

但如果只是“Lua 脚本执行成功后，应用再单独发送 MQ 消息”，这里确实有一致性漏洞：Lua 已经扣了 Redis 库存并记录用户下单，结果应用在发送 MQ 前宕机，订单消息就丢了，后面也不会创建订单。

所以高分回答要承认这个漏洞，并给出改造方案：

如果使用 Redis Stream，可以把写入下单消息也放到同一个 Lua 脚本里。也就是 Lua 中同时完成“检查库存、判断一人一单、扣减库存、记录用户、XADD 下单消息”。这样 Redis 状态变更和消息入队是原子的，不会出现 Redis 打标成功但消息没进队列的问题。

如果使用外部 MQ，比如 RocketMQ 或 Kafka，就需要引入更可靠的一致性方案，比如事务消息、本地消息表 outbox、或者把 Redis Stream 当作本地可靠队列，再由后台 relay 转发到外部 MQ。核心原则是：状态变更和消息发送不能是两个没有保障的独立动作。

### 12. 队列和 Lua 脚本的执行时序是怎么样的？Lua 脚本执行完立刻宕机，消息发不出去怎么办？

高分回答：

如果原方案是“先执行 Lua，Lua 成功后应用代码再发送 MQ”，那么时序是：

```text
请求进入服务 -> 执行 Redis Lua -> Lua 返回成功 -> 应用发送 MQ -> 消费者创建订单
```

这个时序里，`Lua 返回成功 -> 应用发送 MQ` 之间存在宕机窗口。一旦服务在这个窗口宕机，Redis 里库存已经扣了，用户也已经被标记下单，但订单消息没有发出去，后续订单就不会创建。这就是典型的一致性漏洞。

更好的方案是把消息入队动作放进 Lua：

```text
请求进入服务 -> 执行 Redis Lua
Lua 内部完成：校验库存、一人一单、扣库存、记录用户、XADD 到 Redis Stream
消费者从 Redis Stream 创建订单
```

这样 Lua 成功就意味着 Redis 状态和订单消息同时成功；Lua 失败就都不成功。后续如果消费者宕机，消息还在 Stream 的 pending list 里，可以恢复后继续处理。

面试时可以这样说：

“如果我原来是 Lua 后再发 MQ，那确实不能保证订单一定下去。pending list 只能解决消息已经入队后的消费失败，不能解决消息还没发出去的问题。要修这个问题，我会把消息写入 Redis Stream 放到 Lua 里一起做，或者使用事务消息 / 本地消息表这类可靠消息方案。”

这句话基本就是面试官想听到的关键点。

### 13. 说一下 JVM 的垃圾回收算法。

高分回答：

JVM 常见的垃圾回收算法主要有三类：标记-清除、复制、标记-整理。它们都建立在可达性分析的基础上，也就是从 GC Roots 出发，能被访问到的对象认为是存活对象，访问不到的对象可以回收。

标记-清除算法分两步：先从 GC Roots 出发标记所有可达对象，再扫描堆内存，把没有被标记的对象清掉。优点是思路简单，不需要移动对象；缺点是会产生内存碎片，而且清理效率会随着对象数量增加而下降。

复制算法把内存分成两块，每次只使用其中一块。GC 时把存活对象复制到另一块连续空间，然后一次性清空原空间。它的优点是没有碎片，分配内存很快；缺点是需要额外空间，而且如果存活对象很多，复制成本会比较高。所以它更适合新生代，因为新生代对象大多朝生夕死。

标记-整理算法也是先标记存活对象，然后把存活对象向一端移动，整理出连续可用空间，再清理边界外的垃圾。它解决了标记-清除的碎片问题，也不像复制算法那样浪费一半空间，但移动对象本身有成本，通常更适合老年代。

如果面试官继续追问，可以补充一句：实际 JVM 收集器通常会结合分代思想，新生代常用复制算法，老年代更多使用标记-清除或标记-整理思想；像 G1 这类收集器又会把堆划分成 Region，在局部范围内做复制和整理。

### 14. 说一下 Java 的类加载机制。

高分回答：

Java 类加载的生命周期一般可以分为：加载、连接、初始化、使用、卸载。其中连接又包括验证、准备、解析三个阶段。

加载阶段主要做三件事：通过类的全限定名获取 class 字节流；把字节流里的静态存储结构转换成方法区的运行时数据结构；在堆里生成一个 `java.lang.Class` 对象，作为访问这个类元数据的入口。

连接阶段分为三步。验证是检查 class 文件是否合法，防止破坏 JVM 安全；准备是给类变量分配内存并设置默认初始值，比如 `static int a = 10` 在准备阶段先是 0；解析是把常量池里的符号引用转换成直接引用。

初始化阶段才真正执行类构造器 `<clinit>`，给静态变量赋程序员写的初始值，并执行 static 代码块。比如刚才的 `static int a = 10`，到初始化阶段才会变成 10。

常见触发类初始化的场景包括：`new` 一个对象，访问或修改类的静态变量，调用类的静态方法，反射调用，以及初始化子类时先初始化父类。

### 15. 什么叫双亲委派机制？

高分回答：

双亲委派机制是 Java 类加载器处理类加载请求的一种规则。

当一个类加载器收到加载类的请求时，它不会一上来自己加载，而是先检查这个类是否已经被加载过。如果没有加载过，就把请求委托给父加载器；父加载器也会继续向上委托。只有当父加载器都无法加载这个类时，子加载器才会尝试自己加载。

典型类加载器层级是：Bootstrap ClassLoader、Platform ClassLoader 或早期的 Extension ClassLoader、Application ClassLoader，以及用户自定义 ClassLoader。

双亲委派的好处主要有两个：

1. 保证核心类库安全。比如用户自己写了一个 `java.lang.String`，也不会替换 JDK 自带的 String
2. 避免类被重复加载。一个类的唯一性由类的全限定名和加载它的 ClassLoader 共同决定

底层实现上，主要体现在 `ClassLoader#loadClass`：先查找已加载类，再委托父加载器，最后才调用自己的 `findClass`。

如果想再加一点深度，可以补充：双亲委派也有一些打破场景，比如 JDBC SPI 使用线程上下文类加载器，Tomcat 也会为了应用隔离设计自己的类加载机制。

### 16. Redis 里是怎么做持久化的？RDB 和 AOF 分别描述一下。

高分回答：

Redis 主要有两种持久化方式：RDB 和 AOF。

RDB 是快照持久化，会在某个时间点把 Redis 内存数据生成一个紧凑的二进制快照文件。通常通过 `BGSAVE` fork 子进程来做，子进程负责写 RDB 文件，主进程继续处理请求，期间依赖写时复制机制。RDB 的优点是文件紧凑、恢复速度快，适合备份和全量恢复；缺点是两次快照之间的数据可能丢失。

AOF 是追加日志持久化，会把 Redis 执行过的写命令追加到 AOF 文件里。AOF 的 fsync 策略一般有 always、everysec、no 三种，常用的是 everysec，最多丢 1 秒左右数据。AOF 的优点是数据更完整，可读性也更强；缺点是文件通常比 RDB 大，恢复时需要重放命令，速度可能更慢。

AOF 文件过大时会触发 AOF rewrite。重写不是简单压缩旧日志，而是根据当前内存状态生成一份等价但更短的新 AOF，比如多次 `set key` 最后只保留最终值。

工程上通常可以同时开启 RDB 和 AOF。Redis 重启时优先用 AOF 恢复，因为它通常数据更完整。新版本也支持混合持久化，把 RDB 快照和 AOF 增量结合起来，兼顾恢复速度和数据完整性。

### 17. Redis 的集群模式有了解吗？它是怎么实现的？

高分回答：

这里要先区分三个概念：主从复制、哨兵和 Redis Cluster。

主从复制解决的是数据冗余和读扩展。一个 master 可以有多个 replica，master 负责写，从节点复制 master 的数据，可以承担读请求。复制通常是异步的，所以主从之间可能有短暂延迟。

哨兵 Sentinel 解决的是主从架构下的自动故障转移。哨兵会监控 master 和 replica，如果 master 下线，会通过投票选出一个从节点提升为新的 master，并通知客户端更新连接。哨兵本身不做数据分片。

Redis Cluster 解决的是数据分片和高可用。它把整个 key 空间划分成 16384 个 hash slot，每个 master 节点负责一部分 slot。客户端访问某个 key 时，会通过 `CRC16(key) % 16384` 算出 slot，再路由到负责这个 slot 的节点。每个 master 可以有 replica，master 故障时由从节点自动提升。

Redis Cluster 节点之间通过 gossip 协议交换集群状态。如果客户端访问错节点，节点会返回 `MOVED` 或 `ASK` 重定向，让客户端去正确节点访问。

所以如果面试官问“Redis 集群模式”，高分回答应该是：主从和哨兵偏高可用，Redis Cluster 才是官方分片集群方案，核心是 16384 个 hash slot、master-replica、gossip 通信、MOVED / ASK 重定向和自动故障转移。

### 18. MySQL 的索引在 InnoDB 里是怎么实现的？B+ 树具体怎么实现？

高分回答：

InnoDB 的索引主要是用 B+ 树实现的，但面试时不能只说“B+ 树”，还要说清楚聚簇索引、二级索引和页结构。

B+ 树是一种多路平衡搜索树。相比二叉树，一个节点可以存很多 key 和指针，所以树高很低。数据库里一次磁盘 IO 通常读取一个页，InnoDB 默认页大小是 16KB，一个页里能存很多索引项，因此三四层 B+ 树就能支撑很大的数据量。

在 B+ 树里，非叶子节点主要存 key 和子节点指针，不存完整行数据，这样单个节点能容纳更多 key，进一步降低树高。所有完整数据都在叶子节点上，并且叶子节点之间按 key 顺序通过链表连接，所以非常适合范围查询和顺序扫描。

InnoDB 里主键索引是聚簇索引。聚簇索引的叶子节点存的是整行数据，所以按主键查询时，走到叶子节点就能拿到完整记录。

二级索引的叶子节点存的不是完整行，而是索引列和对应主键值。如果通过二级索引查询的列不全在索引里，就需要拿到主键后再回到聚簇索引查整行，这个过程叫回表。如果查询字段都在二级索引里，就可以形成覆盖索引，避免回表。

可以用一个例子总结查询过程：如果有索引 `(user_id, create_time)`，查询某个用户最近订单时，MySQL 会从根页开始按 key 比较，逐层定位到叶子页，再沿叶子节点链表做范围扫描。由于 B+ 树有序，所以范围查询效率很高。

### 19. 在线笔试：题目里提到“子序列”，子序列是不是不一定连续？可以用动态规划吗？

高分回答：

录音里没有完整题面，但从“子序列不一定连续”“可以用动态规划吗”这些关键词看，面试官大概率在考子序列类 DP。现场高分回答的第一步应该是先把概念说清楚：

“子序列不要求连续，只要求相对顺序不变；子串或子数组才要求连续。所以如果题目涉及两个字符串或两个序列的匹配、删除、保留，通常不能简单用滑动窗口，而要考虑双指针或动态规划。”

如果题目是判断 `s` 是否为 `t` 的子序列，用双指针即可：

```java
public boolean isSubsequence(String s, String t) {
    int i = 0, j = 0;
    while (i < s.length() && j < t.length()) {
        if (s.charAt(i) == t.charAt(j)) {
            i++;
        }
        j++;
    }
    return i == s.length();
}
```

如果题目是两个字符串的“删除类子序列问题”，比如求最少删除多少字符能让两个字符串相同，本质就是最长公共子序列 LCS。

状态定义：

```text
dp[i][j] 表示 a 的前 i 个字符和 b 的前 j 个字符的最长公共子序列长度
```

状态转移：

```text
如果 a[i - 1] == b[j - 1]:
    dp[i][j] = dp[i - 1][j - 1] + 1
否则:
    dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])
```

如果要求最少删除次数，答案就是：

```text
a.length + b.length - 2 * LCS
```

Java 代码：

```java
public int minDeleteToSame(String a, String b) {
    int m = a.length();
    int n = b.length();
    int[][] dp = new int[m + 1][n + 1];

    for (int i = 1; i <= m; i++) {
        for (int j = 1; j <= n; j++) {
            if (a.charAt(i - 1) == b.charAt(j - 1)) {
                dp[i][j] = dp[i - 1][j - 1] + 1;
            } else {
                dp[i][j] = Math.max(dp[i - 1][j], dp[i][j - 1]);
            }
        }
    }

    int lcs = dp[m][n];
    return m + n - 2 * lcs;
}
```

复杂度是 O(mn)，空间复杂度是 O(mn)。如果只需要长度，可以进一步用滚动数组优化到 O(n)。

面试现场的表达顺序应该是：先确认子序列不连续，再给状态定义，再说转移方程，最后写代码。不要一直沉默想“词”，至少先把暴力或 DP 方向说出来。

## 三、这场面试最应该补的高频追问

### 1. InnoDB RR 防幻读的标准回答

普通 `select` 是快照读，依赖 MVCC、Read View 和 undo log 版本链。同一个事务里复用同一个 Read View，所以看不到其他事务后续插入的新行。

`select for update`、`update`、`delete` 是当前读，要读最新数据，所以通过 next-key lock 锁住索引记录和间隙，阻止其他事务在范围内插入新记录。

一句话：快照读靠 MVCC 看不到幻影，当前读靠 next-key lock 阻止幻影产生。

### 2. 秒杀 Lua 后宕机的标准回答

如果 Lua 成功后再由应用发送 MQ，这中间宕机会丢消息，方案不可靠。pending list 只能解决消息已经进入队列后的消费失败，不能解决消息还没发出去的问题。

正确改法是把消息入队也放进 Lua，比如使用 Redis Stream 的 `XADD`，让“扣库存、记录用户、写订单消息”在 Redis 内原子完成。消费者再通过消费组、pending list、重试和数据库唯一索引保证最终创建订单。

### 3. Redis Cluster 的标准回答

主从复制负责数据冗余和读扩展，哨兵负责主从故障转移，Redis Cluster 才负责分片。Cluster 把 key 空间分成 16384 个 slot，每个 master 负责一部分 slot，key 通过 CRC16 计算 slot。节点间通过 gossip 通信，访问错节点时用 MOVED / ASK 重定向，master 故障后由 replica 自动提升。

### 4. Agent 项目亮点的标准回答

不要只说“四层架构”。应该说：

1. 用 ReAct 做多步骤工具调用，让模型能先拿环境 / 设备状态，再结合知识库回答
2. 用 RAG 解决产品知识和故障文档的事实依据问题
3. 用 schema、最大轮次、超时、重试和兜底，让工具调用更稳定
4. 用链路日志记录 query、检索片段、工具参数、工具结果和最终回答，方便排查错误

一句话：亮点是把不稳定的大模型能力封装成可控、可观测、可兜底的后端服务。
