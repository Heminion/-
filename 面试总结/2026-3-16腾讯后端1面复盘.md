### **【Q5】如果中间失败了怎么处理呢？**

### **【Q6】重试不会出现问题吗？你的每一步重复执行会不会出问题？**

高分回答：  
这里需要区分两个概念：**可重入**是同一线程多次获取同一把锁；**幂等**是同一操作多次执行效果与一次一致。面试官问的更多是「重试是否导致重复下单」，属于幂等范畴。  
项目中的幂等设计：① 订单号在入队前由 RedisIdWorker 生成并写入消息，重试时使用同一订单号；② 消费端先查 `user_id + voucher_id` 是否已存在；③ 建议 DB 增加 `unique(user_id, voucher_id)`，重复插入视为幂等并 ACK。可重入锁解决的是「同一用户并发多请求的串行化」，与幂等是不同维度。

### **【Q7】你是怎么实现这种可重入的机制的？**

高分回答：  
项目里用的是 Redisson 分布式锁，它底层支持可重入：同一线程多次调用 `lock()`，内部用 `state` 计数，`unlock()` 时 `state--`，为 0 才真正释放。但「一人一单」场景更关键的是**互斥**：同一用户的多请求需要串行，所以锁的 key 是 `lock:order:{userId}`，保证同一用户并发请求只能有一个进入临界区。Redisson 的可重入主要解决「锁内调用另一同样需要该锁的方法」时的死锁问题。

}

### **【Q9】流程本身会有什么问题？机器挂了，用户金币扣了但钱没发，怎么恢复？**

高分回答：  
若扣金币和发钱在**同一 DB 事务**内，任一步失败会整体回滚，不存在「扣了不发」；若中间进程挂掉，事务未提交也会回滚。  
若扣金币和发钱**分属不同服务/库**，无法用本地事务，需要**分布式事务或最终一致性**：如本地消息表、RocketMQ 事务消息、TCC 等。恢复时通过定时任务扫描「已扣未发」记录做补偿或人工处理。

### **【Q10】用户同时点了两次会是什么情况？怎么保证幂等？**

高分回答：  
两次请求若都能进入，可能执行两次扣金币和两次发钱。保证幂等的手段：① **互斥锁**：`lock:withdraw:date:userId`，同用户同天串行，第二次进来时第一次已写提现记录，检查失败直接返回；② **唯一约束**：提现记录表 `unique(user_id, date)`，第二次插入失败，捕获异常视为「已处理」；③ **幂等键**：请求带唯一 requestId，先查是否已处理，有则直接返回成功。  
注意：**可重入锁**是同一线程可多次获取，不适合「两次点击 = 两个请求/两个线程」的互斥；这里需要的是**互斥锁**（同一 key 只允许一个线程），不是可重入。

### **【Q11】可重入锁的 key 是 date+userId 吗？如果一天能换两次呢？**

高分回答：  
锁的 key 用 `date+userId` 可以，保证同用户同天串行。若一天能换两次，锁仍可不变，逻辑改为：在锁内查 `withdraw_log` 今日次数，若 < 2 则执行扣款+发钱+插入记录，否则返回「今日次数已用完」。  
可重入锁的 key 与「一天几次」无关；可重入解决的是「锁内调用另一需同一锁的方法」时的重入，不是次数限制。次数限制靠业务表（如 withdraw_log）的 count 或唯一约束（如 `unique(user_id, date, seq)`）实现。

### **【Q12】扣金币和发钱不在同一数据库/不同系统，怎么处理？**

高分回答：  
无法用本地事务，需要分布式事务或最终一致性：  
① **本地消息表**：扣金币时写本地事务 + 消息表，定时任务发 MQ，消费端发钱，失败重试；发钱成功则回调或更新消息状态。  
② **RocketMQ 事务消息**：发 Half 消息 → 执行本地扣金币 → 提交/回滚消息 → 消费端发钱，失败则回查 + 重试。  
③ **TCC**：Try 阶段预扣、预占；Confirm 真正扣和发；Cancel 回滚。  
④ **Saga**：拆成多个本地事务 + 补偿，任一步失败执行逆向补偿。  
核心思路：扣金币和发钱通过可靠消息或补偿机制达到最终一致，保证不会出现「扣了不发」或「发了不扣」。

### **【Q13】消息队列异步处理主要是做什么？解决什么问题？比你直接做有什么优势？**

高分回答：  
项目里秒杀通过 Redis Stream 异步创建订单。

这里的**异步处理**，具体就是 **Lua 校验通过**后，先把订单消息**写入 Redis Stream**，也就是完成入队；然后由后台消费者线程 VoucherOrderHandler 去**消费消息**，最终执行**数据库扣库存**和**订单落库**。这里的 DB 指的是 MySQL，消费者指的是项目里单线程线程池启动的订单处理线程。这样做的好处是，请求线程只做 Redis 原子校验和入队，快速返回；而数据库写操作交给后台慢慢处理，从而起到削峰、保护数据库的作用。

优势：① **削峰**：瞬时大量请求只做 Lua 校验和**入队**，DB 由消费者按能力处理，不会被冲垮；② **降 RT**：主线程快速返回，用户体验好；③ **解耦**：下单与落库分离，后续可扩展多消费者、重试、监控。  
代价：用户看到「抢购成功」后，若消费失败或延迟，可能出现「提示成功但实际未成单」；需通过 XACK 语义、pending 重试、幂等设计和监控告警来降低影响。

### **【Q14】异步慢慢处理可能带来什么问题？用户已提示成功但消费失败怎么办？措施是什么？**

高分回答：  
问题：消费延迟或失败时，用户以为成功实则未成单，体验差，可能客诉。  
措施：① Redis Stream 用 XACK 确认，**未 ACK 的消息会进入 pending-list**，消费者可从 pending 重新拉取；② 项目里有 `handlePendingList` 处理异常后未确认的消息；③ 前端可**轮询订单状态**或通过 **WebSocket** 推送最终结果；④ 监控消费延迟、失败率、pending 堆积，及时告警；⑤ 对长时间未成单的做补偿（退款/补发优惠券等）。  
坦诚说：在「至少一次投递 + 幂等」模型下，理论上存在「一直失败最终放弃」的边界，需要人工或自动化补偿流程兜底。

### 🌟Redis Stream 的工作原理

正常消息 -> 加入 pending-list -> **处理成功** -> ACK -> 从 pending list 移除 -> 完成
正常消息 -> 加入 pending-list -> **处理中失败** -> 不 ACK -> 留在 pending-list
下次**异常恢复** -> 重新读 pending-list -> 再处理成功 -> ACK -> 从 pending list 移除 -> 完成

```
[用户请求秒杀]
        |
        v
[Lua 脚本执行]
判断库存
判断是否重复下单
扣 Redis 库存
写入 Stream
        |
        v
[stream.orders]
  一条订单消息进入流
        |
        v
[XREADGROUP by g1/c1]
消息投递给消费者 c1
        |
        v
[Pending List]
状态：已投递，未确认
        |
        +--------------------+
        |                    |
        | 成功处理            | 处理失败/宕机
        v                    v
[创建订单 + 扣DB库存]      [未 ACK]
        |                    |
        | XACK               |
        v                    |
[从 Pending List 删除] <-----+
        |
        v
[消息处理完成]

```

#### 什么是pending list

- PEL：Pending Entries List
- 意思是“待确认消息列表”

### 🌟「扣金币和发钱在不同服务」是什么意思

**一个完整业务动作，被拆到了两个独立的微服务里做。**

```
奖励服务
   |
   +--> 调账户服务：扣金币
   |
   +--> 调钱包服务：发钱
```

#### 导致的问题

因为这两个动作不在同一个数据库、同一个本地事务里。

1. 调用账户服务，扣金币成功
2. 调用钱包服务，发钱失败

- 金币已经扣了
- 钱没发出去

业务结果不一致。

这就是**分布式事务/最终一致性问题**。

### **【Q17】缓存击穿是什么？互斥锁怎么做？逻辑过期怎么做？**

高分回答：  
**击穿**：热点 key 过期瞬间，大量请求同时打到 DB。  
**互斥锁**：查缓存未命中时先 `setnx lock:key` 抢锁，拿到锁的线程查库并回填缓存后释放锁；其他线程未抢到锁则 sleep 后重试查缓存或阻塞等待。项目里 `CacheClient.queryWithMutex` 即此思路，用 Redis setIfAbsent 实现互斥。  
**逻辑过期**：缓存不设真实 TTL，在 value 中存过期时间；命中后发现逻辑过期则抢锁，抢到则开异步线程回填，当前线程直接返回旧数据；未抢到也返回旧数据。项目里 `queryWithLogicalExpire` 即此思路，保证高并发下不全打 DB，同时尽量返回可用数据。

### **【Q18】乐观锁和悲观锁的区别？悲观锁是什么意思？**

高分回答：  
**悲观锁**：认为冲突多，访问数据时先加锁（如 SELECT FOR UPDATE、synchronized），其他线程阻塞等待，适合写多读少。  
**乐观锁**：认为冲突少，读不加锁，更新时再检查版本号/时间戳是否变化（如 `update ... where version=旧值`），失败则重试，适合读多写少。  
项目里扣库存用 `setSql("stock=stock-1").eq("voucher_id", id).gt("stock", 0)`，利用「条件更新」实现乐观锁：只有 stock>0 时才会更新，避免超卖。

### **【Q19】Lua 在 Redis 里的主要作用是什么？同一用户同时点两次，Lua 是并发执行两次还是串行排队？为什么能串行？**

高分回答：  
Lua 的主要作用是**原子性**：一系列 Redis 命令在一个脚本里执行，要么全成功要么全失败，且执行期间不会被其他命令打断。  
同一用户发两次请求，会触发两次 Lua 执行，但 Redis 是**单线程**执行命令的，所以这两次 Lua 会**串行排队**执行：先执行完第一次，再执行第二次。第一次已把 userId 写入 `seckill:order:{voucherId}`，第二次执行到 `sismember` 时命中，直接返回 2（重复下单），不会重复扣库存和入队。

### **【Q20】算法题：实现 LRU 缓存。**

高分回答：  
**思路**：最近最少使用 = 最近访问的放前面，最久未访问的淘汰。  
**实现**：HashMap + 双向链表。HashMap 存 key→Node；链表按访问顺序，头为最近使用，尾为最久未使用。`get`：存在则把节点移到头并返回值；`put`：存在则更新值并移到头；不存在则新建节点放头，超容量则删尾节点。  
也可用 Java 的 `LinkedHashMap`（accessOrder=true），重写 `removeEldestEntry` 控制容量。  
时间 O(1)，空间 O(capacity)。

## 🌟四、自我总结问题

### 1.什么是Redisson 的看门狗机制

Redisson 看门狗机制就是分布式锁的自动续期机制。当我们不手动指定锁过期时间时，Redisson 会给锁设置默认过期时间，并在后台定时续期，只要持锁线程还活着，锁就不会提前过期；如果服务宕机，看门狗停止，锁最终会自动释放，避免死锁。

### 2.为什么数据库的唯一索引能兜底不允许脏数据落库

唯一索引的作用是把‘同一用户同一天只能有一条提现记录’这个规则下沉到数据库层。即使应用层分布式锁失效，两个并发请求同时通过了前置校验，数据库在插入时也只会允许第一条成功，第二条因为**唯一键冲突失败**，所以最终数据不会重复。这相当于最终兜底。

### 3.可重入锁是什么，有什么用？

#### 真正的“可重入锁”是：

- 同一个线程已经拿到锁之后，可以再次进入这把锁保护的代码
- 典型例子是方法 A 加锁后调用方法 B，而 B 也要加同一把锁；如果锁不可重入，就会把自己锁死
- 适合有嵌套调用、递归调用、父子方法都要保护临界区的场景
- 常见实现就是 Java 的 synchronized 和 ReentrantLock

#### 它的作用主要是：

- 避免同线程二次加锁时发生死锁
- 让锁的粒度设计更灵活，调用链上多个方法都能安全复用同一把锁

#### 例子

```java
public class Account {
    private int balance = 100;
    private final ReentrantLock lock = new ReentrantLock();

    public void withdraw(int amount) {
        lock.lock();
        try {
            if (balance >= amount) {
                decrease(amount);
            }
        } finally {
            lock.unlock();
        }
    }

    public void decrease(int amount) {
        lock.lock();
        try {
            balance -= amount;
        } finally {
            lock.unlock();
        }
    }
}

```
##### 既然withdraw都加过锁了，为什么decrease还要加锁呢

因为 decrease() 很可能不是只给 withdraw() 一个地方调用的。

给 decrease() 也加锁，本质上是在保护这个方法本身，让它“单独被调用时也安全”。

你可以这样理解：

withdraw() 加锁，保护的是“这整个扣款流程”
decrease() 加锁，保护的是“余额减少这个底层动作”

如果 decrease() 永远只会被 withdraw() 内部调用，而且你能百分百保证以后也没人单独调用它，那确实可以不再加锁

### 4.什么是分布式事务

**分布式事务 = 一个业务操作跨多个服务/库时，怎么保证最终结果一致**

#### 核心目标

- 数据一致
- 失败可恢复
- 状态可追踪
- 系统别被锁死

#### 怎么实现

1. **强一致**
   大家像本地事务一样，要么全成功，要么全失败。
2. **最终一致**
   **允许短时间不一致，但通过重试、消息、补偿，最后变一致。**
