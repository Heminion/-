## 一、专业技能基础题

### 1. `ArrayList` 和 `LinkedList` 的区别是什么？你在业务里怎么选？

答题关键词：动态数组、随机访问、缓存局部性、节点开销、真实业务场景。

高分回答：

- `ArrayList` 底层是动态数组，随机访问是 `O(1)`，遍历性能也通常更好，因为内存连续、CPU 缓存命中率高。
- `LinkedList` 底层是双向链表，理论上插入删除某个已定位节点是 `O(1)`，但大多数业务要先查到那个位置，整体还是 `O(n)`。
- 在普通后端接口开发里，我几乎默认优先选 `ArrayList`，只有在“已经持有节点引用、且需要频繁在中间插删”的场景才会考虑链表。
- 面试时我会强调：不要机械背“链表增删快”，Java 真实业务里更重要的是访问模式和对象开销。

### 2. `HashMap` 底层结构是什么？`put` 的核心流程你怎么讲？

答题关键词：数组 + 链表 + 红黑树、hash、扰动、扩容、树化。

高分回答：

- JDK 8 的 `HashMap` 底层是“数组 + 链表 + 红黑树”，先根据 key 的 hash 定位桶，再在桶内查找节点。
- `put` 时会先做 hash 扰动，降低高位信息丢失带来的冲突，然后根据 `(n - 1) & hash` 找桶下标。
- 如果桶为空就直接插入；如果桶里已有元素，就看是覆盖旧值、链表追加，还是在链表过长时树化成红黑树。
- 当元素数量超过阈值 `capacity * loadFactor` 时触发扩容，扩容本质是创建更大数组并重分布节点。
- 我会补一句：面试官想听的不只是“链表变红黑树”，更想听你知道这么做是为了把极端冲突从 `O(n)` 降到 `O(logn)`。

### 3. 你怎么理解面向对象、继承和多态？不要背概念，结合项目讲。

答题关键词：抽象、复用、扩展点、接口编程、项目例子。

高分回答：

- 我对面向对象的理解是先抽象领域对象，再把变化点留在边界上，而不是把所有逻辑堆在一个大类里。
- 继承更适合表达稳定的“is-a”关系，比如统一的基类能力；但在业务开发里我更谨慎使用继承，避免层级太深。
- 多态更实用，比如对同一接口提供不同实现，让调用方依赖抽象而不是具体类。
- 在项目里我更常用的是“接口 + 实现类”的方式，比如 service 分层、工具抽象、模型工厂，本质上也是多态。
- 如果面试官追问，我会说：业务系统里组合通常比继承更稳，因为组合更容易扩展和替换。

### 4. 重载和重写有什么区别？为什么多态能让代码更好维护？

答题关键词：编译期绑定、运行期绑定、接口解耦、开闭原则。

高分回答：

- 重载是同一个类里方法名相同、参数列表不同，本质是**编译期多态**。
- 重写是子类覆盖父类方法，真正体现的是**运行期多态**，调用哪个实现取决于对象的实际类型。
- 多态的价值不在语法本身，而在于让上层依赖抽象，下层可以平滑替换实现。
- 这样新增实现时通常不需要改调用方，代码更符合开闭原则，系统更容易演进。

### 5. 反射的原理和典型使用场景是什么？你会怎么回答它的代价？

答题关键词：运行时获取类信息、动态调用、框架、性能、类型安全。

高分回答：

- 反射本质上是程序在运行时获取类的元信息，并动态创建对象、访问字段、调用方法。
- 它在框架里非常常见，比如 IOC、ORM、序列化、注解处理等，核心价值是“解耦硬编码依赖”。
- 代价主要有三点：性能通常比直接调用差、编译期类型检查弱、可读性和调试复杂度更高。
- 所以我的回答不会停在“反射很强大”，而是会补一句：业务代码里我会控制反射使用范围，更多让框架层去承担这部分复杂度。

### 6. 你怎么讲 JVM 的运行时内存结构？

答题关键词：堆、虚拟机栈、程序计数器、本地方法栈、方法区。

高分回答：

- JVM 运行时内存我一般分成线程私有和线程共享两类来讲。
- 线程私有部分包括程序计数器、虚拟机栈、本地方法栈；共享部分主要是堆和方法区。
- 堆里放对象实例，是 GC 的核心区域；虚拟机栈里是栈帧，包含局部变量表、操作数栈、方法返回信息。
- 方法区主要存类元数据、常量池、静态变量等内容。
- 我会补一句：大多数内存问题最后都绕不开“对象在哪分配、谁在引用、什么时候能被回收”。

### 7. 类加载机制怎么讲？双亲委派为什么重要？

答题关键词：加载、验证、准备、解析、初始化、双亲委派、类隔离。

高分回答：

- 类加载的完整流程是：加载、验证、准备、解析、初始化，使用和卸载通常放在更后面讲。
- 双亲委派的核心是：类加载请求先交给父加载器，父加载器加载不了，子加载器再自己加载。
- 这样做主要有两个价值：一是避免同一个类被重复加载，二是保护核心类库不被业务代码篡改。
- 比如 `java.lang.String` 必须由引导类加载器优先处理，否则安全边界会被破坏。

### 8. 对象在 JVM 里是怎么创建的？GC Roots 你会怎么解释？

答题关键词：类加载检查、内存分配、初始化、对象头、引用链、可达性分析。

高分回答：

- 对象创建我会按“先检查类是否已加载，再分配内存，再做零值初始化、对象头设置、执行构造方法”这条线来讲。
- 分配内存时常见有指针碰撞和空闲列表两种方式，取决于堆空间是否规整。
- JVM 判断对象是否可回收，主流不是引用计数，而是可达性分析。
- `GC Roots` 可以理解成一组起点，比如栈中的局部变量、静态变量、JNI 引用等，只要对象从这些根还能走到，就不能回收。

### 9. 常见垃圾回收算法有哪些？你会怎么把“算法”和“收集器”区分开？

答题关键词：标记清除、复制、标记整理、分代、G1。

高分回答：

- 算法层面我会先讲三类：标记清除、复制、标记整理。
- 年轻代通常更适合复制算法，因为对象朝生夕灭；老年代更常见标记整理或带整理能力的方案，避免碎片。
- 分代回收不是单独算法，而是一种设计思想：不同生命周期对象用不同策略处理。
- 如果面试官继续追问收集器，我会再接 Serial、ParNew、CMS、G1，并强调 G1 是面向可预测停顿时间的分区化回收器。

### 10. Redis 常见数据结构有哪些？你会怎么映射到业务？

答题关键词：String、Hash、List、Set、ZSet、Stream、Geo、Bitmap。

高分回答：

- `String` 适合缓存对象、计数器、分布式锁标记；`Hash` 适合存用户登录态这种结构化字段。
- `List` 适合简单队列；`Set` 适合去重、一人一单、标签集合；`ZSet` 适合排行榜、按分数排序。
- `Stream` 更适合带消费组、可恢复消费的消息流；`Geo` 适合附近店铺这类地理位置检索。
- 我不会只背结构，而是会顺手讲项目例子，比如秒杀项目里用 `Set + Lua + Stream`，点评项目里 `Geo` 做附近店铺查询。

### 11. Redis 持久化你怎么讲？`RDB` 和 `AOF` 怎么选？

答题关键词：快照、追加日志、恢复速度、数据丢失窗口、混合持久化。

高分回答：

- `RDB` 是某个时间点的内存快照，优点是文件紧凑、恢复快，缺点是两次快照之间的数据可能丢失。
- `AOF` 是把写命令追加到日志里，数据更完整，但文件更大、恢复通常更慢。
- 真正在生产里通常不是二选一，而是根据业务对恢复速度和数据完整性的要求组合使用。
- 如果面试官继续追问，我会补一句：现在很多场景会考虑混合持久化，兼顾恢复速度和数据安全。

### 12. Redis 的过期删除和内存淘汰机制怎么讲？

答题关键词：惰性删除、定期删除、淘汰策略、热点数据。

高分回答：

- 过期键删除通常不是“到点立刻删”，而是惰性删除加定期删除配合。
- 惰性删除是在访问键时发现过期再删，定期删除是后台抽样扫描一部分过期键。
- 当内存不足时才会触发淘汰策略，比如 `noeviction`、`allkeys-lru`、`volatile-lru` 等。
- 我会强调：过期删除解决的是“键该不该继续存在”，淘汰策略解决的是“内存不够时先牺牲谁”。

### 13. 缓存穿透、击穿、雪崩分别是什么？你怎么给解决方案分层？

答题关键词：不存在数据、热点 Key、批量失效、空值缓存、布隆过滤器、互斥锁、逻辑过期。

高分回答：

- 缓存穿透是查询根本不存在的数据，请求直接打到数据库；常见方案是空值缓存或布隆过滤器。
- 缓存击穿是热点 Key 突然失效，大量请求同时回源；常见方案是互斥锁、逻辑过期、永不过期加异步重建。
- 缓存雪崩是大量 Key 同时过期或 Redis 整体不可用；常见方案是过期时间打散、多级缓存、限流降级、集群高可用。
- 高分回答的关键是别只背定义，要顺手说明“为什么热点 Key 更需要保护数据库”。

### 14. 为什么 Lua 能保证秒杀校验的原子性？它在 Redis 里是并发执行还是串行执行？

答题关键词：单线程执行模型、脚本整体执行、无命令插队。

高分回答：

- Redis 执行 Lua 脚本时，会把整段脚本当成一个原子操作来执行，中间不会被其他命令打断。
- 因为 Redis 的命令执行模型本身是单线程处理，所以多个请求触发 Lua 时，本质上是串行排队。
- 这就是为什么在秒杀里可以把“查库存、判重、扣减、入队”放进一个脚本里一次完成。
- 我会补一句：Lua 解决的是 Redis 侧并发竞争，不等于数据库层就完全不需要兜底。

### 15. 分布式锁常见坑有哪些？为什么解锁最好用 Lua？

答题关键词：误删他人锁、锁过期、可重入、续期、原子校验删除。

高分回答：

- 最经典的坑是“线程 A 的锁过期后，线程 B 拿到锁，A 再执行 `delete` 把 B 的锁删掉了”。
- 所以解锁不能简单 `get` 再 `del`，因为这两个动作之间也可能被并发打断。
- 用 Lua 的好处是能把“比较锁值是否是自己”与“删除锁”做成一个原子操作。
- 如果业务更复杂，我会直接用成熟实现，比如 Redisson，它还处理了可重入和续期问题。

### 16. Redis Stream 和传统消息队列比，有什么优缺点？

答题关键词：消费组、pending-list、轻量、生态、可靠性边界。

高分回答：

- `Stream` 的优点是和 Redis 生态天然结合，轻量、部署简单，而且支持消费组、消息确认、`pending-list` 恢复。
- 对中小型业务来说，它比“再引入一套 MQ 基础设施”更快落地。
- 缺点是消息能力、运维体系、死信治理、可观测性通常不如专业 MQ 完整。
- 所以我会回答：`Stream` 很适合当前项目体量的异步削峰，但如果链路继续复杂化，我会评估 RabbitMQ 或 Kafka。

### 17. MySQL 为什么用 B+ 树做索引？为什么不是普通二叉树或哈希？

答题关键词：多路平衡树、磁盘 IO、范围查询、叶子节点有序。

高分回答：

- B+ 树是多路平衡树，单个节点能放更多 key，所以树高更低，磁盘 IO 次数更少。
- 非叶子节点只存索引键和指针，不存完整数据，这让同一页能容纳更多索引项。
- 所有数据都在叶子节点，且叶子节点天然有序，范围查询和排序都更友好。
- 哈希索引适合等值查询，但不擅长范围查询、排序和最左前缀匹配，所以不适合作为通用索引结构。

### 18. 联合索引、最左匹配、覆盖索引你怎么讲？

答题关键词：有序性、查询条件顺序、回表、索引下推。

高分回答：

- 联合索引的本质是把多个字段按顺序组织在一棵 B+ 树里，所以顺序非常重要。
- 最左匹配的意思是查询要尽量从联合索引的最左列开始连续使用，才能最大化利用索引有序性。
- 覆盖索引是查询需要的字段都能直接从索引里拿到，不用再回表查主键数据，所以性能更好。
- 我会补一句：设计索引时不是字段越多越好，而是要围绕高频过滤、排序、回表成本一起看。

### 19. MVCC 是什么？你会怎么把它讲到 `ReadView`？

答题关键词：版本链、undo log、快照读、当前读、可见性。

高分回答：

- MVCC 可以理解成“一个数据行有多个版本，读请求按自己的视角选择可见版本”，这样读写不必完全互斥。
- 它主要依赖隐藏字段、`undo log` 形成的版本链，以及事务读时生成的 `ReadView`。
- 快照读会根据 `ReadView` 决定当前事务能看到哪个版本；当前读比如 `select ... for update`，则会读最新版本并加锁。
- 面试时我会强调：MVCC 解决的是并发读性能和一致性平衡问题，不是单独替代锁。

### 20. 事务隔离级别和并发异常怎么讲更顺？

答题关键词：脏读、不可重复读、幻读、RC、RR、Serializable。

高分回答：

- 我一般按“问题是什么，再看隔离级别怎么解决”来讲：脏读、不可重复读、幻读是三类典型异常。
- `Read Uncommitted` 最弱，可能脏读；`Read Committed` 解决脏读；`Repeatable Read` 解决不可重复读；`Serializable` 最强但并发最低。
- InnoDB 默认是 `Repeatable Read`，再结合 MVCC 和 next-key lock，对很多场景已经比较平衡。
- 高分点在于别把概念背成表格，而要讲出“隔离越强，一般并发越低”这个权衡。

### 21. `redo log`、`undo log`、`binlog` 分别做什么？两阶段提交为什么会被问到？

答题关键词：崩溃恢复、回滚、多版本、主从复制、数据一致性。

高分回答：

- `redo log` 主要保证崩溃恢复，属于 InnoDB 引擎层；`undo log` 主要用于回滚和 MVCC；`binlog` 是 Server 层的逻辑日志，常用于主从复制和数据恢复。
- 面试官问这三者，通常是想看你有没有把“事务提交”和“数据恢复链路”串起来理解。
- 两阶段提交的意义是让 `redo log` 和 `binlog` 在提交时尽量保持一致，避免出现一个成功、一个失败导致的数据不一致问题。

### 22. 如果一条 SQL 很慢，你会怎么排查和优化？

答题关键词：慢查询日志、`EXPLAIN`、索引、回表、N+1、SQL 重写。

高分回答：

- 我会先从慢查询日志或接口监控定位具体 SQL，再用 `EXPLAIN` 看执行计划。
- 重点看有没有全表扫描、索引失效、扫描行数过大、回表过多、排序或临时表等问题。
- 如果问题在 SQL 写法，我会考虑改查询条件、拆/并 SQL、避免函数操作索引列、优化分页或把 N+1 改成批量查询或 `JOIN`。
- 如果问题在索引，我会根据高频过滤列、排序列和选择性去补单列索引或联合索引。

## 二、异乡好居 CRM 实习深挖

### 23. 先不用讲技术，先把异乡好居这段业务讲清楚：你到底在做什么？

答题关键词：海外租房 CRM、中台后台 API、房源、商机、合作方、运营工具。

高分回答：

- 我这段实习做是海外租房 CRM 中台后台 API。

### 24. 你简历里写“房源同步链路建设”，这条链路具体指什么？

答题关键词：人工校对、查房库、房型回填、同步状态、留痕。

高分回答：

- 一部分是爬虫房源入库后的人工校对，核心是把爬虫侧供应商、房源、房型、房间和 CRM 里的实体重新对齐。
- 另一部分是把查房库房间数据汇总回房型，代码里有 `getUnitDataFromRoom` 先从房间侧聚合 `sub_block`、`floor`、`room_numbers`、`area/area_max`，再由 `saveUnitFromRoom` 批量写回 `Unit`。
- 再往后还有同步状态切换和字段级日志，保证人工修正不是黑盒操作。
- 所以这条链路不是一个接口，而是“校对 -> 状态切换 -> 批量回填 -> 审计留痕”的完整流程。

### 25. 你做的房源人工校对，为什么不是“改一条数据”这么简单？

答题关键词：多层映射、reference、一致性。

高分回答：

- 因为爬虫侧不是简单一条记录，代码里至少会带 `supplier_reference`、`house_reference`、`unit_reference`、`room_reference` 这几层标识。
- 一次人工校对可能会影响同一个 `spider_id` 下的多条匹配记录，甚至还要继续更新 CRM 主数据里的 `House.reference`、`Unit.reference` 和查房库房间标识。
- 如果只改当前一行，很容易出现匹配表改了，但主数据没回填、状态没切换，后续同步继续错的情况。
- 所以难点不在表单修改，而在“多层实体映射的一致性”。

### 26. 你在这条链路里具体处理了哪些“匹配、状态切换、批量回填”动作？

答题关键词：匹配表更新、状态切换、主数据回填。

高分回答：

- 在 `HouseSpiderService::saveMatchData()` 里，会先拿到当前记录的 `spider_id` 和各级 `reference`。
- 如果人工确认了 `supplier_id`、`house_id`、`unit_id`、`hcr_id`，服务会按这些 reference 批量更新对应匹配记录，并把默认状态切到可同步状态。
- 更新完匹配表后，还会继续回填业务主数据：房间侧写 `HouseCheckRoomsExtend.room_identifier`，房型侧写 `Unit.reference`，房源侧写 `House.spider_id` 和 `House.reference`。
- 这就是我简历里“房源/房型匹配、同步状态切换、事务性批量回填”的真实代码落点。

### 27. 为什么这里一定要用事务？如果不用事务会出什么问题？

答题关键词：部分成功、半更新、排障成本。

高分回答：

- 这类操作本质上都是多条数据一起修正，`HouseSpiderService::saveMatchData()` 和 `HouseCheckLibraryService::saveUnitFromRoom()` 都用了事务。
- 如果中间失败，很容易出现只更新了一部分 reference 或状态，剩下的数据还停留在旧关系上的“半成功”状态。
- 这种问题最难排查，因为页面上看起来像改过了，但后续同步、查房库展示、日志追踪会互相打架。
- 所以事务的价值不是“显得规范”，而是保证一次人工校对在业务语义上要么全成功、要么全失败。

### 28. 你们的字段级操作日志是怎么设计的？为什么这是个亮点？

答题关键词：主日志、季度分表、批次、操作类型。

高分回答：

- 这套日志不是简单写一条文本，而是结构化记录“哪个模型、哪条记录、哪个字段、旧值是什么、新值是什么”。
- `LogsCrmOperatedService::saveData()` 会先写主日志，带上 `model`、`record_id`、`controller`、`action`、`request_id`、`batch`、`user_id`、`type` 等元信息。
- 字段明细再写进按季度分表的字段日志表里，操作类型也明确区分 `U/C/D/R`，不只是更新。
- 它的亮点在于把日志从“留个记录”做成了“可以审计、可以排障、可以还原现场”的基础设施。

### 29. 这个字段级留痕真正解决了什么问题？

答题关键词：可追溯、批量操作、现场还原。

高分回答：

- 对人工校对这种批量动作来说，最怕的是过一段时间没人知道“谁改了什么、为什么改、改动影响到哪”。
- 这里的日志不仅记单字段差异，还能用同一个 `batch` 把 `LogsAutomanMatch`、`House`、`Unit`、`HouseCheckRoomsExtend` 这几处改动串起来。
- 这样一来，出了问题可以顺着批次把整次人工修正还原出来，而不是只看到零散几条 update。
- 所以它解决的核心是可追溯性，而不只是“方便看一眼”。

### 30. 如果不是字段真的变了，而是“查看了完整手机号/邮箱”这种动作，日志怎么记？

答题关键词：查看类日志、自定义消息、审计。

高分回答：

- 这种场景本质上是查看行为，不是字段修改，不适合硬套旧值新值 diff 模型。

- 所以像“查看了完整手机号”“查看了完整邮箱”这种动作，也可以按查看类日志留痕。
- 这样更符合 CRM 对敏感信息访问审计的真实需求。

### 31. 你简历里说接入了 AI workbench，基于文本和 URL 做房源信息抽取，这条链路怎么讲？

答题关键词：文本/URL 输入、schema 约束、标准化。

高分回答：

- 这条链路的重点不是“调模型”，而是把模型结果变成业务系统能接住的数据。

### 32. 为什么要支持“文本/URL”两种输入，还要额外做 schema 约束？

答题关键词：真实输入脏、输出可控、工程化。

高分回答：

- 真实运营输入很杂，有时是一段文案，有时是一条链接，也可能是多条链接混在一起。
- `AiWorkbenchService::parseUrls()` 专门处理逗号、中文逗号、换行这类情况，并做去重，说明这块考虑过真实输入质量。
- `expected_schema` 则是在输出侧给模型加约束，尽量把结果锁进业务真正需要的字段结构里。
- 所以这不是单纯做了个 AI 接口，而是在输入和输出两端都做了工程化约束。

### 33. 你怎么保证 AI 抽取结果能被业务使用，而不是“模型说抽到了就算成功”？

答题关键词：校验、标准化、入库链路。

高分回答：

- 代码里不会因为“模型返回了 JSON”就算成功，`parseExtractData()` 先检查 `room_types` 是否为空，再校验 `display_type` 和房型/房间数据是否匹配。

- 创建完成后还会异步触发房源价格状态更新，而不是把 AI 结果孤立地停在解析阶段。
- 所以我会把这块讲成“抽取 + 标准化 + 入业务体系”，而不是只说“抽取成功”。

### 34. 你写的运营工具接入，具体落到了哪些后台能力？

## 三、雅鉴生活志项目深挖

- 以下题目按简历里“秒杀防超卖和一人一单、消息队列异步处理、支付和关单并发、缓存优化”这几条来追问；回答再落到 `hm-dianping` 的真实代码。支付和关单并发因仓库里没有完整支付链路源码，回答按你的简历表述和通用工程设计组织。

### 41. 先整体介绍一下雅鉴生活志这个项目，你主要做了什么？

答题关键词：商家查询、优惠券、秒杀、高并发、缓存优化。

高分回答：

- 这是一个偏本地生活场景的项目，核心能力包括商家信息查询、优惠券和秒杀等业务。
- 我主要做了四块：秒杀防超卖和一人一单、把同步下单改成消息队列异步下单、支付和关单并发控制、缓存击穿和穿透治理。
- 如果面试官继续深挖，我会重点讲秒杀链路和缓存优化，因为这两块既能讲业务，也能讲并发控制和工程实现。

### 42. 你简历里写“秒杀防超卖和一人一单”，这条下单链路你怎么讲？

答题关键词：Redis 预热、Lua 原子校验、异步下单、数据库兜底。

高分回答：

- 秒杀开始前先把库存预热到 Redis。
- 用户请求进来后，先执行 Lua 脚本，在 Redis 侧一次性完成库存判断、一人一单判断、预扣库存和消息入队。
- 主线程只要拿到资格就快速返回，真正的订单创建由后台异步消费消息完成。
- 落库时再用 Redisson 锁、数据库查重和 `stock > 0` 条件更新做最后兜底，保证不超卖、不重复下单。

### 43. 为什么这里要用 Redis + Lua 做资格判断，而不是直接打数据库？

答题关键词：高并发削峰、快速失败、原子性。

高分回答：

- 秒杀场景的核心矛盾是瞬时并发高，如果每个请求都先进数据库查库存、查订单，数据库很容易先被打爆。
- Redis 更适合做高并发入口判断，Lua 又能把“查库存、查是否下单、扣库存、记录用户、发消息”做成一个原子操作。
- 代码里的 `seckill.lua` 就是这样做的：先查 `seckill:stock`，再查 `seckill:order`，最后再扣库存并写入异步消息。
- 所以 Redis + Lua 解决的是入口竞争问题，但它不是数据库的替代品，只是第一道门禁。

### 44. 你简历里写“用户下单后使用消息队列异步处理库存扣减和订单生成”，为什么要改成异步？

答题关键词：缩短响应时间、削峰、解耦主链路。

高分回答：

- 如果把资格校验、扣库存、创建订单都放在主线程同步做，接口响应时间会更长，而且数据库在高峰期更容易成为瓶颈。
- 异步化之后，主线程只负责快速判断资格并返回，订单创建由后台慢慢消费消息完成。
- 在代码里，Lua 脚本会把订单信息写进 `stream.orders`，后台单线程消费者再去读消息并创建订单。
- 这类设计的核心价值是削峰和降时延，而不是为了“炫技上 MQ”。

### 45. 既然你用了消息队列异步下单，那异常情况下怎么保证消息还能继续处理？

答题关键词：消费确认、异常恢复、可重试。

高分回答：

- 这里用的是 Redis Stream，不是简单 List。
- 消费端通过 `XREADGROUP` 读取消息，处理成功后再 `XACK` 确认；如果处理中抛异常，消息不会确认，就会留在 `pending-list`。
- 代码里专门有 `handlePendingList()` 去补拉这些未确认消息，避免服务抖动时消息直接丢失。
- 所以这条异步链路不是只有“发消息”，还考虑了异常恢复。

### 46. 既然入口已经做了资格校验，为什么落库阶段还要继续做并发兜底？

答题关键词：Redis 是门禁，数据库是最终事实，重复消费。

高分回答：

- 入口资格校验只解决了高并发入口问题，但订单最终还是要落数据库，所以数据库必须是最后一道事实校验。
- 后台消费可能遇到重复消费、重试、服务重启等情况，只靠入口判断不够稳。
- 所以代码里又加了用户粒度的 Redisson 锁、按 `user_id + voucher_id` 查重，以及 `stock > 0` 条件更新库存。
- 这体现的是多层防线思路，而不是迷信某一层一定百分百可靠。

### 47. 这种高并发下单场景里，订单 ID 你会怎么设计？

答题关键词：全局唯一、趋势递增、链路追踪。

高分回答：

- 这类场景不太适合只靠数据库自增，因为并发高时数据库会成为瓶颈，而且异步链路里也希望主线程先拿到订单 ID。
- 当前代码里用的是 `RedisIdWorker`，思路是“时间戳差值左移 + 当天自增序列号”，兼顾全局唯一和趋势递增。
- 这样用户在入口就能拿到订单 ID，后续消息重试和链路排查也都能围绕同一个业务 ID 做。
- 所以重点不是类名，而是它满足了高并发下“唯一、可追踪、性能可接受”这几个目标。

### 48. 你简历里写“逻辑过期方案防热点 Key 缓存击穿”，这个方案怎么讲？

答题关键词：先返回旧值、异步重建、保护数据库。

高分回答：

- 逻辑过期的核心不是把 Key 真删掉，而是在缓存值里额外存一个逻辑过期时间。
- 代码里 `CacheClient.setWithLogicalExpire()` 会把真实数据和 `expireTime` 一起写入 Redis。
- 查询时如果发现逻辑过期了，不是立刻让所有请求回源，而是先返回旧值，同时尝试拿锁，由后台线程异步重建缓存。
- 这种方案特别适合热点数据，因为它优先保护数据库和接口可用性。

### 49. 你简历里写“缓存空值方案解决缓存穿透”，为什么这个方案有效？

答题关键词：不存在数据、短期缓存、减少重复回源。

高分回答：

- 缓存穿透的典型场景是用户一直查根本不存在的数据，请求每次都打到数据库。
- `CacheClient.queryWithPassThrough()` 的做法是：如果数据库查不到，就往 Redis 写一个带短 TTL 的空值。
- 后续同样的不存在请求会先命中这个空值，直接返回，不再继续打数据库。
- 它的本质是把“不存在”也变成一种可缓存结果，从而保护数据库。

### 50. 如果业务数据更新了，你的缓存方案怎么和写操作配合？

答题关键词：先改库再删缓存、最终一致性。

高分回答：

- 当前项目采用的是很常见的“先更新数据库，再删除缓存”。
- `ShopServiceImpl.update()` 里就是先 `updateById(shop)`，再删除对应的 `cache:shop:` Key。
- 这样做是因为数据库通常是最终事实来源，如果先删缓存再改库，窗口期里旧数据可能被重新写回缓存。
- 如果要继续增强，我会考虑失败重试、异步补偿和告警，把最终一致性做得更稳。

### 51. 你简历里写“支付和关单的并发用了乐观锁”，面试官真追问你会怎么答？

答题关键词：状态机、条件更新、幂等。

高分回答：

- 这个场景本质上是两个并发动作在争抢同一订单的状态修改权，比如一个想把订单从“待支付”改成“已支付”，另一个想改成“已关闭”。
- 乐观锁的常见做法是带旧状态条件更新，例如 `where status = WAIT_PAY`，谁先成功谁拿到修改权。
- 另一个请求如果更新 0 行，就说明状态已经被别人改过了，这时按幂等逻辑返回，而不是继续强行覆盖。
- 我会强调：核心不是背“乐观锁”三个字，而是把订单状态机和并发冲突处理规则讲清楚。

### 52. 如果把这个项目继续往生产环境推进，你会优先补哪些工程措施？

答题关键词：唯一索引、事务、消息治理、监控。

高分回答：

- 我会先补数据库层的唯一索引，比如 `(user_id, voucher_id)`，把一人一单再压实一层。
- 第二，订单创建最好放进显式事务里，把查重、扣库存、落单作为原子数据库事务执行。
- 第三，异步链路要补齐消费组初始化、消息确认监控、异常告警、死信和重试治理。
- 最后再补压测、链路观测和优雅停机，这样它才更接近真正可上线的高并发方案。

## 四、扫地机器人智能客服 Agent 项目深挖

- 以下题目按简历里“RAG + ReAct Agent、知识问答、故障排查、维护保养、天气适配、个人使用报告生成、工具调用、动态提示词机制”这些表述来追问；回答再落到 Agent 项目的真实代码。

### 53. 先整体介绍一下你的 Agent 项目，最好一句话就能让面试官听懂。

答题关键词：RAG + ReAct、智能客服、工具调用、报告生成。

高分回答：

- 我做的是一个面向扫地机器人场景的智能客服原型，核心架构是 `RAG + ReAct Agent`。
- RAG 负责补充专业知识，ReAct 负责按任务需要调用天气、位置、用户记录等工具。
- 它覆盖的不是单一问答，而是知识问答、故障排查、维护保养、天气适配和个人使用报告生成这几类场景。

### 54. 你简历里写基于 `RAG + ReAct Agent` 构建系统，为什么要把这两者结合？

答题关键词：知识边界、工具边界、减少幻觉。

高分回答：

- 因为这个项目里既有“知识密集型问题”，也有“必须访问外部信息的问题”，只靠一个大 prompt 很难把两类问题都稳定接住。
- RAG 解决的是知识边界问题，让模型先拿到产品选购、故障排查、保养知识再回答。
- ReAct 解决的是动作边界问题，比如先拿天气、先拿用户位置、先拿外部使用记录，再决定下一步回答。
- 我会把它总结成：RAG 让它知道，Agent 让它会做。

### 55. 你的知识库是怎么构建的？

答题关键词：TXT/PDF、切片、向量化、Chroma。

高分回答：

- 知识库数据来自 `txt/pdf` 文件，先通过 loader 读成 `Document`。
- 然后用 `RecursiveCharacterTextSplitter` 做切片，再把切好的文档写入 Chroma 向量库。
- 查询时会先从向量库里召回相关文档，再把资料和用户问题一起交给模型总结。
- 所以它不是单纯“把文档塞给模型”，而是走了一条完整的检索增强链路。

### 56. 为什么你还专门做了知识库文件去重？

答题关键词：增量导入、避免重复召回、工程化。

高分回答：

- 因为知识库更新通常不是一次性的，而是持续增量导入。
- 当前代码里会给文件算 MD5，并把已经处理过的 MD5 写到 `md5.text`，下次加载时先检查是否已导入。
- 这样可以避免同一份资料重复入库，导致向量库膨胀、检索结果重复。
- 这一步虽然小，但很工程化，因为它考虑了知识库的长期维护。

### 57. 你这里的切片参数是怎么权衡的？

答题关键词：`chunk_size`、`overlap`、语义完整性、召回粒度。

高分回答：

- 当前配置里 `chunk_size` 是 200，`chunk_overlap` 是 20。
- 我的理解是：块太小会把语义切碎，块太大又会把无关内容一起带进上下文，影响模型聚焦。
- overlap 的作用是避免边界信息被截断，比如一个故障处理步骤刚好跨在两个分片之间。
- 这组参数不是绝对最优，而是一个比较稳妥的原型起点，后续应结合召回效果继续调。

### 58. 为什么你的技术选型是 `Chroma + DashScope Embeddings + Qwen3-Max`？

答题关键词：轻量、中文能力、原型效率。

高分回答：

- `Chroma` 比较适合本地原型和轻量级向量检索，部署和接入成本低。
- `DashScope Embeddings` 和 `Qwen3-Max` 的组合对中文知识库和中文问答场景比较自然，适合这个项目的数据特征。
- 我的选型思路是先快速把原型跑通，再根据效果和成本决定是否替换底层组件。
- 所以我会强调选型逻辑，而不是只背技术名词。

### 59. 你的 RAG 检索增强链路是怎么工作的？

答题关键词：检索、拼接上下文、受约束总结。

高分回答：

- 代码里会先从向量库检索 top-k 文档，再把每段资料和元数据拼成上下文字符串。
- 然后把用户问题和资料上下文一起填进 `rag_summarize` 提示词，再交给模型总结。
- 提示词里明确要求“只能基于参考资料回答，不编造、不扩写”，这是在压制幻觉。
- 所以它不是通用聊天，而是一个带证据约束的知识回答链路。

### 60. 你的 Agent 工具是怎么设计的？为什么不是把所有能力塞进一个大 prompt？

答题关键词：工具分层、职责边界、可组合。

高分回答：

- 我的工具可以按职责分成几类：知识检索类、环境信息类、身份与时间类、外部记录类。
- 比如知识检索会走 `rag_summarize`，环境信息有天气和位置，报告场景还会读取外部使用记录。
- 这样做的好处是边界清晰，模型知道什么时候该检索知识、什么时候该取外部事实，而不是把所有任务都压进一个超级 prompt。
- 我会强调：好工具设计不是工具越多越好，而是边界清晰、参数简单、可组合。

### 61. 你简历里写覆盖“天气适配”场景，这类问题为什么要做成工具调用？

答题关键词：实时性、知识与事实分离。

高分回答：

- 因为天气是实时变化的外部事实，不适合静态固化在知识库里。
- 知识库适合放“湿度高时怎么保养”这类长期稳定知识，当前天气则应该由工具实时提供。
- 代码里的思路也是先拿用户位置，再拿天气，再结合 RAG 返回的保养知识生成回答。
- 这正好体现了 RAG 和工具的分工：知识回答原则，工具回答当前状态。

### 62. 你简历里写支持“个人使用报告生成”，这个场景为什么不能按普通问答处理？

答题关键词：结构化输入、固定流程、报告输出。

高分回答：

- 报告生成不是开放式闲聊，而是需要一组完整输入：用户是谁、哪个月、有哪些外部使用记录。
- 如果按普通问答来做，模型很容易漏掉某些前置条件，最后直接编一份“像报告的东西”出来。
- 所以这个场景更像“结构化数据 + 语言生成”的组合，而不是单轮客服问答。
- 这也是为什么它需要单独的流程约束和提示词设计。

### 64. 为什么报告生成前要先补齐用户、月份这类上下文信息？

答题关键词：输入完整、避免漏步骤、流程约束。

高分回答：

- 因为报告生成依赖明确的查询条件，没有用户和月份，就没法准确取到那一段使用记录。
- 当前 prompt 里就把这条流程写成了强约束：先拿用户 ID，再拿月份，再切换到报告场景，再查外部记录。
- 这样做的目的是减少模型漏步骤的概率，保证报告输入完整。
- 我会把它理解成给 Agent 加了一层最小流程编排规范。

### 65. 你这里的外部使用记录是怎么组织的？为什么这样设计？

答题关键词：用户 ID、月份、特征、效率、耗材、对比。

高分回答：

- 外部数据来自 `records.csv`，字段包括用户 ID、特征、清洁效率、耗材、对比和时间。
- 加载后会整理成“用户 ID -> 月份 -> 指标内容”的层级结构，方便按用户和月份读取。
- 这样的结构已经足够支撑报告生成场景，也比较贴近真实报表系统常见的查询维度。
- 所以重点不是 CSV 本身，而是它把报告生成从纯语言问题变成了结构化数据问题。

### 63. 你简历里还写了“动态提示词机制”，它解决了什么问题？

答题关键词：场景切换、避免一套 prompt 包打天下。

高分回答：

- 因为普通客服问答和报告生成的写作目标完全不同。
- 当前代码里会在报告场景打上上下文标记，再通过中间件动态切换到报告专用 prompt，而不是一直复用同一套系统提示词。
- 这样做能让不同场景的提示词职责更清晰，也更容易扩展，而不是让一个超级 prompt 越写越臃肿。
- 所以动态提示词机制解决的核心是多场景切换，而不是单纯换个文案。

### 66. 你的前端交互怎么做的？为什么选 `Streamlit`？

答题关键词：轻量原型、会话状态、流式展示。

高分回答：

- 前端入口用的是 `Streamlit`，主要负责聊天 UI、会话状态保存和流式输出展示。
- 用户输入后会调用 Agent 的流式执行接口，再把返回的 chunk 做逐字展示，营造实时响应的体验。
- `Streamlit` 的优势是搭原型很快，特别适合这种需要快速验证 Agent 交互效果的项目。
- 对我来说它不是终态前端，而是一个高效验证产品形态的工具。

### 67. 这个 Agent 原型现在最大的不足是什么？

答题关键词：原型能力、mock 工具、评测不足。

高分回答：

- 我会主动说它现在还是一个原型，几个工具返回的是模拟数据，比如天气、位置、用户 ID、月份都是 mock 或随机返回。
- 检索侧也还没有做 rerank、来源引用、召回评估和离线基准测试。
- 如果要上线，还要补真实外部接口、权限控制、监控告警、答案评测和成本控制。
- 这种回答能体现你知道“能跑”和“可上线”之间差了哪些工程工作。

### 68. 如果要提升这套 Agent 的回答准确率，你优先改哪几件事？

答题关键词：知识库质量、检索质量、工具路由质量。

高分回答：

- 第一，我会先治理知识库内容，清理重复、冲突和低质量文本，因为垃圾进垃圾出。
- 第二，优化检索，比如调 `k`、调 chunk、做 rerank、增加来源引用和召回评估。
- 第三，优化工具路由和场景识别，减少模型在“该检索还是该调用工具”上的误判。
- 准确率通常不是靠单点优化，而是“数据、检索、路由、提示词”一起调。

### 69. 如果让我评估这套 Agent，你会看哪些指标？

答题关键词：召回、忠实性、工具成功率、延迟、成本。

高分回答：

- 检索层我会看召回命中率、`Recall@K` 或人工抽样相关性。
- 生成层我会看答案忠实性，重点看有没有脱离资料乱答。
- 工具层我会看工具调用成功率、错误率和平均调用次数。
- 工程层我会看端到端延迟、单次会话成本、用户满意度和问题闭环率。

### 70. 如果把这套原型推进到生产，你会怎么规划？

答题关键词：真实工具、可观测、评测闭环、安全。

高分回答：

- 第一阶段先把 mock 工具替换成真实接口，并补鉴权、超时、重试和熔断。
- 第二阶段补全可观测性，包括日志、trace、答案与工具调用记录、失败告警。
- 第三阶段建立评测闭环，做知识库更新流程、离线测试集、线上反馈收集和版本回归。
- 最后再看成本优化，比如缓存常见问答、控制工具调用次数、做分层模型路由。
