### **【Q2】ArrayList 和 LinkedList 的区别？**
高分回答（示例）：
底层结构上，ArrayList 基于动态数组，LinkedList 基于双向链表。  
复杂度上，ArrayList 随机访问是 O(1)，中间插入/删除通常 O(n)；LinkedList 定位节点 O(n)，但在已定位节点处插入删除 O(1)。  
工程上，ArrayList 更符合 CPU 缓存局部性，综合性能通常更好，LinkedList 只有在“频繁头尾插删且很少随机访问”的场景才可能占优。  
结合项目，“雅鉴生活志”里高频数据更多在 Redis/DB，不在 JVM 内存链表上做复杂结构操作，所以集合选择通常优先 ArrayList。

### **【Q4】讲一下 Java 类加载/初始化流程。**
高分回答（示例）：
类加载主流程：加载（Loading）→ 链接（Linking：验证、准备、解析）→ 初始化（Initialization）→ 使用 → 卸载。  
初始化阶段核心是执行 `<clinit>`，即静态变量显式赋值和静态代码块。  
高分点：强调“加载”和“初始化”不是一回事，很多题目就在考触发初始化的边界条件。

### 🌟什么是类加载，什么是类初始化？

- 类加载：是“把类弄进 JVM，并做好基础准备”
- 类初始化：是“真正执行这个类的静态逻辑”

#### 🌟例子

```java
class A {    
  static int x = 10;    
  static {        
    System.out.println("A init");    
  } 
} 
```

- 加载时：JVM 先把 A 的字节码读进来，完成验证、准备、解析
- 准备阶段：x 先是默认值 0
- 初始化阶段：才会执行 x = 10 和静态代码块，打印 A init

### **【Q5】什么情况下会触发类初始化？**
高分回答（示例）：
**主动使用会触发**，常见包括：  

1) `new` 创建对象；  
2) 访问或赋值该类的静态变量（非 `final` 编译期常量）；  
3) 调用该类静态方法；  
4) 反射主动使用；  
5) 初始化子类前先初始化父类；  
6) 启动类（含 `main`）初始化。  
不会触发的典型场景：访问编译期常量、创建“该类数组类型”。

### **【Q6】在另一个类里调用某个静态字段，会触发该类初始化吗？**
高分回答（示例）：
要看字段是不是“编译期常量”。  
如果是 `static final` 且值可在**编译期**确定，常量会被调用方常量池内联，通常不触发定义类初始化；  
如果是普通静态字段，通常会触发。  
回答这题最好明确“常量折叠/内联”这个关键词。

### 🌟什么是编译期常量

1. static final
2. 值在编译阶段就能确定
3. 一般是基本类型或字符串字面量常量

#### 🌟编译期常量VS运行时常量

- 编译期常量：编译阶段就能确定值，编译器可以直接把值内联到使用方代码里
- 运行时常量：编译阶段不能确定，必须等程序运行时才能得到值

#### 🌟例子

```java
class A {
    static {
        System.out.println("A init");
    }

    public static final int X = 10;

}
```

```java
class B {
    public static void main(String[] args) {
        System.out.println(A.X);
    }
}
```

这里很多情况下输出只有：

```
10
```

不会输出：

```
A init
```

原因是 10 在编译阶段就已经确定了，编译器可能直接把 A.X 替换成字面量 10。
运行时 B 不需要真的去“主动使用” A，所以 A 不初始化。

这就是“在另一个类里调用某个静态字段，不一定触发类初始化”的原因。

### 🌟静态变量==静态字段

### **【Q7】`new User[10]` 会初始化 User 类吗？**
高分回答（示例）：因为 new User[10] 创建的不是 User 对象，而是 User[] 数组对象。

JVM 只是在内存里开了一块能放 10 个 User 引用的位置，这时候数组里的每个元素默认都是 null，并没有真正去创建任何一个 User 实例，也就没有“主动使用” User 类，所以不会触发 User 的初始化。

你可以看这个例子：

```java
class User {    
  static {        
    System.out.println("User init");    
  } 
} 
public class Test {    
  public static void main(String[] args) {        
    User[] arr = new User[10];        
    System.out.println(arr.length);    
  } 
} 
```

输出通常只有：

```
10 
```

不会打印：

```
User init 
```

因为这里发生的是：

1. 创建了一个数组对象 User[]
2. 数组元素类型是 User
3. 但并没有创建 User 实例
4. 所以 User 类不需要初始化

你可以把它理解成：

- new User()：真的要用 User 这个类创建对象，所以要先初始化 User
- new User[10]：只是创建“装 User 引用的数组壳子”，还没真正用到 User 对象，所以不初始化 User

### **【Q11】线程生命周期是什么？**
高分回答（示例）：
`NEW` → `RUNNABLE` → `BLOCKED / WAITING / TIMED_WAITING` → `TERMINATED`。  
高分点：区分 Java 层 `RUNNABLE`（含就绪和运行）与 OS 调度态；说明 `wait/join/park/sleep` 对状态的影响。

```
NEW
 -> start()
RUNNABLE
 -> 抢不到 synchronized 锁
BLOCKED
 -> 抢到锁后回到
RUNNABLE
 -> wait()/join()/park()
WAITING
 -> 被唤醒后回到
RUNNABLE
 -> sleep()/wait(timeout)/join(timeout)
TIMED_WAITING
 -> 超时或唤醒后回到
RUNNABLE
 -> run() 执行结束
TERMINATED

```

### 🌟单机锁VS分布式锁

- 单机锁：只在一个 JVM / 一个进程内部生效
- 分布式锁：在多个 JVM、多个服务实例之间生效

#### 一、单机锁是什么

比如：

- synchronized
- ReentrantLock

它们锁住的是当前进程里的线程。

举个例子：

你的服务只部署了 1 台机器，或者虽然有多线程，但都在同一个 JVM 里。
这时用 synchronized / ReentrantLock 就能保证：

“同一时刻只有一个线程进入临界区”

但它只能管本机线程。

如果服务部署成 3 个实例：

- 实例 A 有自己的锁
- 实例 B 有自己的锁
- 实例 C 有自己的锁

这三个锁彼此不知道对方的存在，所以不能实现全局互斥。

#### 二、分布式锁是什么

分布式锁要解决的问题是：

“多个服务实例、多个 JVM、甚至多台机器上的线程，怎么共同竞争同一把锁”

它通常依赖一个“大家都能访问到的共享存储/协调组件”，比如：

- Redis
- ZooKeeper
- etcd
- 数据库

常见做法比如 Redis 分布式锁：

```
SET lock_key unique_value NX PX 30000 
```

含义是：

- 只有 key 不存在时才能加锁
- 设置过期时间，防止死锁

这样不管请求打到哪台机器，只要它们都去 Redis 竞争同一个 lock_key，就能实现“全局只有一个成功”。

### **【Q14】给表建索引要考虑哪些因素？**

### **【Q15】建了索引查询仍然慢，怎么排查？**
高分回答（示例）：
我的排查步骤是：  

1) 先看慢查询日志定位 SQL；  
2) `EXPLAIN` 看 `type/key/rows/Extra`，判断是否走索引、是否回表/临时表/文件排序；  
3) 检查是否有索引失效（函数、隐式类型转换、范围条件截断）；  
4) 根据 where/join/order by 重建联合索引；  
5) 必要时做 SQL 重写、分页优化、冷热数据分层。  
  高分点在于“步骤化”和“可落地”。

### 🌟`EXPLAIN` 看 `type/key/rows/Extra`

- type：访问类型，判断 SQL 扫描效率高不高

  常见从好到差大致可以这么记：

  - system
  - const 通过主键或唯一索引，并且只匹配一条记录。
  - eq_ref
  - ref 使用普通索引或非唯一索引做等值查询。
  - range 范围查询。
  - index 扫描整个索引树 虽然走了索引，但其实是“全索引扫描”
  - ALL 全表扫描

- key：实际用了哪个索引

- rows：MySQL 预估要扫描多少行

- Extra：额外信息，能看出有没有回表、临时表、文件排序等风险

### 🌟什么是回表

在 InnoDB 里：

- 主键索引的叶子节点，存的是整行数据
- 二级索引的叶子节点，存的是“索引列值 + 主键值”

所以如果你先走了二级索引，但查询需要的列不在这个二级索引里，MySQL 就要先从二级索引找到主键，再根据主键去主键索引里把整行数据查出来。

这个“再去主键索引查一次”的过程，就叫回表。

### 🌟什么是临时表

临时表指 MySQL 在执行 SQL 时，为了处理中间结果额外创建的表。

比如：

```mysql
SELECT age, COUNT(*) FROM user GROUP BY age; 
```

如果不能直接利用索引高效完成分组，MySQL 可能先生成一个临时表来存中间分组结果。

### 风险

- 临时表本身有开销
- 数据量小时可能在内存
- 数据量大时可能落磁盘，性能会更差

所以 Using temporary 通常说明 SQL 还有优化空间。

### 🌟什么是文件排序

Using filesort 不是说“一定用文件”，而是说：

“MySQL 不能按索引顺序直接拿到结果，必须额外做排序。”

例如：

```
SELECT * FROM user WHERE age = 20 ORDER BY score; 
```

如果没有 (age, score) 这样的合适索引，MySQL 就可能先筛选出 age=20 的记录，再自己排序。

这就是 filesort。

### **【Q17】执行 `alter table` 时数据库一般做哪些操作？**
高分回答（示例）：
看 DDL 类型与版本能力（MySQL 5.6/5.7/8.0 的 `ALGORITHM=INSTANT/INPLACE/COPY` 差异）：  
可能涉及元数据锁（MDL）、创建临时表/重建表、回填数据、重建索引、切换新旧表、提交元数据变更。  
高分补充：线上变更要考虑锁等待和阻塞风险，必要时用 gh-ost / pt-osc 做在线变更。

**1. 解析 SQL，检查元数据**

数据库先解析你的 ALTER TABLE 语句，确认：

- 要改哪张表
- 改什么结构
- 语法是否合法
- 表、列、索引是否存在
- 当前变更是否允许执行

例如你要加一个列，它先得知道表结构里有没有同名列。

**2. 获取元数据锁（MDL）**

执行 ALTER TABLE 时，MySQL 会对表加元数据锁。

这个锁的作用是：
在修改表结构期间，防止别的会话同时对这张表做不兼容的结构变更，保证一致性。

这是线上特别重要的一点，因为：

- 如果有长事务一直占着表
- ALTER TABLE 可能拿不到锁，被阻塞
- 反过来，ALTER TABLE 拿到锁后，也可能影响后续查询或写入

所以很多线上 DDL 慢，不一定是“改表本身慢”，而可能是“等锁慢”。

**3. 判断采用哪种 DDL 算法**

MySQL 会根据变更类型和版本能力，决定这次 DDL 是：

- INSTANT
- INPLACE
- COPY

这是面试高分点。

**INSTANT**

只改元数据，不重建数据页，速度最快。
例如某些“加列到末尾”的操作，在较新版本 MySQL 里可以做到瞬时完成。

**INPLACE**

不需要整张表复制，但可能仍需要重建部分数据结构或索引。
比 COPY 好，但也不一定完全无影响。

**COPY**

最重的一种方式。
通常会创建新表，把旧表数据一行行拷贝过去，再切换表。
这种开销最大，对大表风险也最高。

所以你可以理解为：

- 能只改字典就只改字典
- 不行就尽量原地处理
- 再不行才整表拷贝

**4. 可能创建临时表/新表**

如果当前变更不能直接在原表上完成，数据库可能会：

1. 创建一张新表，结构是修改后的结构
2. 把旧表数据拷贝过去
3. 重建相关索引
4. 完成后切换新旧表

这就是很多人说的“重建表”。

常见容易触发表重建的操作有：

- 修改列类型
- 调整列顺序
- 某些加减列
- 修改主键
- 某些字符集变更

**5. 回填数据**

如果涉及新表重建或数据格式变更，MySQL 需要把旧表数据搬到新结构里。

例如：

```
ALTER TABLE user MODIFY COLUMN name VARCHAR(128); 
```

这时数据库可能要把原有数据按新的列定义重新组织。

如果表很大，这一步就可能很慢。

**6. 重建索引**

如果表结构变化影响索引，数据库可能需要重建索引。

例如：

- 新增索引
- 删除索引
- 修改被索引列类型
- 重建表时顺带重建所有相关索引

索引重建本身也是重活，尤其大表更明显。

**7. 更新数据字典 / 元数据**

结构改完以后，MySQL 要更新系统里的表定义信息，比如：

- 列定义
- 索引定义
- 主键信息
- 表版本
- 统计信息

这一步相当于告诉数据库：
“从现在开始，这张表的新结构是这个。”

**8. 切换新旧表并提交**

如果用了重建表方式，最后会做一次切换：

- 新表替换旧表
- 提交元数据变更
- 释放锁

这一步完成后，外部看到的就是新结构。

**9. 释放锁**

DDL 完成后，数据库释放持有的元数据锁，其他会话才能继续正常访问。

### 🌟什么是alter table 

ALTER TABLE 就是修改表定义，不是改表里的某一行数据，而是改表结构。

```mysql
ALTER TABLE user ADD COLUMN age INT;
ALTER TABLE user DROP COLUMN age;
ALTER TABLE user MODIFY COLUMN name VARCHAR(64);//修改列类型
ALTER TABLE user ADD INDEX idx_age(age);
ALTER TABLE user DROP INDEX idx_age;
ALTER TABLE user RENAME COLUMN old_name TO new_name;
```

### 🌟什么是元数据

数据库里的真正业务数据是这样的：

```
user 表里有一行：id=1, name='Tom', age=20 
```

这是“数据”。

那下面这些信息不是业务数据本身，而是“描述这些数据怎么存、怎么组织、怎么约束”的信息，这就是元数据：

- 有哪些库、哪些表
- 表里有哪些列
- 每列的数据类型是什么
- 哪一列是主键
- 建了哪些索引
- 默认值是什么
- 是否允许为 NULL
- 字符集、排序规则是什么
- 表属于哪个存储引擎
- 视图、触发器、约束定义是什么

所以元数据本质上是：

“关于数据库对象结构和属性的信息”。

### 🌟什么是数据字典

数据字典就是数据库内部用来保存和维护这些元数据的一套系统信息。

你可以把它理解成数据库的“目录”和“说明书”。

比如数据库要执行：

```
SELECT * FROM user; 
```

它首先得知道：

- user 这张表存不存在
- 表结构是什么
- 哪些列在哪
- 主键和索引是什么
- 权限是否允许访问

这些信息都来自数据字典。

所以数据字典的作用就是：
让数据库知道“这张表长什么样、该怎么处理”。

### **【Q18】你用消息队列做了哪些事情？**
高分回答（结合当前项目实际）：
在“雅鉴生活志”这个代码版本里，异步链路是 **Redis Stream**，不是 RabbitMQ：  
用户请求进入后先执行 Lua 完成资格校验与预扣库存，再 `XADD` 到 `stream.orders`；后台单线程消费者 `XREADGROUP` 拉取并创建订单，成功后 `XACK`。  
这样把下单主链路从“同步落库”改为“快速返回 + 异步落库”，显著降低接口 RT。  
如果你简历写 RabbitMQ，就必须明确“哪一段代码、哪个交换机/队列、重试和死信怎么做”，否则会被追问击穿。

### **【Q19】为什么要用消息队列？**
高分回答（示例）：
核心价值是三点：解耦、削峰、异步。  
在秒杀场景下，异步化最直接：前台快速给用户反馈，后台平滑消费，防止数据库被瞬时流量打穿。  
结合项目：Lua 负责“快且准”的资格判定，Stream 负责“慢且稳”的订单处理，职责分离后系统稳定性更高。

### **【Q20】你主要体现了消息队列哪个能力？**
高分回答（示例）：
主要体现“异步 + 削峰”。  
在峰值流量时，请求线程不做完整下单事务，只做轻量校验后入流；真正的落库由消费者按能力处理。  
这比同步链路更能保护数据库和下游服务。

### **【Q21】为什么要异步？主线程是做什么的？请举场景。**
高分回答（示例）：
异步的本质是把“用户强感知路径”和“可延后任务”拆开。  
主线程应优先完成**高优先级动作**（参数校验、资格判断、快速响应）；耗时任务（如下单落库、通知）交给异步通道。  
秒杀场景里，用户更关心“是否抢到”，不需要等待完整订单后处理全部完成。

### **【Q22】你说用 Redis 分布式锁解决一人一单，具体怎么做？**
高分回答（结合项目）：
我做了三层防线：  
1) Lua 原子校验：库存 > 0 且用户未下单，直接在 Redis 侧判定；  
2) 消费端 Redisson 按用户加锁，串行化同一用户下单；  
3) DB 再校验一次 `user_id + voucher_id` 是否已存在，并通过条件更新扣库存。  
这能同时防超卖与重复下单，并且兼顾吞吐。

### **【Q23】订单号怎么生成？在发送端还是消费端生成？**
高分回答（结合项目）：
本项目在**发送前**就用 `RedisIdWorker` 生成订单号，并作为字段写入 Stream。  
ID 结构是时间戳差值左移 + 当日自增序列（Redis `INCR`），兼顾趋势递增、全局唯一、低冲突。  
高分点：强调“消息重试时订单号不能重生”，要用同一业务主键贯穿全链路。

### **【Q24】如果消费失败并重试，会不会重复创建订单？怎么优化幂等？**
高分回答（结合项目 + 改进方案）：
这是关键问题：消息系统通常至少一次投递，消费端必须幂等。  
当前代码已把订单 ID 在入流前生成，这比“消费时生成”更安全；但仅靠应用层查询仍有并发窗口。  
建议进一步做两件事：  

1) 数据库建立唯一约束 `unique(user_id, voucher_id)`（或以业务单号唯一）；  
2) 消费时“先判重后落库”，对唯一冲突视为幂等成功并 ACK。  
这样即使重复投递，也不会生成多单。

### **【Q26】讲一下 Cache Aside 模式。**
高分回答（结合项目）：
读流程：先查缓存，未命中再查库并回填；  
写流程：先更新数据库，再删除缓存。  
“雅鉴生活志”里店铺更新就是这个策略：`updateById` 后删除 `cache:shop:{id}`，避免脏缓存长期存在。

### **【Q27】为什么更新数据库后删缓存，而不是直接更新缓存？**
高分回答（示例）：
删缓存优于改缓存有三个原因：  
1) 并发写时“改缓存”容易发生覆盖回退（新值被旧写覆盖）；  
2) 缓存字段可能比数据库复杂，更新路径容易漏字段；  
3) 热点不稳定时，删缓存让下一次读按需回源，整体更稳。  
结合项目：已经采用“先写库后删缓存”，并可进一步加延迟双删/消息补偿提升一致性上限。

### **【Q28】你知道二阶段事务消息吗？**
高分回答（示例）：
知道，它是解决“本地事务与消息发送原子性”问题的方案。  
流程通常是：先发半消息（prepare）→ 执行本地事务 → 提交/回滚消息；若状态不明，由 MQ 回查本地事务状态。  
适用场景是跨系统最终一致性，不等价于本地 ACID 事务。  
在当前项目里未实现这一套，但可作为“删除缓存失败后异步补偿”或“订单与下游状态同步”的升级方向。

二阶段事务消息 = 先发一条暂时不可投递的半消息，等本地事务执行成功后再提交消息；如果本地事务失败，就回滚消息。

**第一阶段**

先发一条“半消息”或者叫“预备消息”

特点是：

- MQ 先把消息存下来
- 但这条消息对消费者不可见
- 消费者此时还不能消费

**第二阶段**

执行本地事务，然后根据结果决定：

- 本地事务成功：提交消息，让消息对消费者可见
- 本地事务失败：回滚消息，删除或丢弃这条消息

所以叫二阶段，本质上就是：

1. 先预留消息
2. 再确认提交还是回滚

### **【Q30】算法题：最长公共子序列（LCS）怎么做？动态规划思路？**
高分回答（示例）：
定义 `dp[i][j]`：`text1[0..i-1]` 与 `text2[0..j-1]` 的 LCS 长度。  
转移：  
- 若 `text1[i-1] == text2[j-1]`，`dp[i][j] = dp[i-1][j-1] + 1`；  
- 否则 `dp[i][j] = max(dp[i-1][j], dp[i][j-1])`。  
初始化第 0 行/列为 0，答案是 `dp[m][n]`，时间 O(mn)，空间 O(mn)（可压缩到 O(n)）。  
面试时要先给状态定义再给转移，这是关键得分点。
