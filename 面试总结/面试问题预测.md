## 一、Java 基础与集合类

### **【高频问题】ArrayList 和 LinkedList 的区别？**
高分回答：  
**底层结构**：ArrayList 基于动态数组，容量不足时触发扩容；LinkedList 基于双向链表，每个节点含 prev/next 指针。**复杂度**：ArrayList 随机访问 O(1)，中间插入删除需移动元素 O(n)；LinkedList 查找需遍历 O(n)，在已定位节点处插入/删除仅改指针 O(1)；注意 LinkedList 的 `addLast` 是 O(1)，因为有尾指针。**选型**：工程上 ArrayList 更常用，因为 CPU 缓存局部性好、综合性能稳定；LinkedList 仅在“频繁头尾插删且极少随机访问”时可能占优。结合项目，雅鉴生活志中业务数据主要在 Redis/DB，JVM 集合多用 ArrayList 即可。

### **【高频问题】HashMap 底层结构和 put 流程？1.7 与 1.8 差异？**
高分回答：  
**结构**：数组 + 链表 + 红黑树。**put 流程**：(1) 对 key 做 `hashCode()` 再与高16位异或扰动，降低低位碰撞；(2) `(n-1) & hash` 定位桶下标；(3) 桶空则直接插入；(4) 桶非空则遍历链/树：key 相同则覆盖 value 并返回旧值，不同则追加；链上插入前会先比较 key，避免重复 key 入链。(5) 若链表长度>=8 且数组>=64，链表转红黑树；树节点数<=6 时退化为链表。(6) 超过负载因子触发扩容，元素按高位 bit 迁到新桶。**1.7 vs 1.8**：1.7 头插法（可能形成环），1.8 尾插法；1.8 引入树化，极端冲突下查 O(log n)。

### **【高频问题】equals 和 hashCode 的关系？**
高分回答：  
**语义**：`equals` 判断两个对象逻辑相等；`hashCode` 返回对象哈希值，用于哈希表定位桶。**契约**：若 `a.equals(b)==true`，则 `a.hashCode()==b.hashCode()` 必须成立；反之不成立（哈希碰撞时）。**在 HashMap 中的使用**：先用 `hash(key)` 定位桶，桶内再遍历用 `equals` 比较 key；若 key 相等则覆盖，否则追加。重写 `equals` 必须同时重写 `hashCode`，否则放入 HashSet/HashMap 会出问题（两个“相等”对象可能进不同桶）。

### **【高频问题】Object 常用方法有哪些？**
高分回答：  
**常见方法**：`equals()` 判断相等、`hashCode()` 哈希值、`toString()` 字符串表示、`getClass()` 获取类对象、`clone()` 浅拷贝、`wait()/notify()/notifyAll()` 线程协作、`finalize()`（已不推荐）。**面试重点**：(1) equals-hashCode 约定：重写 equals 必须重写 hashCode，保证哈希容器正确；(2) wait/notify 必须在 synchronized 块内调用，否则抛 `IllegalMonitorStateException`；(3) clone 默认浅拷贝，深拷贝需自行实现或序列化。

### **【高频问题】深拷贝和浅拷贝区别？**
高分回答：  
**浅拷贝**：复制对象本身字段值，基本类型复制值，引用类型复制引用（地址），新旧对象共享引用对象。**深拷贝**：递归复制引用对象，副本和原对象完全隔离，修改一方不影响另一方。**Object.clone()**：默认浅拷贝，且需实现 Cloneable。**实现深拷贝方式**：递归 clone、拷贝构造、序列化/反序列化、BeanUtils 等。典型坑：浅拷贝下修改共享的 List，原对象也会受影响。

### **【高频问题】Java 类加载和初始化触发条件？**
高分回答：  
**流程**：加载（Loading）→ 链接（验证、准备、解析）→ 初始化（Initialization）→ 使用 → 卸载。**触发初始化的场景**：① new 对象；② 访问/赋值该类的非编译期常量静态字段；③ 调用该类静态方法；④ 反射；⑤ 初始化子类前先初始化父类；⑥ 启动类（含 main）。**不触发**：访问编译期常量（常量折叠内联）、`new User[10]` 只创建数组类不触发 User 初始化。**关键点**：“加载”和“初始化”不同，很多题考的是初始化边界。

## 二、并发与线程

### **【高频问题】创建线程的方式？为什么推荐线程池？**
高分回答：  
**创建方式**：① 继承 Thread；② 实现 Runnable；③ 实现 Callable + FutureTask（可拿返回值）。**为何用线程池**：线程创建/销毁有开销，大量线程导致上下文切换和 OOM；线程池复用线程、控制并发数、提供队列缓冲和拒绝策略，生产环境几乎必用。**项目结合**：雅鉴生活志的 `VoucherOrderHandler` 用 `Executors.newSingleThreadExecutor()` 单线程消费 Redis Stream，属线程池典型用法；秒杀场景下主线程快速返回，下单由后台线程异步处理。

### **【高频问题】线程池核心参数与执行流程？**
高分回答：  
**核心参数**：`corePoolSize` 核心线程数、`maximumPoolSize` 最大线程数、`keepAliveTime`+`unit` 非核心线程存活时间、`workQueue` 任务队列、`threadFactory` 线程工厂、`RejectedExecutionHandler` 拒绝策略。**执行流程**：① 任务提交后，若当前线程数 < core，新建核心线程执行；② 核心满则入队；③ 队列满则创建非核心线程直至 max；④ 达到 max 仍满则执行拒绝策略。**常见队列**：有界 ArrayBlockingQueue、无界 LinkedBlockingQueue、同步移交 SynchronousQueue。**建议**：生产用 `ThreadPoolExecutor` 显式配置，避免 `Executors` 默认无界队列导致 OOM。

### **【高频问题】线程生命周期？**
高分回答：  
**状态流转**：`NEW`（未启动）→ `RUNNABLE`（就绪/运行，Java 合并了 OS 的就绪与运行）→ `BLOCKED`（等待 monitor 锁）→ `WAITING`（无限期等待，如 wait/join）→ `TIMED_WAITING`（超时等待，如 sleep/parkNanos）→ `TERMINATED`。**注意**：`wait()` 释放锁并进入 WAITING，被 `notify()` 唤醒后需重新竞争锁才能继续；`sleep()` 不释放锁。

### **【高频问题】synchronized 和 ReentrantLock 的区别？**
高分回答：  
**synchronized**：JVM 内置，语法简单（方法/代码块），自动加锁解锁，不可中断，非公平；底层基于对象头 Mark Word 和 Monitor。**ReentrantLock**：JUC 显式锁，需手动 unlock（放 finally），支持可中断 `lockInterruptibly()`、公平锁、`tryLock()` 尝试加锁、多个 `Condition` 精细等待；基于 AQS。**选型**：一般场景 synchronized 够用；需要超时、可中断、公平锁时用 ReentrantLock。**项目**：雅鉴生活志秒杀是分布式场景，用 Redisson 分布式锁

### **【高频问题】AQS 原理是什么？**
高分回答：  
**核心**：AbstractQueuedSynchronizer，用 `volatile int state` 表示同步状态 + CLH 双向队列管理阻塞线程 + CAS 修改 state。**流程**：线程尝试 CAS 获取 state，成功则占锁；失败则封装成 Node 入队，并 park 阻塞；前驱释放锁时 unpark 后继，循环尝试获取。**应用**：ReentrantLock、ReentrantReadWriteLock、Semaphore、CountDownLatch、线程池 Worker 都基于 AQS。**可重入**：state 可大于 1，同一线程多次 lock 则 state++，unlock 时 state--，为 0 才真正释放。

### **【高频问题】wait/notify 有什么作用？**
高分回答：  
**作用**：在持有对象 monitor 的线程间做协作，实现“条件不满足则等待、条件满足则被唤醒”。**wait()**：释放当前对象锁，当前线程进入该对象的等待集，直到被 notify 或中断；被唤醒后需重新竞争锁才能从 wait 返回。**notify()**：唤醒等待集中任意一个线程；**notifyAll()** 唤醒全部。**前提**：必须在 `synchronized(对象)` 块内调用，否则抛 `IllegalMonitorStateException`。**与 sleep 区别**：sleep 不释放锁，wait 释放锁。

### **【腾讯真题】可重入、幂等、互斥有什么区别？如何实现？**
高分回答：  
**可重入**：同一线程多次获取同一把锁而不死锁；Redisson/synchronized 支持，state 计数。**幂等**：同一操作多次执行与一次效果一致；用业务唯一键、DB 唯一约束、requestId 去重实现。**互斥**：多线程/多请求对同一资源排他访问；锁 key 包含业务维度（如 `lock:withdraw:date:userId`），保证同用户串行。**易混点**：“用户点两次”需要**互斥**（串行化）+**幂等**（提现记录唯一），不是可重入；可重入解决的是锁内调用另一需同一锁的方法。

### **【腾讯真题】乐观锁和悲观锁的区别？**
高分回答：  
**悲观锁**：认为冲突多，访问数据时先加锁（SELECT FOR UPDATE、synchronized），其他线程阻塞；适合写多。**乐观锁**：认为冲突少，读不加锁，更新时检查版本号/条件是否变化，失败则重试；适合读多写少。**项目**：雅鉴生活志扣库存用 `setSql("stock=stock-1").eq("voucher_id",id).gt("stock",0)`，条件更新即乐观锁，避免超卖。

## 三、JVM

### **【高频问题】JVM 内存结构有哪些？**
高分回答：  
**五块区域**：① 程序计数器 PC：当前线程执行字节码行号，唯一无 OOM；② 虚拟机栈：栈帧（局部变量、操作数栈、返回地址），方法调用入栈、返回出栈；③ 本地方法栈：native 方法；④ 堆：对象实例、数组，GC 主战场，线程共享；⑤ 方法区（JDK8 实现为元空间）：类元数据、常量、静态变量。**线程私有**：PC、虚拟机栈、本地方法栈；**共享**：堆、方法区。**栈溢出**：栈深度超限（如无限递归）抛 StackOverflowError；**堆溢出**：对象过多抛 OutOfMemoryError。

### **【高频问题】元空间、堆分代、Eden/Survivor 比例？**
高分回答：  
**元空间**：JDK8 取代永久代，存类元数据于本地内存，避免永久代 OOM；默认不限制大小，需注意 metaspace 膨胀。**堆分代**：新生代（Eden + 2 个 Survivor）+ 老年代；新对象先在 Eden，Minor GC 后存活对象进 Survivor，多次存活后晋升老年代，Major GC 回收老年代。**比例**：Eden:S0:S1 常见 8:1:1（-XX:SurvivorRatio 可调）；新生代与老年代比例约 1:2（-XX:NewRatio）。**目的**：分代假设“大部分对象朝生夕死”，新生代小一些可加快 Minor GC。

### **【高频问题】垃圾回收器有哪些？**
高分回答：  
** Serial**：单线程，STW，适用客户端；**ParNew**：多线程版 Serial，配合 CMS；**Parallel Scavenge**：多线程，关注吞吐量；**CMS**：并发标记清除，低停顿，有碎片和浮动垃圾；**G1**：分区回收，可设停顿目标，适合大堆；**ZGC/Shenandoah**：超低延迟。**选型**：吞吐优先用 Parallel；低延迟用 G1/ZGC；老项目或小堆用 CMS。

## 四、MySQL 与事务

### **【高频问题】为什么 InnoDB 选 B+ 树？**
高分回答：  
（1）**B+ 树 vs 普通二叉树**：B+ 树是多路平衡树，单节点可存大量键，树高低，磁盘 IO 次数少；普通二叉树在数据有序时会退化成链表，查找 O(n)。  
（2）**B+ 树 vs B 树**：B+ 树非叶子节点不存数据，只存键和指针，单页可容纳更多键，树更矮；数据全在叶子节点，且叶子通过双向链表串接，天然支持范围查询和顺序扫描。  
（3）**B+ 树 vs 哈希**：哈希等值查找 O(1)，但不支持范围、排序、模糊查询，且对磁盘页友好性差；B+ 树适合磁盘按页读写模型。结合项目，雅鉴生活志的订单、优惠券、用户表都依赖 InnoDB 的 B+ 树索引做高效查询和范围扫描。

### **【高频问题】联合索引最左前缀与范围截断怎么理解？**
高分回答：  
（1）**最左前缀**：联合索引 `(a,b,c)` 在 B+ 树中按 a→b→c 顺序排序；查询时必须从最左列开始匹配，否则索引无法使用。如 `where b=1 and c=2` 无法利用该索引。  
（2）**范围截断**：等值条件可继续利用后续列，但遇到范围条件（`>`、`<`、`between`、`like '%x'`）后，该列及之后的列无法再用于有序查找。例：`where a=1 and b>2 and c=3` 只用到 a 和 b，c 需回表过滤。  
（3）**SQL 写法顺序**：优化器会重排 WHERE 条件，关键是谓词类型（等值/范围），不是书写顺序。实习做 N+1 优化时，就是通过理解联合索引规则，把关联查询改为合理顺序的 JOIN 以命中索引。

### **【高频问题】主键索引、唯一索引、普通索引区别？**
高分回答：  
（1）**主键索引**：每个表只能有一个，值唯一且非空，InnoDB 用主键组织聚簇索引（数据按主键物理排序存储），其他索引的叶子节点存主键值用于回表。  
（2）**唯一索引**：可建多个，保证列值唯一，NULL 可有多条（视实现而定）；用于业务唯一约束，如手机号、用户名。  
（3）**普通索引**：只加速查询，不保证唯一。  
（4）**为何推荐自增整型主键**：插入时追加在尾部，减少页分裂和移动；整型短，索引体积小；业务字段（如身份证）可能修改，主键不宜变。雅鉴生活志的订单表用 `bigint` 自增式 ID（RedisIdWorker 生成），符合这一原则。

### **【高频问题】慢查询如何排查？N+1 问题怎么解决？**
高分回答：  
（1）**慢查询排查流程**：① 开启 `slow_query_log`、设置 `long_query_time` 阈值；② 从慢日志或监控定位慢 SQL；③ 用 `EXPLAIN` 看 `type`（all/index/range/ref）、`key`、`rows`、`Extra`（是否文件排序、临时表、回表）；④ 结合业务判断是否索引失效（函数包裹列、隐式类型转换、范围截断）；⑤ 重建联合索引或 SQL 重写；⑥ 回归压测与监控对比。  
（2）**N+1 问题**：一次查主表得 N 条，再循环查 N 次关联表，共 1+N 次查询。解决：改为 JOIN 一次查出，或批量查询关联表后内存组装。实习中把城市-房源从循环查改为 JOIN，查询时间从 500ms 降到 50ms，就是典型 N+1 优化。

### **【高频问题】事务隔离级别、脏读/不可重复读/幻读？**
高分回答：  
（1）**四种隔离级别**：读未提交 RU、读已提交 RC、可重复读 RR、串行化 Serializable；InnoDB 默认 RR。  
（2）**脏读**：事务 A 读到事务 B 未提交的修改；发生在 RU。  
（3）**不可重复读**：事务 A 内两次读同一行，结果不同（B 已提交的修改被读到）；RC 及以下会出现，RR 通过 MVCC 解决。  
（4）**幻读**：事务 A 内两次按相同条件查询，记录数不同（B 插入或删除了满足条件的行）；RR 下 InnoDB 通过 MVCC + 间隙锁减少幻读，串行化彻底消除。  
（5）**不可重复读的危害**：如统计场景，第一次汇总、第二次再汇总，中间被他人修改会导致前后不一致，影响业务决策。

### **【高频问题】alter table 线上风险和过程？**
高分回答：  
（1）**常见过程**：加列、改类型、加索引等可能触发：获取元数据锁 MDL、创建临时表、数据拷贝、重建索引、切换新表、提交元数据。MySQL 5.6 起支持部分 Online DDL（如加索引可用 INPLACE），但大表仍可能长时间锁表。  
（2）**风险**：MDL 阻塞其他 DML、复制延迟、磁盘空间翻倍、主从不一致。  
（3）**大表变更方案**：使用 pt-online-schema-change、gh-ost 等工具，通过影子表 + 增量同步实现在线变更，减少业务影响。

### **【高频问题】乐观锁和悲观锁的区别？**（来源：腾讯 2026-3-16）
高分回答：  
**悲观锁**：认为冲突多，访问数据时先加锁（SELECT FOR UPDATE、synchronized），其他线程阻塞等待，适合写多读少。  
**乐观锁**：认为冲突少，读不加锁，更新时检查版本号/条件是否变化（如 `update ... where version=旧值` 或 `where stock>0`），失败则重试，适合读多写少。  
**项目**：雅鉴生活志扣库存用 `setSql("stock=stock-1").eq("voucher_id",id).gt("stock",0)`，利用条件更新实现乐观锁，避免超卖。

### **【高频问题】分布式事务了解过吗？**（来源：腾讯 2026-3-16）
高分回答：  
常见方案：① **2PC**：协调者两阶段提交，同步阻塞，有单点；② **TCC**：Try-Confirm-Cancel，需业务实现补偿；③ **Saga**：长事务拆成多个本地事务，失败执行逆向操作；④ **本地消息表**：事务内写业务+消息，异步发 MQ；⑤ **RocketMQ 事务消息**：Half 消息 + 本地事务 + 回查。  
适用场景：扣金币和发钱分属不同服务时，无法用本地事务，需上述方案之一保证最终一致。项目中未实现完整分布式事务，但秒杀和 Cache Aside 采用最终一致性思路。

## 五、Redis、缓存与登录态

### **【高频问题】Redis 为什么单线程还快？**
高分回答：  
**原因**：① 内存访问纳秒级，比磁盘快几个数量级；② IO 多路复用（select/epoll），单线程可同时监听大量连接，避免阻塞；③ 单线程执行命令，无锁竞争、无上下文切换；④ 命令执行路径短，数据结构高效（跳表、压缩列表等）。**Redis 6**：网络 IO 可多线程，但命令执行仍是单线程，保证原子性。**对比多线程**：多线程需加锁，反而可能降低吞吐；Redis 瓶颈在内存和网络，不在 CPU。

### **【高频问题】缓存穿透、击穿、雪崩区别和方案？**
高分回答：  
**穿透**：查不存在的数据，缓存和 DB 都无，每次请求打库。方案：缓存空值（短 TTL）、布隆过滤器前置拦截。**击穿**：热点 key 过期瞬间，大量请求同时打库。方案：互斥锁（只有一个线程查库回填）、逻辑过期（不设真实 TTL，另存过期时间，异步重建）。**雪崩**：大量 key 同时过期或 Redis 宕机，请求涌向 DB。方案：过期时间加随机偏移、多级缓存、限流降级、集群高可用。**项目**：雅鉴生活志用逻辑过期防击穿（`CacheClient.queryWithLogicalExpire`）、缓存空值防穿透（`queryWithPassThrough` 存空串）。

### **【高频问题】Cache Aside 为什么“更新数据库后删缓存”？**
高分回答：  
**为什么删而不是更新**：① 并发写：A 写 1、B 写 2，若都改缓存，执行顺序可能是 B 先更新缓存 2、A 后更新缓存 1，最终库是 2 但缓存是 1，不一致；② 缓存字段可能来自多表或聚合，更新逻辑复杂易漏；③ 删缓存让下次读回源，按最新库数据重建，更简单可靠。**项目**：`ShopServiceImpl.update` 先 `updateById` 再 `delete(CACHE_SHOP_KEY+id)`，符合 Cache Aside。可再加延迟双删或 MQ 补偿提高一致性。

### **【高频问题】登录校验怎么设计？ThreadLocal 为什么要用？**
高分回答：  
**项目设计**：token（UUID）存 Redis，key 为 `login:token:{token}`，value 为 UserDTO（Hash）；登录成功返回 token，前端存 localStorage 或 Cookie，请求时放 Header `authorization`。**拦截器**：RefreshTokenInterceptor 取 token、查 Redis，命中则 `UserHolder.saveUser()` 写入 ThreadLocal 并刷新 TTL；LoginInterceptor 检查 `UserHolder.getUser()` 是否为空，空则 401。**ThreadLocal 作用**：同一请求内 Controller/Service 任意层都能 `UserHolder.getUser()` 取当前用户，无需层层传参；请求结束 `afterCompletion` 里 `removeUser()` 防止线程复用串数据。

### **【高频问题】双拦截器流程是什么？**
高分回答：  
**RefreshTokenInterceptor（order=0）**：对所有路径生效；取 Header 的 token，查 Redis；无 token 或查不到用户则直接放行（不拦截）；有用户则写入 ThreadLocal、刷新 Redis TTL、放行。**LoginInterceptor（order=1）**：排除登录、验证码、店铺列表等公开路径；检查 ThreadLocal 是否有用户；无则 401 拦截，有则放行。**顺序**：先 Refresh 恢复/续期登录态，再 Login 做强校验；二者配合实现“公开接口可访问、需登录接口无 token 即拦截”。

### **【腾讯真题】Lua 在 Redis 里的主要作用？同一用户同时点两次，Lua 是并发还是串行？为什么？**
高分回答：  
**作用**：Lua 保证**原子性**，一系列 Redis 命令在一个脚本里执行，要么全成功要么全失败，执行期间不会被其他命令打断。**同一用户点两次**：会触发两次 Lua 执行，但 Redis **单线程**执行命令，所以这两次会**串行排队**；第一次已把 userId 写入 `seckill:order:{voucherId}`，第二次执行到 `sismember` 时命中，返回 2（重复下单），不会重复扣库存和入队。**项目**：`seckill.lua` 内 get stockKey、sismember、incrby、sadd、xadd 一气呵成。

### **【腾讯真题】缓存击穿的互斥锁和逻辑过期分别怎么做？有什么区别？**
高分回答：  
**互斥锁**：查缓存未命中时先 `setnx lock:key` 抢锁，拿到锁的线程查库并回填缓存后释放锁；其他线程未抢到则 sleep 后重试查缓存。**逻辑过期**：缓存不设真实 TTL，value 中存过期时间；命中后发现逻辑过期则抢锁，抢到则开异步线程回填，当前线程直接返回旧数据；未抢到也返回旧数据。**区别**：互斥锁会阻塞等待，逻辑过期不等待、立即返回旧值，高并发下体验更好。**项目**：`CacheClient.queryWithMutex` 用 Redis setIfAbsent 实现互斥；`queryWithLogicalExpire` 用逻辑过期。

## 六、消息队列、异步与一致性

### **【高频问题】为什么用消息队列？**
高分回答：  
**三大价值**：① 解耦：生产者和消费者互不依赖，新增消费方只需订阅；② 削峰：瞬时高峰写入队列，消费者按能力消费，保护下游；③ 异步：主流程快速返回，耗时操作异步处理。**项目**：秒杀场景下，Lua 校验通过后 XADD 入 Redis Stream，主线程立即返回“抢购资格已获得”，订单创建由后台消费者异步执行；若同步落库，高并发时 DB 易被打穿、接口 RT 飙升。

### **【高频问题】消息可靠性如何保证（不丢/不重）？**
高分回答：  
**不丢**：① 生产端：开启确认机制（如 RabbitMQ publisher confirm），消息落盘后才 ack；② Broker：持久化到磁盘；③ 消费端：手动 ACK，处理成功后再确认，失败则 nack 重试。**不重**：消息系统通常“至少一次”投递，重试可能重复；需业务幂等：唯一业务键（user_id+voucher_id）、DB 唯一约束、去重表等，重复消费时识别为已处理并 ACK。**项目**：Redis Stream 用 XACK 确认，pending-list 处理超时未确认消息；订单表应加 unique(user_id,voucher_id)，重复插入时捕获唯一冲突视为幂等成功。

### **【高频问题】消费重试导致重复下单怎么处理？**
高分回答：  
**问题**：消费失败后重试，若第一次其实已成功（如超时、网络抖动），重试会再执行一次创建订单，导致一单多建。**方案**：① 订单号在入队前生成并写入消息，消费时用同一 ID，避免每次重试生成新 ID；② 业务唯一键：user_id + voucher_id 天然唯一，消费前先查是否已存在；③ 数据库唯一约束 `unique(user_id, voucher_id)` 兜底，重复插入抛异常时视为幂等成功并 ACK；④ 去重表：存 messageId，消费前查，有则跳过。**项目**：当前订单 ID 已前置生成，建议补唯一约束，消费端对唯一冲突按成功处理。

### **【高频问题】二阶段事务消息是什么？**
高分回答：  
**场景**：本地 DB 事务与发送 MQ 消息需要“同时成功或同时失败”，避免 DB 提交了但消息没发、或消息发了但 DB 回滚。**流程**：① 发送 Half 消息（对消费者不可见）；② 执行本地事务；③ 根据本地事务结果提交或回滚 Half 消息；④ 若状态未知，Broker 主动回查本地事务状态，决定提交或回滚。**代表**：RocketMQ 事务消息。**与本地 ACID 区别**：这是跨系统的最终一致性，不能替代本地事务；适用于订单->库存、支付->通知等场景。

### **【腾讯真题】异步慢慢处理可能带来什么问题？用户已提示成功但消费失败怎么办？扣金币成功、发钱失败如何回滚？**
高分回答：  
**问题**：消费延迟或失败时，用户以为成功实则未成单，体验差、可能客诉。**措施**：① Redis Stream 用 XACK 确认，未 ACK 的消息进入 pending-list，`handlePendingList` 可重新拉取；② 前端轮询订单状态或 WebSocket 推送；③ 监控消费延迟、失败率、pending 堆积；④ 对长时间未成单的做补偿（退款/补发）。**跨服务补偿**：若扣金币和发钱分属不同服务，发钱永远失败时，需**补偿**把已扣金币加回；通过定时任务或人工处理，MQ 本身不提供自动回滚。

### **【高频问题】请讲一个最有挑战的项目问题（背景-方案-结果）**

### **【高频问题】秒杀流程怎么设计？**

**链路**：① 前置校验（时间、库存、一人一单）→ ② 快速失败（Lua 内原子判断）→ ③ 预扣库存 + 入队（Lua 内 incrby、sadd、xadd）→ ④ 消费者取消息 → ⑤ Redisson 按用户加锁、查重、扣 DB 库存、建订单 → ⑥ ACK。

### **【高频问题】分布式 UID 怎么设计？**
高分回答：  
**常见方案**：① 雪花算法（时间戳 + 机器 ID + 序列号），趋势递增、高性能；② Redis INCR（按天或按业务 key），简单可靠；③ 数据库自增（多库需号段）；④ UUID（无序、索引效率差，不推荐做主键）。  
**项目结合**：`RedisIdWorker` 使用"时间戳差值左移 32 位 + 当日 Redis 自增序列"，key 为 `icr:order:yyyy:MM:dd`，保证全局唯一、趋势递增、易读。需注意时钟回拨和序列溢出的边界处理。

### **【高频问题】系统架构、流量规模、你负责边界如何讲？**
高分回答：  
**框架**：先讲业务闭环（用户做什么、数据怎么流转），再讲你负责的模块、上下游依赖、技术选型；流量和规模有数就说，没有就诚实说"当前 demo/低流量，但具备扩展思路"。  
**边界**：不清楚的（如是否分布式、多少实例）直接说"当时未深入架构层"，同时表达"我会在入职后快速补齐"。避免编造，保持可信度。

### **【腾讯真题】场景题：金币换现金，一天只能换一次，三步（检查资格→扣1万金币→发1块钱），如何设计？机器挂了/用户点两次/扣金币和发钱在不同服务怎么处理？**
高分回答：  
**设计**：锁 key=`withdraw:date:userId`，保证同用户同天串行；检查 `withdraw_log` 今日是否已存在，有则直接返回；扣金币用 `where balance>=10000` 条件更新；扣金币+发钱+写提现记录放同一事务。**机器挂了**：同一事务内任一步失败会回滚。**用户点两次**：互斥锁串行化，第二次进来时第一次已写记录，检查失败返回；或提现表 `unique(user_id,date)` 兜底。**跨服务**：无法用本地事务，需本地消息表/RocketMQ 事务消息/TCC 等；发钱永远失败时需补偿，把金币加回用户账户。

## 八、算法高频归类

### **【高频问题】旋转数组查找（LeetCode 33）**
高分回答：  
**思路**：二分时比较 `mid` 与 `right`，若 `mid > right` 说明左半有序，若 `target` 在 [left,mid] 则 right=mid-1，否则 left=mid+1；若 `mid <= right` 说明右半有序，同理收缩。**要点**：旋转后必有一侧有序，在有序侧判断 target 是否在其中。时间 O(log n)，空间 O(1)。

### **【高频问题】二叉树右视图**
高分回答：  
**思路**：层序遍历（BFS），每层遍历时记录该层最后一个节点值，即为右视图。也可 DFS：按根-右-左顺序，每层首次访问的节点即右视图节点。时间 O(n)，空间 O(树宽) 或 O(高度)。

### **【高频问题】最长无重复子串**
高分回答：  
**思路**：滑动窗口 + 哈希表记录字符最近出现下标。右指针扩张，若当前字符已出现过且下标>=左指针，则左指针移到“上次出现位置+1”；每次更新右指针时记录长度最大值。**关键**：左右指针均单调右移，每个字符最多进出一次，时间 O(n)；空间 O(字符集大小)。若答 O(n²) 会被追问优化到 O(n)。

### **【高频问题】LCS 最长公共子序列**
高分回答：  
**状态**：`dp[i][j]` 表示 text1[0..i-1] 与 text2[0..j-1] 的 LCS 长度。**转移**：若 text1[i-1]==text2[j-1]，则 dp[i][j]=dp[i-1][j-1]+1；否则 dp[i][j]=max(dp[i-1][j], dp[i][j-1])。**初始化**：第 0 行和第 0 列为 0。时间 O(mn)，空间可压缩到 O(n)。

### **【腾讯真题】实现 LRU 缓存（最近最少使用淘汰）**
高分回答：  
**思路**：最近访问的放前面，最久未访问的淘汰。**实现**：HashMap + 双向链表。HashMap 存 key→Node；链表按访问顺序，头为最近使用，尾为最久未使用。`get`：存在则把节点移到头并返回值；`put`：存在则更新值并移到头；不存在则新建节点放头，超容量则删尾节点。也可用 `LinkedHashMap`（accessOrder=true），重写 `removeEldestEntry`。时间 O(1)，空间 O(capacity)。

### **【预测问题】为什么更新 DB 后删除缓存，而不是更新缓存？**
建议回答：  
“主要有三点：① 并发写时，后写入 DB 的请求可能先更新缓存，导致缓存与 DB 不一致；② 缓存可能是多表聚合，更新路径复杂易漏；③ 删缓存后下次读会回源，按最新 DB 数据重建，策略更简单可靠。我们项目 ShopServiceImpl.update 就是先 updateById 再 delete 缓存，符合 Cache Aside。可再加延迟双删或 MQ 补偿提高一致性。”

### **【预测问题】登录态为什么放 Redis，不直接 JWT 无状态？**
建议回答：  
“Redis 会话可以主动失效（踢人、封号）、续期、查看在线状态、做单设备登录等，运维和风控更灵活。JWT 无状态、易水平扩展，但一旦签发难以提前失效，除非维护黑名单（又变有状态）。我们项目选 Redis 是因为需要续期（RefreshTokenInterceptor 里 expire）、以及后续可能做在线人数等，所以用 token+Redis 会话。”

### **【预测问题】线程池参数如何按业务设置？**
建议回答：  
“CPU 密集型：core 约等于 CPU 核数，max 可略大，队列不宜过长；IO 密集型：core 可设 2*CPU 或更高，因为线程大部分时间在等待，max 可更大；有界队列防止 OOM；拒绝策略根据业务选 CallerRunsPolicy（让调用者执行）或 AbortPolicy（抛异常）。先压测再调，结合监控看队列堆积、拒绝次数、线程利用率。”

### **【腾讯真题】Lua 中间失败了怎么处理？重试不会出问题吗？如何实现幂等？**（来源：腾讯 2026-3-16）
建议回答：  
“Lua 内部任一步失败会整体回滚。若 Lua 成功但消费前进程挂掉，消息在 pending-list，重启后重试消费；幂等靠 user_id+voucher_id 判重和 DB 唯一约束，重复消费视为成功并 ACK。可重入解决的是同线程重入锁，幂等解决的是多次执行结果一致，二者不同。”
