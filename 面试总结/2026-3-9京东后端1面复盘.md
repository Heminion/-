### **【Q1】你做这个项目最大的技术挑战是什么？怎么解决？最终效果如何？**
高分回答（示例）：
我选“缓存治理”这个挑战。背景是多模块重复写缓存逻辑、Key 命名不统一、并且多语言场景下出现串数据。  
我的方案是三步：第一，统一 Key 规范（业务前缀 + 模型 + ID + 语言）；第二，抽象缓存模板能力减少重复代码；第三，补齐缓存读写和失效策略，避免脏读。  
最终效果是：重复代码明显减少，语言串数据问题被修复，缓存命中与排障效率都提升。  
高分点是用“背景-方案-结果”结构，而不是只讲技术名词。

### **【Q7】设计一个分布式 UID（流水号）服务，要求多实例、高并发、低延迟、全局唯一，你怎么做？**
高分回答（结合“雅鉴生活志”）：
我会用“时间戳 + 序列号 + 业务位”方案，典型如 Snowflake 思路；并按实例或机房分配 workerId 保证并行安全。  
在“雅鉴生活志”里我用了 `RedisIdWorker`：高位是时间戳差值，低位是 Redis `INCR` 自增序列，最终拼接成全局唯一订单号。  
工程细节要补齐：时钟回拨保护、序列溢出处理、按日分段计数、可观测性（ID 生成失败率/耗时）。  
这是非常高频系统设计题，建议背熟一版 90 秒口述稿。

### **【Q8】AQS 的实现原理是什么？**
高分回答（示例）：
AQS 是 JUC 同步器基础框架，核心是一个 `volatile state` 状态位 + CLH 变体双向队列。  
获取锁失败的线程会入队并通过 `park/unpark` 挂起唤醒，子类通过实现 `tryAcquire/tryRelease` 定义语义。  
`ReentrantLock`、`Semaphore`、`CountDownLatch` 都基于 AQS。  
高分点：讲清“状态位 + 队列 + CAS + 挂起唤醒”。

---

### **【Q9】Spring 事务传播机制有哪些？**
高分回答（示例）：
`REQUIRED`、`REQUIRES_NEW`、`NESTED`、`SUPPORTS`、`NOT_SUPPORTED`、`MANDATORY`、`NEVER`。  
常用的是 `REQUIRED`（默认）和 `REQUIRES_NEW`（新事务隔离外层影响）。  
面试时可加一句：传播行为解决的是“方法间事务边界”，不是隔离级别问题。

---

### **【Q10】MySQL 四种隔离级别？默认是哪种？**
高分回答（示例）：
`READ UNCOMMITTED`、`READ COMMITTED`、`REPEATABLE READ`、`SERIALIZABLE`。  
MySQL InnoDB 默认是 `REPEATABLE READ`。  
高分补充：InnoDB 通过 MVCC + 间隙锁等机制在 RR 下处理幻读问题。

### **【Q11】秒杀流程怎么设计实现？**
高分回答（结合项目代码）：
“雅鉴生活志”当前实现是：  
1) 秒杀前把库存放入 Redis；  
2) Lua 脚本原子校验库存和一人一单，并预扣库存；  
3) Lua 里 `XADD` 写入 `stream.orders`；  
4) 后台消费者 `XREADGROUP` 异步创建订单，成功后 `XACK`。  
配合 Redisson 用户粒度锁和数据库条件扣减，保证高并发下防超卖与防重复下单。  
注意：该项目代码实际是 Redis Stream，不是 RabbitMQ。

### **【Q12】数据库和缓存不一致怎么处理？**
高分回答（结合项目）：
我采用 Cache Aside：写请求“先更新 DB，再删除缓存”。  
在项目中店铺更新就是 `updateById` 后删除 `cache:shop:{id}`。  
如果追求更高一致性，可加延迟双删、删除失败重试、消息补偿，并配 TTL 做兜底。

### **【Q13】秒杀下单时如果库存不足，后续流程是什么？**
高分回答（示例）：

高分点：强调“失败前置 + 快速返回 + 减少无效流量”。

## 二、基于面试问题 + 项目代码的简历改进建议

### 1) 统一“项目技术口径”，避免被追问反杀
- 当前“雅鉴生活志”代码里是 Redis Stream（`XADD/XREADGROUP/XACK`），不是 RabbitMQ。  
- 简历中“消息队列”建议写成“Redis Stream 异步下单链路”，除非你有可展示的 RabbitMQ 项目。  
- 面试中技术名词必须可落到代码文件与具体实现。

### 2) 删除/降级未落地的架构描述
- 本场你口述了“分库分表、Kafka、推荐系统、监控告警体系”，但代码无法支撑。  
- 建议改为“可落地计划”而非“已实现事实”，保持可信度。

### 3) 强化“系统设计能力”条目（对齐京东题风）
- 增加一条：`分布式 ID 生成：时间戳 + Redis 自增序列，保障全局唯一与高并发低冲突`。  
- 增加一条：`秒杀链路：Lua 原子校验 + Stream 异步削峰 + 幂等设计`。

### 4) 用指标写法替代泛化写法
- 每条经历尽量补“前后对比指标”：RT、QPS、失败率、重复订单率、慢 SQL 数。  
- 没有真实线上数据就写压测数据和测试场景，不要空口“高并发”。

### 5) 重新打磨“自我介绍”模板
- 重点放在：你解决过什么问题、用过哪些可验证技术、产出过什么可量化结果。  
- 控制在 60-90 秒，减少口语化和无效背景铺垫。

## 三、全方位深度复盘（问题本质 + 失分机制 + 修复路径）

## 1. 本场面试官考察风格
- 偏业务穿透 + 工程真实性，不是纯八股。  
- 会从业务流程一路追到架构能力，再追到基础理论和工程边界。  
- 如果回答不具体，会持续追问直到确认你是否真正做过。

## 2. 主要失分点

### A. 业务表达不成体系
- 多次被追问“你到底处理了什么”，说明业务链路表达不清。  
- 修复：固定“输入-处理-输出-价值”模板，任何业务题按这四句展开。

### B. 技术口径与实现不一致
- 秒杀项目提到 RabbitMQ/Kafka/分库分表，但现有代码难以支撑。  
- 修复：只讲能落地到代码的内容，未实现的用“计划”语态。

### C. 基础能力暴露短板
- AQS、事务传播机制、RPC 等基础题薄弱。  
- 修复：按“定义-原理-场景-坑点”做 2 周专项补齐。

### D. 系统设计题无结构
- 分布式 UID 是标准题，但回答停在“不太清楚”。  
- 修复：背熟 3 套模板题（UID、秒杀、缓存一致性），每题准备 90 秒版本。

### E. 职业表达不职业
- “30 岁退休”在企业语境里是明显减分项。  
- 修复：职业规划强调成长路径、岗位匹配与投入度。

## 3. 你这场的优势
- 真实做过缓存治理与业务适配，不是零经验。  
- 能理解异步化和并发控制的核心价值。  
- 沟通态度稳定，可塑性强。
