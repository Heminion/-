# 2026-4-13 小厂 AI 全栈复盘

## 一、面试分析

这场面试整体不是传统后端八股面，而是非常贴近 AI 全栈实习的沟通型技术面。面试官重点看三件事：

1. 你是不是真的在主动从后端往 AI 全栈转
2. 你是不是实际用过 AI coding，并能说清楚怎么协作、怎么落地
3. 你对 Agent、RAG、Embedding、工具调用这些基础概念有没有工程化理解

这场的优点是：

1. 能拿出微信小程序和扫地机器人智能客服 Agent 两个项目，和岗位方向有一定匹配度
2. 对 AI coding 的基本方法有意识，比如拆任务、给上下文、多轮迭代、让 AI 写测试
3. RAG 和 ReAct Agent 的边界能说出大方向：RAG 解决知识边界，Agent / Tool 解决动作边界

主要失分点也很明显：

1. 项目讲解不够结构化，展示小程序时没有先讲背景、目标、架构和自己负责的部分，导致面试官不断帮你拉回叙事
2. AI coding 经验回答偏泛，缺少具体案例，比如某个功能如何拆 prompt、如何审查 AI 代码、如何测试和回滚
3. RAG / Embedding 的底层过程说得不够技术化，尤其是文档切分、向量化、相似度召回、上下文拼接、引用与评估
4. Agent 工具调用没有讲清楚“具体工具列表、输入输出、触发时机、路由规则、失败兜底”
5. 反问环节较弱，只问了工作内容，没有继续追问技术栈、实习产出、团队评价标准等关键信息

建议你优先补三块：

1. AI coding 项目表达：准备一个完整案例，按“需求 -> 任务拆分 -> prompt -> 代码审查 -> 测试 -> 人工接管”来讲
2. RAG 工程化：补文档切分、Embedding、向量库、召回、重排、Query Rewrite、多语言检索、评估指标
3. Agent 工程化：补 ReAct、工具定义、工具路由、状态管理、错误处理、长任务拆解、权限和安全边界

### 3. 平时会用 AI coding 吗？

高分回答：

会用，而且我现在基本会把 AI coding 当成开发流程的一部分，而不是只拿来生成代码。

我自己的原则是：AI 可以加速产出，但关键逻辑、数据安全、边界条件和最终代码合并必须自己 review。

### 4. 一般用什么 AI coding 工具？

高分回答：

我之前用过 Cursor，现在更多使用 Codex / Claude Code 这类工具配合 VS Code。

Cursor 的优势是和编辑器结合比较顺，适合快速补代码、改文件、做局部重构。但我后来发现对于复杂任务，像 Codex / Claude Code 这种更偏 agentic coding 的工具，在长上下文、多文件修改、跑测试和根据测试结果继续修复方面会更适合。

所以我现在的使用方式是：简单局部修改用编辑器内补全，复杂功能会把任务拆成几个阶段，让 AI 先读项目结构，再给方案，最后分步实现和验证。

### 5. 使用 AI coding 工具时有什么技巧或者心得？你怎么和 AI coding 工具协作？

高分回答：

我觉得 AI coding 最重要的不是“让它一次生成完整项目”，而是把它当成一个开发协作者来管理。

我一般会按五步来做：

1. 先给背景：告诉它项目技术栈、目录结构、数据库、已有约定和这次要改的边界
2. 再拆任务：把大功能拆成数据模型、接口、页面、状态管理、测试几个小任务
3. 明确约束：比如不要改无关文件、遵循现有代码风格、失败要说明原因
4. 分步实现：每次只让它做一个相对封闭的改动，做完我会 review diff
5. 验证闭环：让它跑测试、补边界 case，然后我自己再做关键路径验收

举个例子，如果我要做一个小程序的路线规划功能，我不会直接说“帮我做路线规划”，而是会先让它读页面结构和腾讯地图 API 文档，再拆成地点搜索、起终点选择、路线请求、结果渲染和异常提示几个部分。这样 AI 的输出更可控，我也更容易发现问题。

### 6. 你哪个项目是用 AI coding 做的？能不能举一个具体功能点的例子？

高分回答：

我可以讲微信小程序旅游项目里的路线规划功能，这是我用 Cursor 辅助完成比较多的一块。

这个功能的目标是让用户选择起点和终点，然后调用腾讯地图 API 获取路线规划结果，并在小程序里展示出来。我当时没有让 AI 一次性写完整功能，而是分成几步：

1. 先让 AI 根据微信小程序页面结构生成起点、终点输入和选择组件
2. 再让它封装腾讯地图 API 的调用逻辑，包括参数、key、错误返回处理
3. 接着让它把路线结果转换成页面可展示的数据结构
4. 最后让它补充异常场景，比如没有授权定位、地点为空、接口失败、没有路线结果

AI 生成之后，我主要做了三类人工检查：

1. 检查 API key、请求参数和回调逻辑是否符合腾讯地图规范
2. 检查页面状态是否会出现起点终点错乱、重复请求等问题
3. 手动测试不同地点输入，确认路径规划结果能正确展示

这个例子让我比较明显地感受到，AI coding 适合做结构化实现，但前提是人要负责拆任务、定边界和验收。

### 11. 这个接的是腾讯地图 API 对吧？这些接口和推荐都是它提供的吗？

3. 推荐排序逻辑：当前是基于评分和热度字段的简单排序，后续可以接真实用户行为做推荐

### 12. 按热度、按评分是 mock 数据，还是根据真实用户点击计算的？

高分回答：

当前项目没有真实上线，所以没有真实用户点击数据。热度和评分主要是我们预置在数据库里的字段，可以理解为种子数据或 mock 数据。

但如果按真实产品来设计，我会把热度拆成可计算指标，而不是人工写死。比如：

1. 浏览量、点赞数、收藏数、评论数作为基础行为信号
2. 加上时间衰减，避免老内容长期霸榜
3. 对异常刷量做限制，比如同一用户重复点击只计一次或做权重降低

一个简单的热度公式可以是：

```text
hot_score = view_count * 1 + like_count * 3 + favorite_count * 5 + comment_count * 4 - time_decay
```

这样热度排序就能从 mock 字段升级为真实用户行为驱动。

### 18. 扫地机器人智能客服 Agent 项目可以详细说一下吗？

高分回答：

这个项目是一个面向扫地机器人用户的智能客服 Agent，目标是解决三类问题：产品选购咨询、使用说明问答和故障排查。

整体架构可以分成四层：

1. 前端交互层：用 Streamlit 做一个客服对话界面，支持用户输入问题和查看回答
2. 后端编排层：用 Python + LangChain / LangGraph 管理对话、RAG 检索和工具调用
3. 知识检索层：把产品说明书、FAQ、故障排查文档切分后做 Embedding，存入 Chroma 向量库
4. 模型与工具层：模型使用通义千问相关模型，工具包括知识检索、故障诊断、时间 / 位置 / 环境信息等

这个项目里我主要想验证两个点：

1. RAG 能不能让模型基于产品文档回答，减少胡编
2. ReAct Agent 能不能根据用户问题选择下一步动作，比如先检索知识库，或者追问用户设备状态，再给出排查步骤

一句话总结：它不是单纯聊天机器人，而是把产品知识库、故障排查流程和工具调用结合起来的客服 Agent。

### 19. 你这个 ReAct Agent + RAG 是 Agentic RAG，还是传统 RAG？怎么做的？

高分回答：

当前版本更接近“传统 RAG + ReAct 工具调用”，还不是完整的 Agentic RAG。

传统 RAG 部分是固定链路：用户提问后，系统会对 query 做 embedding，在 Chroma 里召回相关文档片段，然后把召回内容作为上下文交给大模型生成回答。这个链路主要解决“知识边界”问题，让模型回答基于产品说明书、FAQ 和故障文档。

ReAct Agent 部分主要解决“动作边界”问题。比如用户不是问一个静态知识，而是说“机器在某个环境下清扫异常”，Agent 可以根据问题判断是否需要调用故障排查工具、环境信息工具，或者追问更多信息。

如果升级成更完整的 Agentic RAG，我会让 Agent 在检索前后做更多决策，比如：

1. Query Rewrite：把口语化、跨语言或不完整问题改写成更适合检索的 query
2. 多路检索：同时查 FAQ、说明书、故障库，再合并结果
3. 结果反思：判断召回内容是否足够，不够就二次检索
4. 答案校验：检查回答是否有来源引用，避免脱离知识库

### 20. 你是在什么时候开始使用 RAG？它是一定触发的吗？

高分回答：

我当前实现里，知识类问题基本会默认触发 RAG，因为客服场景下大部分回答都应该基于产品文档，不能完全依赖模型记忆。

但如果做得更工程化，我不会让所有问题都无脑走 RAG，而会先做一个轻量路由：

1. 产品参数、使用说明、故障排查类问题：走 RAG
2. 闲聊、问候、能力说明：不需要查知识库
3. 需要实时信息或用户上下文的问题：先调用工具，再决定是否 RAG
4. 召回置信度低的问题：追问用户或提示无法确定，而不是强行回答

也就是说，第一版可以默认触发 RAG 保证回答有依据；更成熟版本应该做意图识别和路由，让 RAG 只在需要外部知识时触发。

### 22. 工具调用有定义哪些工具？

高分回答：

我把工具按职责分成几类：

1. 知识检索工具：比如 `rag_search`，根据用户问题召回产品说明书、FAQ、故障排查文档
2. 故障诊断工具：比如 `diagnose_issue`，根据故障现象、设备状态、错误码输出排查步骤
3. 环境信息工具：比如位置、天气、地面环境等，用于判断某些清扫问题是否和环境有关
4. 时间和上下文工具：比如当前时间、用户设备型号、历史对话摘要
5. 总结工具：比如 `rag_summarize`，把多段召回内容压缩成更适合模型引用的上下文

每个工具都应该有清晰的输入输出。比如 `rag_search` 的输入是 query、top_k、文档类型过滤条件，输出是文档片段、来源、相似度分数；`diagnose_issue` 的输入是故障类型、错误码、用户描述，输出是分步骤排查建议和是否建议转人工。

这样 Agent 才不是“随便调函数”，而是基于工具能力边界做决策。

### 23. 具体有哪些工具？RAG summarize 是什么？

高分回答：

一个更具体的工具列表可以这样设计：

1. `search_product_docs(query, top_k)`：检索说明书、参数和使用文档
2. `search_faq(query, top_k)`：检索高频问答
3. `search_troubleshooting(query, top_k)`：检索故障排查手册
4. `summarize_evidence(chunks)`：把召回片段压缩成结构化证据
5. `diagnose_robot_issue(symptom, model, error_code)`：根据现象和型号生成排查路径
6. `get_user_context(user_id)`：获取用户设备型号、购买时间、历史问题等上下文
7. `handoff_to_human(reason)`：当置信度低或涉及售后维修时转人工

`RAG summarize` 不是简单“总结一下”，而是为了解决召回片段太多、太散的问题。它会把多个 chunk 结构化成：

```text
相关结论：
- ...

证据来源：
- 文档 A / FAQ B / 故障手册 C

限制条件：
- 当前资料没有覆盖 ...
```

然后再把这个压缩后的证据交给最终回答模型。这样可以减少上下文噪声，也方便回答时带来源。

### 24. RAG 是什么意思？简单讲一下

高分回答：

RAG 全称是 Retrieval-Augmented Generation，中文一般叫检索增强生成。

它解决的问题是：大模型本身的参数知识可能过时、不完整，或者不了解企业私有文档。RAG 会先从外部知识库里检索和用户问题相关的内容，再把这些内容作为上下文交给大模型生成答案。

所以它的核心不是让模型“凭记忆回答”，而是让模型“基于检索到的资料回答”。这在客服、企业知识库、法律法规、产品手册这类场景里特别重要，因为回答需要可追溯、可更新、少幻觉。

---

### 25. RAG 的整个过程是什么样的？怎么检索、怎么增强、怎么生成？

高分回答：

RAG 可以分成离线建库和在线问答两部分。

离线建库阶段：

1. 收集文档，比如说明书、FAQ、故障排查手册
2. 清洗文档，去掉重复、无效、格式混乱的内容
3. 文档切分，把长文档切成合适大小的 chunk
4. 对每个 chunk 做 embedding，转成向量
5. 把向量、原文、标题、来源等 metadata 存入向量库，比如 Chroma

在线问答阶段：

1. 用户输入问题
2. 对用户问题做 embedding
3. 用问题向量和文档向量做相似度匹配，召回 top_k 个相关片段
4. 可选地做 rerank、过滤和摘要
5. 把用户问题、召回内容、回答要求一起拼进 prompt
6. 大模型基于这些上下文生成最终答案
7. 返回答案时最好带来源引用，并在证据不足时明确说明

一句话概括：检索负责找资料，增强负责把资料组织进上下文，生成负责基于资料给用户可读答案。

### 26. Embedding 是做什么的？DashScope Embedding 用来做什么？

高分回答：

Embedding 的作用是把文本转换成向量，让机器可以计算文本之间的语义相似度。

在 RAG 里，文档和用户问题都要经过 embedding 模型。比如我先把产品说明书切成很多 chunk，每个 chunk 通过 DashScope Embedding 转成一个向量，存到 Chroma 里。用户提问时，也把问题转成向量，然后和库里的文档向量做相似度计算，找出最相关的几个片段。

这里重点不是“Embedding 能让中文回答更自然”，而是它把自然语言变成可计算的语义空间。这样即使用户问法和文档原文不完全一样，只要语义接近，也有机会被召回。

选择 DashScope Embedding 主要是因为它对中文语义支持比较好，和通义千问生态集成方便，适合中文产品客服场景。

### 27. 你现在做的这个 Agent / RAG 项目，有没有可以优化的地方？缺点在哪里？

高分回答：

有，当前版本更像可运行原型，离生产级智能客服还有不少优化空间。

第一是知识库质量。现在文档里可能有重复、冲突、过期或低质量内容，会直接影响召回质量。需要做文档清洗、去重、版本管理和来源标注。

第二是检索效果。可以优化 chunk size、chunk overlap、top_k、metadata filter，也可以加 rerank 模型，把粗召回结果重新排序。还要做召回评估，比如命中率、MRR、答案是否引用正确来源。

第三是 Agent 路由。现在工具调用还比较粗，可以增加意图识别，区分产品问答、故障排查、售后政策、闲聊和转人工，减少不必要的工具调用。

第四是可靠性。客服场景不能乱答，所以要加置信度判断、证据不足提示、敏感问题转人工、工具失败兜底和日志追踪。

第五是多轮上下文。故障排查经常需要追问，比如设备型号、错误码、使用环境，所以需要更明确的状态管理，而不是每轮都独立回答。

### 28. 如果文档是中文，用户用英文问，传统 RAG 相似度匹配不上，你怎么优化？

高分回答：

这个问题本质是跨语言检索。可以从三层优化。

第一层是 Query Rewrite / 翻译。先识别用户问题语言，如果用户用英文问，而知识库主要是中文，就用模型把英文 query 翻译或改写成中文，再去做检索。这是最直接的方案。

第二层是使用多语言 Embedding。选择支持中英文跨语言对齐的 embedding 模型，让英文 query 和中文文档能落到接近的向量空间里。这样不一定必须先翻译，也能召回中文内容。

第三层是双路召回。对于英文问题，可以同时用英文原 query 和中文改写 query 检索，再合并结果、去重、rerank。这样能兼顾原始语义和翻译后的中文表达。

工程上我会这样做：

1. 先判断 query 语言
2. 如果和知识库主语言不同，生成中文改写 query
3. 原 query 和改写 query 双路召回
4. 用 rerank 或相似度阈值筛选结果
5. 最终回答可以按用户语言输出，比如用户英文问就英文答，但引用中文资料

这样比单纯“把问题翻译一下”更稳，也更接近 Agentic RAG 的做法。

## 三、这场最应该重点补强的回答

### 1. AI coding 不要只讲方法，要讲具体案例

低分表达容易变成：

```text

```

更好的表达是：


面试官要听的是“你真的这么做过”，不是“你知道应该这么做”。

低分表达：


```text
RAG 分离线建库和在线检索。离线先清洗文档、切 chunk、做 embedding、存向量库；在线把用户 query 也做 embedding，和文档向量做相似度召回，再把 top_k 片段、来源和用户问题一起放进 prompt，让模型基于证据回答。

```

```text

模型负责理解意图和规划下一步，工具负责访问外部能力，比如知识库、数据库、API。
工程上最关键的是工具 schema 清晰、路由可控、状态可追踪、失败可兜底。
```

## 五、这场面试一句话总结

这场面试不难，但它很考验“AI 工程化表达”。你已经有项目和方向意识，下一步要把回答从“我知道这个概念”升级成“我做过这个链路，并且知道怎么优化、怎么上线、怎么评估”。
