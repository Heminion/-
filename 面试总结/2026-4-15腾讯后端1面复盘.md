### 2. 第一道算法题：根据中序遍历和后序遍历构造二叉树。你说一下思路。

高分回答：

这题的核心是利用后序遍历的最后一个元素确定当前根节点，再用根节点在中序遍历中的位置把数组划分成左子树和右子树。

具体做法是：先用 HashMap 记录中序遍历中每个值对应的下标，这样可以 O(1) 找到根节点位置。递归函数维护当前中序区间 `[inL, inR]` 和后序区间 `[postL, postR]`，如果区间为空就返回 null。每次取 `postorder[postR]` 作为根节点，找到它在中序中的下标 `idx`，左子树节点数是 `idx - inL`，右子树节点数是 `inR - idx`，再递归构造左右子树。

区间划分如下：

```java
leftSize = idx - inL;
root.left = build(inL, idx - 1, postL, postL + leftSize - 1);
root.right = build(idx + 1, inR, postL + leftSize, postR - 1);
```

复杂度方面，每个节点只创建一次，HashMap 查下标是 O(1)，所以时间复杂度是 O(n)，额外空间是 O(n)，递归栈最坏 O(n)，平均平衡情况下 O(log n)。

### 4. 你看一下 buildTree 里的递归终止条件，有发现问题吗？

高分回答：

递归终止条件应该判断当前区间是否为空，也就是左边界大于右边界：

```java
if (inL > inR || postL > postR) {
    return null;
}
```

不能只判断相等。区间长度为 1 时，`inL == inR` 反而是合法叶子节点，应该继续创建节点；只有 `inL > inR` 才表示没有节点可构造。后序区间同理。

### 5. 第二道算法题：如果没有最优思路，最暴力方式是什么？排序可以自己实现吗？

高分回答：

如果这题的核心是先对数组做排序，再基于排序结果求答案，那么最直接的暴力思路是先排序，再按题目要求扫描或取值。面试中即使不会最优解，也应该先给出一个可运行方案。

如果不能直接用库函数，我可以手写快排或归并排序。快排平均时间复杂度 O(nlogn)，原地排序，空间复杂度主要是递归栈；为了避免最坏 O(n²)，可以随机选 pivot。

Java 快排示例：

```java
void quickSort(int[] nums, int l, int r) {
    if (l >= r) return;
    int pivotIndex = l + (int) (Math.random() * (r - l + 1));
    swap(nums, pivotIndex, r);
    int pivot = nums[r];
    int i = l;
    for (int j = l; j < r; j++) {
        if (nums[j] <= pivot) {
            swap(nums, i++, j);
        }
    }
    swap(nums, i, r);
    quickSort(nums, l, i - 1);
    quickSort(nums, i + 1, r);
}

void swap(int[] nums, int i, int j) {
    int tmp = nums[i];
    nums[i] = nums[j];
    nums[j] = tmp;
}
```

面试时更重要的是不要沉默：先说暴力解、复杂度和能否优化，再尝试写代码。

### 6. 第三道算法题：长度为 n 的木棍，给定若干切割点，每次切割成本是当前木棍长度，求最小总成本。

高分回答：

这题是区间 DP。关键点是：一次切割的成本不是固定位置差，而是当前被切的那一段木棍长度；不同切割顺序会影响后续成本，所以不能简单贪心。

做法是先把切割点排序，并在两端加上 `0` 和 `n`。设排序后的数组为 `cuts`，`dp[i][j]` 表示把 `cuts[i]` 到 `cuts[j]` 这一段木棍内部所有切割点都切完的最小成本。

如果 `i` 和 `j` 中间没有切割点，也就是 `j == i + 1`，则 `dp[i][j] = 0`。否则枚举最后一次切割点 `k`，其中 `i < k < j`，最后一次切这一段的成本是 `cuts[j] - cuts[i]`，左右两边成本分别是 `dp[i][k]` 和 `dp[k][j]`：

```java
dp[i][j] = min(dp[i][k] + dp[k][j] + cuts[j] - cuts[i])
```

Java 代码：

```java
public int minCost(int n, int[] rawCuts) {
    int m = rawCuts.length;
    int[] cuts = new int[m + 2];
    cuts[0] = 0;
    cuts[m + 1] = n;
    for (int i = 0; i < m; i++) {
        cuts[i + 1] = rawCuts[i];
    }
    Arrays.sort(cuts);

    int[][] dp = new int[m + 2][m + 2];
    for (int len = 2; len < m + 2; len++) {
        for (int i = 0; i + len < m + 2; i++) {
            int j = i + len;
            dp[i][j] = Integer.MAX_VALUE;
            for (int k = i + 1; k < j; k++) {
                dp[i][j] = Math.min(dp[i][j],
                        dp[i][k] + dp[k][j] + cuts[j] - cuts[i]);
            }
            if (dp[i][j] == Integer.MAX_VALUE) {
                dp[i][j] = 0;
            }
        }
    }
    return dp[0][m + 1];
}
```

复杂度是 O(m³)，m 是切割点数量；空间复杂度 O(m²)。如果切割点数量不大，这是标准解法。

### 8. Redis 和 MySQL 在项目里分别承担什么角色？它们之间怎么协作？

高分回答：

在这个项目里，MySQL 是核心数据的持久化存储，负责保存房源、客户、房型、校对结果等业务事实数据；Redis 主要作为缓存层，用来缓存读多写少或访问频率较高的数据，比如配置类数据、房源详情、部分列表查询结果等。

一次典型读请求的流程是 Cache Aside 模式：

1. 先查 Redis
2. 命中则直接返回
3. 未命中则查 MySQL
4. 查到结果后写入 Redis，并设置合理过期时间
5. 返回结果给调用方

写请求一般以 MySQL 为准：

1. 先更新 MySQL
2. 再删除 Redis 缓存

这里选择删除缓存而不是更新缓存，是因为缓存里的结构可能和数据库表结构不完全一致，直接更新容易遗漏字段或并发覆盖；删除后让下一次读请求重新从数据库加载，逻辑更简单，也更不容易出错。

### 9. 你是怎么保持 Redis 和 MySQL 缓存一致性的？Cache Aside 具体步骤是什么？

高分回答：

我会采用 Cache Aside，也就是旁路缓存模式。读的时候先读缓存，缓存没有再读数据库并回填缓存；写的时候先更新数据库，再删除缓存。

具体步骤是：

读流程：

1. 查询 Redis
2. Redis 命中，直接返回
3. Redis 未命中，查询 MySQL
4. MySQL 查询到数据后写入 Redis，并设置过期时间
5. 返回数据

写流程：

1. 开启业务更新
2. 更新 MySQL
3. MySQL 更新成功后删除对应 Redis key
4. 如果删除缓存失败，记录日志并通过重试、消息队列或 Canal/binlog 异步补偿

为什么通常是“先更新数据库，再删缓存”：因为数据库是最终数据源，先保证持久化成功；缓存只是加速层，删除后下一次读会加载新值。

不过这个方案只能保证最终一致性，不能保证强一致性。并发下可能出现一个线程读到旧数据并回填缓存，另一个线程刚更新完数据库并删除缓存，最终缓存里短暂留下旧值。所以要结合过期时间、延迟双删、删除失败重试、订阅 binlog 等方式兜底。

### 10. 先更新数据库再删除缓存会有什么问题？会不会删完缓存后又被写入旧数据？怎么解决？

高分回答：

会有这种可能。典型并发场景是：

1. 线程 A 读缓存未命中
2. 线程 A 查询数据库，读到了旧值
3. 线程 B 更新数据库为新值
4. 线程 B 删除缓存
5. 线程 A 把刚才读到的旧值写回 Redis

这样 Redis 里会短暂出现旧数据。

常见解决方案有几类：

1. 设置较短过期时间，让旧缓存即使写回也能自动过期
2. 延迟双删：更新数据库前或更新数据库后立即删一次缓存，再延迟一小段时间删第二次，尽量覆盖并发读回填旧值的窗口
3. 删除失败重试：删除缓存失败不能静默失败，可以写入重试队列，异步重试删除
4. 订阅 binlog：通过 Canal 这类工具监听数据库变更，异步删除或更新缓存
5. 对强一致性要求特别高的场景，不应该依赖普通缓存，可以加锁、串行化写读或直接读数据库

延迟双删常见步骤是：

1. 删除缓存
2. 更新数据库
3. 等待一段时间，比如几十毫秒到几百毫秒，时间要覆盖大多数读数据库并回填缓存的耗时
4. 再删除一次缓存

也有工程里采用“先更新数据库，再删缓存，再延迟删一次”的变体。面试中要强调：延迟双删不是强一致方案，只是降低旧值回填概率；最终仍要配合过期时间和失败重试。

### 11. MySQL 联合索引了解吗？它底层是怎么组织的？

高分回答：

联合索引是基于多个列一起建立的索引，比如：

```sql
CREATE INDEX idx_class_name_score ON student(class_id, name, score);
```

在 InnoDB 里，联合索引也是一棵 B+ 树，只是索引 key 由多个列按定义顺序组成。它的排序规则是先按第一列排序，第一列相同再按第二列排序，第二列也相同再按第三列排序。

所以联合索引最重要的使用规则是最左前缀原则：查询条件要从索引最左列开始连续使用，才能比较充分地利用索引。比如索引是 `(class_id, name, score)`：

```sql
where class_id = 1
where class_id = 1 and name = '张三'
where class_id = 1 and name like '张%' and score > 80
```

这些都可能用到这个联合索引。但如果只查：

```sql
where score > 80
where name = '张三'
```

通常无法有效利用这个联合索引的有序性，因为没有从最左列 `class_id` 开始。

### 12. 如果有一个学生成绩系统，有姓名、ID、分数，你要怎么设计索引？

高分回答：

索引设计不能只看有哪些字段，而要先看查询场景。

如果学生 ID 是主键或唯一标识，那么它本身适合做主键索引或唯一索引：

```sql
PRIMARY KEY(id)
```

这时没有必要为了“ID、姓名、分数都有”就建 `(id, name, score)`。因为只要 `id` 是等值查询，主键索引已经可以非常快地定位一条记录，后面的 `name` 和 `score` 对查询帮助不大。

如果常见查询是“查某个班级 80 分以上的学生，并按分数排序”，更合理的索引可能是：

```sql
CREATE INDEX idx_class_score ON student(class_id, score);
```

如果常见查询是“查某个班级姓张的学生”，可以考虑：

```sql
CREATE INDEX idx_class_name ON student(class_id, name);
```

然后 SQL 写成：

```sql
where class_id = ? and name like '张%'
```

这样可以利用 `class_id` 的等值匹配和 `name` 的前缀匹配。注意 `like '%张'` 或 `like '%张%'` 通常不能很好利用普通 B+ 树索引。

所以高分回答是：ID 查单人用主键索引；按分数筛选就让分数出现在能被利用的位置；按班级 + 姓名前缀查，就建 `(class_id, name)`；联合索引顺序要服务于高频查询条件，而不是机械地把字段都拼进去。

### 13. 查分数 80 分以上的学生，能命中你设计的 `(id, name, score)` 联合索引吗？

高分回答：

基本不能有效命中。因为 `(id, name, score)` 的 B+ 树首先按 `id` 排序，只有在 `id` 相同的范围内才按 `name`、`score` 排序。如果查询条件只有：

```sql
where score > 80
```

没有使用最左列 `id`，就无法利用这个联合索引快速定位 `score > 80` 的范围，通常会走全表扫描或选择其他更合适的索引。

如果这个查询很高频，应单独为分数建索引：

```sql
CREATE INDEX idx_score ON student(score);
```

如果还带班级条件，比如：

```sql
where class_id = ? and score > 80
```

更合理的是：

```sql
CREATE INDEX idx_class_score ON student(class_id, score);
```

因为 `class_id` 可以等值定位班级范围，`score` 再做范围扫描。

### 14. 如果想查一个班级所有姓张的同学，联合索引能用吗？

高分回答：

要看索引设计和 SQL 写法。

如果索引是：

```sql
CREATE INDEX idx_class_name ON student(class_id, name);
```

SQL 是：

```sql
where class_id = ? and name like '张%'
```

那么可以利用联合索引。因为 `class_id` 是最左列等值匹配，`name like '张%'` 是前缀匹配，B+ 树可以定位到该班级下姓名以“张”开头的一段连续范围。

但如果 SQL 是：

```sql
where name like '%张%'
```

这种前面带通配符的模糊查询，一般无法利用普通 B+ 树索引的有序性。

如果只是“全校姓张的学生”，没有班级条件，则 `(class_id, name)` 不能充分使用，因为缺少最左列 `class_id`；可以考虑单独建 `name` 索引，或者根据业务使用搜索引擎 / 全文索引。

### 15. 进程和线程的区别是什么？



| 对比项          | 进程                                              | 线程                                                |
| :-------------- | :------------------------------------------------ | :-------------------------------------------------- |
| 基本定义        | 操作系统进行资源分配的基本单位                    | CPU 调度和执行的基本单位                            |
| 地址空间        | 每个进程有独立的虚拟地址空间                      | 同一进程内的线程共享该进程的地址空间                |
| 资源拥有        | 拥有独立的代码段、数据段、堆、文件描述符等资源    | 本身不独立拥有大量资源，主要共享所属进程的资源      |
| 私有内容        | 进程控制块、独立地址空间、打开的文件等            | 程序计数器、寄存器、线程栈、线程 ID、ThreadLocal 等 |
| 创建销毁开销    | 较大，需要分配独立资源和地址空间                  | 较小，只需创建线程执行上下文                        |
| 上下文切换开销  | 较大，可能涉及地址空间切换                        | 较小，通常只切换线程上下文                          |
| 通信方式        | 需要 IPC，例如管道、消息队列、共享内存、Socket 等 | 可直接读写共享变量，但需要加锁保证线程安全          |
| 数据共享        | 默认不共享，隔离性强                              | 默认共享进程内存，共享方便但风险更高                |
| 安全性 / 隔离性 | 隔离性好，一个进程崩溃通常不直接影响其他进程      | 隔离性弱，一个线程异常可能影响整个进程              |
| 并发场景        | 适合需要强隔离、独立生命周期的任务                | 适合需要轻量并发、频繁共享数据的任务                |
| 典型例子        | 浏览器多进程、服务 worker 进程、数据库进程        | Web 服务器线程池、后台异步任务、并发请求处理        |

---

### 16. 哪些资源是线程独有的？

高分回答：

线程共享进程的地址空间，但每个线程也有自己独立的执行上下文，主要包括：

1. 程序计数器，用来记录当前线程执行到哪条指令
2. 寄存器上下文，线程切换时需要保存和恢复
3. 线程栈，用来保存方法调用栈、局部变量、返回地址等
4. 线程私有数据，比如 ThreadLocal
5. 线程 ID、调度状态、优先级等内核调度相关信息

如果从 Java 角度说，每个线程私有的是程序计数器、Java 虚拟机栈和本地方法栈；堆和方法区是线程共享的。

---

### 17. 什么情况下用线程？什么情况下用进程？

高分回答：

如果任务之间需要频繁共享内存数据、协作成本要低，通常更适合用多线程。比如 Web 服务处理多个请求、后台异步任务、IO 密集型任务，都可以通过线程池提高并发能力。

如果更看重隔离性、稳定性和安全边界，通常更适合用多进程。比如浏览器不同标签页、服务的 worker 进程、需要隔离崩溃影响的任务，就适合进程模型。

CPU 密集型任务不一定简单等于“用进程”。更准确地说，要结合语言运行时和部署环境判断。比如 Java 没有 GIL，CPU 密集型任务也可以使用固定大小线程池，让线程数接近 CPU 核心数；而在有 GIL 限制的语言里，多进程可能更适合充分利用多核。

所以我的判断标准是：需要共享数据和轻量并发，优先线程；需要强隔离和独立生命周期，优先进程；CPU / IO 密集决定的是并发度和调度模型，而不是唯一标准。

---

### 18. 进程间通信方式有哪些？

高分回答：

常见 IPC 方式有：

1. 管道：适合有亲缘关系的进程，半双工，通常用于父子进程
2. 命名管道 FIFO：在文件系统中有名字，无亲缘关系的进程也可以通信
3. 消息队列：以消息为单位通信，内核维护队列，解耦发送方和接收方
4. 共享内存：多个进程映射同一块物理内存，速度最快，但需要信号量、互斥锁等同步机制
5. 信号量：主要用于进程间同步和互斥，不适合传大量数据
6. 信号：用于通知进程某个事件发生，比如终止、暂停、用户自定义信号
7. Socket：可以用于同机或跨机器通信，是分布式场景最常用的方式

如果面试官追问性能，通常共享内存最快；如果追问跨机器，Socket 最通用；如果追问简单父子进程通信，管道最常见。

---

### 19. 管道和命名管道的区别是什么？

高分回答：

普通管道通常用于有亲缘关系的进程，比如父子进程之间通信。它没有文件系统中的名字，生命周期一般跟随进程，通信方式通常是半双工。

命名管道也叫 FIFO，它在文件系统中有一个路径名，因此没有亲缘关系的进程也可以通过打开同一个 FIFO 文件进行通信。它仍然是先进先出的字节流通信方式，但适用范围比普通管道更广。

简单总结：普通管道依赖亲缘关系，命名管道通过文件系统路径建立连接，可以服务无亲缘关系进程。

---

### 20. 操作系统的虚拟内存了解吗？

高分回答：

虚拟内存是操作系统给每个进程提供的一套独立、连续的虚拟地址空间。进程看到的是连续地址，但实际物理内存可以是不连续的，虚拟地址到物理地址的映射由页表和 MMU 完成。

以分页管理为例，虚拟地址会被划分成页，物理内存划分成页框。进程访问某个虚拟地址时，CPU 通过页表把虚拟页号转换成物理页框号；如果对应页不在内存，就会触发缺页中断，由操作系统把数据从磁盘加载到内存。

---

### 21. 虚拟内存的优势是什么？

高分回答：

虚拟内存主要有四个优势：

1. 地址空间隔离：每个进程都有独立虚拟地址空间，不能随意访问其他进程内存，提高安全性和稳定性
2. 简化编程模型：程序可以认为自己拥有连续完整的地址空间，不需要关心物理内存碎片
3. 提高内存利用率：物理内存可以按页分配，不要求连续，减少外部碎片
4. 支持更大的逻辑内存：通过按需加载和换页，程序可使用的虚拟地址空间可以大于实际物理内存

另外，它还支持内存映射文件、共享库、多进程共享只读代码段、写时复制等机制。比如 fork 后父子进程可以先共享物理页，只有写入时才复制，从而降低创建进程的成本。

---

### 22. TCP 和 UDP 的区别是什么？

高分回答：

TCP 和 UDP 的核心区别可以从连接、可靠性、有序性、传输单位和适用场景几个角度讲。

TCP 是面向连接的，通信前需要三次握手建立连接；UDP 是无连接的，发送方可以直接发数据报。

TCP 提供可靠传输，依靠序列号、确认应答、超时重传、滑动窗口、拥塞控制等机制保证数据尽量完整到达；UDP 不保证可靠性，丢包、重复、乱序都需要应用层自己处理。

TCP 保证字节流有序，接收方读到的是按发送顺序重组后的数据；UDP 是数据报协议，每个包独立发送，网络层面不保证到达顺序。

TCP 适合对可靠性要求高的场景，比如文件传输、HTTP、数据库连接；UDP 适合低延迟、允许少量丢包或由应用层自定义可靠性的场景，比如直播、实时音视频、DNS、游戏同步。

---

### 23. TCP 的有序性指什么？UDP 接收方没法区分数据顺序吗？

高分回答：

TCP 的有序性指的是：应用层从 TCP 连接里读取到的数据顺序，和发送方写入 TCP 连接的字节顺序一致。底层网络包即使乱序到达，TCP 也会根据序列号重排，并且只把连续有序的数据交给应用层。

UDP 本身不保证顺序，但这不代表接收方一定没法区分顺序。UDP 报文里没有 TCP 那种连接级别的序列号和重排机制，不过应用层可以在 UDP payload 里自己加序号、时间戳、帧编号等字段。接收方根据这些字段就能判断先后顺序、发现丢包、做乱序重排或丢弃过期包。

所以准确说法是：UDP 协议本身不提供有序交付；如果业务需要顺序，要由应用层协议自己设计。

---

### 24. 像 UDP 直播传输视频，接收方也需要知道数据顺序，这里怎么实现有序化？

高分回答：

UDP 直播或实时音视频通常会在应用层协议里自己加顺序控制，而不是依赖 UDP 本身。

常见做法是：

1. 每个 UDP 包携带序列号、时间戳、帧号等元信息
2. 接收端维护一个 jitter buffer，也就是抖动缓冲区，短暂缓存乱序到达的数据包
3. 在可接受延迟范围内，根据序列号或时间戳重排
4. 如果某些包超时还没到，就选择丢弃、插帧、用上一帧补偿，或者在少量场景下请求重传
5. 播放端按时间戳持续解码和播放，保证整体体验连续

实时音视频更关注低延迟，所以不会像 TCP 那样为了严格可靠而无限等待丢失的包。因为直播里旧包即使重传回来，也可能已经错过播放时间，价值不大。实际工程中可能使用 RTP/RTCP、QUIC 或自研 UDP 协议，在应用层平衡顺序、丢包恢复和延迟。

## 四、下次面试注意事项

1. 不会最优解时，先给暴力解。面试官通常愿意沿着暴力解引导你优化
2. 回答基础题时不要只背一句定义，要主动补“场景 + 机制 + 缺点”
3. 联合索引设计一定先问查询条件，不能机械地把字段拼成索引
4. 简历上写 Redis / MySQL，就默认会被问一致性、索引、事务、缓存问题
5. 算法题思路先用三句话概括，再讲代码细节，避免一开始陷入变量名和下标

这场面试官最后的建议很准确：校招后端一面主要看基础。短期内最有效的提升方式，是把高频八股整理成“可追问版本”，同时每天稳定刷 2-3 道基础算法题，优先保证现场能写出来。
